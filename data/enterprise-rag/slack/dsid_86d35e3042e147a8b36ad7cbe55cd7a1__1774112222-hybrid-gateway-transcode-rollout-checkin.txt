maya: thinking out loud — should we converge on a hybrid gateway model for internal APIs? ie an L7 router that handles routing/quotas/observability + lightweight per-service adapters for proto-to-rest where needed

oliver: +1 to hybrid in principle. main concern is where to enforce quota and auth. gateway makes single place for telemetry but can be a bottleneck

sasha: telemetry note — if we centralize, we need stable request IDs and token-level cost attribution. console needs per-route token breakdown (not just service-level)

chen: proto evolution worry: if we rely on gateway for transcoding, we must support schema evolution rules (optional fields, oneofs) or we'll break older clients. prefer explicit adapter for complex contracts

liam: operationally sidecars solve backpressure and let services keep native gRPC. gateway can do routing + canary + fast-fail. but sidecars add rollout complexity across many services

maya: tradeoffs: gateway-first makes onboarding easier for new teams (no sidecar work) and simplifies rollout UX in console (single toggle). sidecars give lower tail latency and preserve client-server streaming

oliver: what about HTTP/2 multiplexing? if gateway does grpc->http/1.1 rest for browser clients we lose streaming. could expose grpc-web and do transcoding only for plain REST clients

chen: +1. propose pattern: gateway exposes native gRPC and grpc-web, plus a `transcode` flag on routes that enables autogenerated REST stubs. add CI lint that checks proto-forwards before enabling transcode

sasha: quotas: we should support two enforcement modes — "gateway" and "service". Gateway mode applies umbrella quotas (global call rate), service mode lets service enforce fine-grained token-based quotas. Console should surface which mode is active per route

liam: also need emergency fallback policy. if gateway overloads, route degrade to a cached model or lower-cost model, or fail-open to a fallback service. existing deploy-bot can flip route flags but we need safer UI in console

maya: UX ask: make canary + rollback simple. A single route config in console: primary variant, canary percent, fallback variant. telemetry shows token and latency differential live. Product wants that for Dedicated customers

oliver: schema & client SDKs: if we commit to protos we should auto-generate first-class SDKs for rest and grpc-web. otherwise teams will invent inconsistent adapters

chen: also, add a proto-compat check in CI that blocks non-backwards compatible changes to protos used by more than 1 service version. annotate protos with stability levels

sasha: telemetry mapping: route -> model -> variant -> cost. we need a single ID passed through request headers so trace + cost attribution works end-to-end. suggest `x-rw-request-id` and `x-rw-route-id`

liam: ops: rollout plan: 1) implement route metadata and flags, 2) telemetry headers, 3) gateway-only quotas, 4) per-service enforcement, 5) SDK autogen. land in two sprints for a beta
