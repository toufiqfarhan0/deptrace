Priya: heads up 1: dashboards with many small panels (20+) show high p99s when RBAC + composite caching enabled. saw this during load test yesterday.
Ethan: hmm, composite cache should reduce backend hits. are permissions evaluated before cache lookup or after cache hit?
Priya: current flow: panels compute canonical key -> check composite-cache -> if miss, call perms-service -> if allow, fetch panel data -> write cache. so perms are gated before expensive data fetch.
Luis: that means each cache miss triggers a perms RPC. for a cold dashboard that's N perms calls. could be the source of tail.
Naomi: did we try swapping order: fetch data then authorize? cheaper in aggregate but risky - we'd pull data for unauthorized principals.
Priya: exact tradeoff. we considered data-first + post-filter in a previous RFC but ops rejected due to leak risk.
Ethan: two safer options: 1) batch perms for the whole dashboard, 2) seed composite-cache with precomputed allow bitmaps at dashboard-level that we can check locally.
Luis: bitmap idea is neat: perms-service computes a small bloom/bitmap of allowed principals per-dashboard-version and returns with cache entry. then panels check bitmap locally. saves RPCs on subsequent loads.
Naomi: but bitmap size vs false positive rate? also keys rotate when roles change. need TTL and invalidation hooks.
Priya: we can mitigate with 2-phase validation: bitmap optimistic allow => render; if audit-level or explicit deny occurs, call perms-service to validate the specific resource and increment miscompare metric.
Ethan: add metrics: rbac.bitmap_fp and rbac.bitmap_miscompare_count. track by tenant.
Luis: batching perms is simpler to implement: just POST /perms/batch with list of resource ids. perms-service can optimize via internal index and return a compact list of allowed resources. downside: still RPC cost but amortized.
Naomi: perms-service CPU might spike. can we provide a cache priming API from console-control-plane on dashboard update? then perms-service pushes dashboard-level allow list into CDN or a distributed cache.
Priya: push model increases coupling and operational complexity. prefer read-path optimizations first.
Ethan: proposal: incremental plan:
- short term (hotfix): when loading dashboards, parallelize panels' perms calls with concurrency limit (8) to reduce p99 blocking. feature flag `dashboard.perms.parallel`.
- medium term: implement `POST /perms/batch` and query-executor prefetch that hits /perms/batch once per dashboard load (FF controlled). cache response keyed by (tenant, dashboard-version). TTL 45s.
- longer term: explore dashboard-level allow bitmaps pushed by perms-service on dashboard-change events (opt-in tenants).
Naomi: agree. add safety: always require final single-resource recheck before exposing any write or export action. read-only rendering can be optimistic.
Luis: QA note: need synthetic tests that simulate role churn (add/remove role) and ensure TTL/invalidation behaves.
