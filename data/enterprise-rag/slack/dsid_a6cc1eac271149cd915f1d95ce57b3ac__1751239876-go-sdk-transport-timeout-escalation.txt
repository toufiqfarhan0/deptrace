kevin_go_eng: Yep. Short explanation: if requests are canceled frequently, connections can accumulate in a half-closed state and if Transport defaults aren't tuned you can hit slow handoffs and 504s. Also older SDK did not set ResponseHeaderTimeout or IdleConnTimeout meaning hung connections linger.

kevin_go_eng: That lines up. Two immediate mitigation suggestions for customers who can't upgrade: 1) configure SDK to use a Transport with smaller MaxIdleConnsPerHost and an IdleConnTimeout; 2) set a ResponseHeaderTimeout or overall client.Timeout so hung requests kill earlier. Example patch we recommend: 
```
tr := &http.Transport{
  MaxIdleConns: 100,
  MaxIdleConnsPerHost: 20,
  IdleConnTimeout: 30 * time.Second,
  ResponseHeaderTimeout: 5 * time.Second,
}
httpClient := &http.Client{
  Transport: tr,
  Timeout: 10 * time.Second, // total request deadline
}
// pass httpClient into sdk (newer versions accept it)
```
kevin_go_eng: Also ensure every code path calls `resp.Body.Close()` even on error. Otherwise connections leak.
liam_oncall: For the long-term fix we shipped a patch in go-sdk v1.0.0: SDK now constructs a Transport with sensible defaults (IdleConnTimeout/ResponseHeaderTimeout) and exposes a WithHTTPClient option. Recommend upgrading to v1.0.0+; it also fixes a subtle bug where client.Timeout wasn't honored because context was used incorrectly.
