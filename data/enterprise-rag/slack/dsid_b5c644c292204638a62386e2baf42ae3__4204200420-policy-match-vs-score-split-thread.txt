Sam W: Quick thought — we should decouple "policy matching" from "policy scoring" in the policy engine. current monolith makes caching + hotreload pretty painful.
Alex R: +1. can you sketch the surface? where do adapters live?
Sam W: Idea: split into two phases:
- Phase A: matcher -> returns candidate routes (ids + light meta)
- Phase B: scorer -> takes candidates + runtime metrics to produce ordered list + confidence
This lets us cache A aggressively and keep B fast/ephemeral.
Maria C: That helps with per-tenant overrides too. A can be tenant-aware cached key, B can incorporate live latency/cost signals.
Jess (infra): Concern: cache key explosion. tenants + region + model-version -> huge.
Sam W: agreed. propose TTL + selective shard keys: primary cache key = (tenant_id, route_template_id) and annotate with region hints. we invalidate on route-template change/hotreload.
Tina - Runtime: Also need to think about KV cache/coherency for scored results — B will depend on realtime capacity signals (free_slots, avg_latency). we should keep those inputs as annotations to scorer, not embedded in cache key.
Alex R: API shape suggestion:
