ajay: quick question — do we move forward with per-token canonical events for billing or keep the current compact-per-request aggregates?

lina: my vote is canonical events. makes audits and late-arrival reparations easier. but cost and storage are the tradeoff. :thinking_face:

sam: +1 for canonical from an accuracy POV. but remember our SLA for query latency/lookup during reconciliation — scanning billions of token events is expensive.

kevin: can we get the best of both worlds? store compact aggregates as primary, write a sampled canonical stream to cold storage for audits/backfills. cheaper day-to-day, auditable when needed.

ajay: that sounds plausible. how do we handle attribution though — tenant-level vs request-level provenance? current payload has tenant_id, route, model, token_count, fingerprint.

maria: we need an immutable provenance envelope if we're doing any kind of rollups or rehydration. something like:
```
{
  envelope_id,
  source_request_id,
  tenant_id,
  model_version,
  token_events_ref (optional),
  aggregate_metrics,
  timestamp,
  provenance_signatures[]
}
```

sam: love the envelope idea. the optional token_events_ref is key — pointer to cold canonical set when available. would allow a fast reconcile path: compare aggregates -> if mismatch, consult canonical ref.

kevin: what about idempotency? we get duplicated delivery from some connectors. If envelope_id is a GUID with signing, should be straightforward to dedupe at ingestion layer. but we also need a lease/claiming model for ownership of credits during a reconciliation window.

ajay: lease vs append-only ownership debate. append-only is simpler for audits, but leases help enforce temporary ownership for cashflow and invoice windows. thoughts?

lina: prefer append-only for source of truth + a short-lived lease table for operational flows (30-60s) that helps with near-real-time chargeability. leases expire; invoice job reads append-only and locks via idempotent markers before finalizing.

maria: agree. also add a reconciliation ledger that stores reconciled pointers so we don't re-run expensive scans. ledger row example:
```
{reconcile_id, envelope_id_range, reconciled_at, diff_summary_ref}
```

ajay: late arrivals — how tolerant are we? current system accepts late events up to 7 days. do we tighten that if we move more canonical?

sam: we can keep 7 days but change strategy: aggregates are computed with a watermark and we emit a provisional invoice. finalization after watermark + reconciliation window. add a correction event type for any delta.

kevin: correction events are painful for downstream billing systems. we should surface a clear contract: provisional -> final with a TTL for corrections (eg 30 days) and a separate corrections feed for accounting.

lina: perf note — if we keep token-level canonical, index by fingerprint+shard to make hotspotting less likely. also consider segmenting canonical by model_version to speed model-specific audits.

maria: compression + vectorized encodings help here. parquet on S3 with fast manifest layer works well. then aggregate pipeline can build from manifests instead of scanning raw.
