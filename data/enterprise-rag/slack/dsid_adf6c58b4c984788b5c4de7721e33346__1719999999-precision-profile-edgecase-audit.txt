sanjay: Quick follow-up after the quant profiles RFC — I ran an internal audit and found a couple of edge cases we didn't explicitly cover. Short list below, want opinions on what needs a runtime contract vs. an ops playbook.

maria: list please — good catch.

sanjay: 1) KV-cache + precision mismatch: if a request is served from cached KV entries created under fp16/int8 but we later route to fp4 hotpath, we can see instabilities in attention scaling. Not always catastrophic, but quality drift shows up on long-context prompts.

kevin: that's nasty. Are we talking about prefix caching across routes or within the same model variant?

sanjay: across compatible variants — e.g., model-v2.fp16 and model-v2.int8-1. They share weights but runtime kernels apply different quantized transforms. The cache stores raw kv tensors which assume a particular numeric interpretation.

ellie: do we have an example repro? If we can reproduce deterministically we should add it to the precision regression suite.

sanjay: I have a small repro with a long instruction-following prompt, will post later. For design: options are a) annotate cache entries with quant-steering metadata and only serve exact-match quant variants, b) store cache in dequantized fp32 canonical form (expensive memory), or c) add fallback check at runtime to rekey/regen cache if mismatch detected.

maria: pros/cons: (a) is cheap but fragments cache; (b) is heavy on memory but simple correctness; (c) is hybrid but adds latency on mismatch. Ops perspective prefers (a) + metrics to see fragmentation.

kevin: from runtime side, (a) looks straightforward: add a small 8-byte tag to each cache entry header with profile_id and kernel_hash. Quick lookup. Only caveat: we need a deterministic hashing function that accounts for quant metadata (scale/zero points).

ops-bot: deploy-checklist: ensure cache header bump is backward compatible. Old nodes must ignore unknown header and assume legacy semantics.

ellie: second edge case: tokenizer rounding for 4-bit packing. We saw a case where subtle whitespace normalization changed token ids that, after 4-bit packing, caused byte alignment bugs in our custom packer.

sanjay: yeah — the packer assumes token stream lengths mod 8 align in a certain way for the vectorized store. When tokenizer change changes pad behavior, we get silent corruption in corner prompts.

kevin: fix should be defensive: packer must validate post-pack checksum and fall back to scalar writer if checksum fails. Also add unit tests that fuzz tokenizer outputs across languages.

maria: add an integration test in the rollout that uses known tokenizer variations (emoji, CJK, combining marks). Failure should block canary.

ellie: third item: eval surfaces where int8 quality cost is non-linear with sequence length — short prompts are fine, long ones degrade faster than our regression threshold. That makes single-number quality budgets misleading.

sanjay: proposal: add "quality_curve" metadata to quant profiles — a small vector describing expected relative quality at [8, 64, 256, 1024] tokens. Runtime and dashboard can consume it for smarter routing and SLOs.

kevin: API impact? We could keep profiles backward compatible: add optional field in model catalog: "quality_curve": [0.99,0.96,0.88,0.7]. If missing, treat as flat 1.

maria: love that. Product will want UI knobs to prefer higher curve for chat flows. Also need UI to show per-route realized curve from telemetry.

ops-bot: telemetry-note: add tags: quant_profile_id, quality_bucket="short|medium|long", kv_cache_hit_quant_mismatch=true/false.

ellie: rollout strategy: canary quant variants only for read-only endpoints first (embeddings/rerank) then generation. Also add an automatic rollback if request-level perplexity delta > threshold for canary.

kevin: implementation detail: runtime should expose a quick "profile_compat" check RPC that clients (console/rollout controller) can call to verify caches, kernels, and storage format compatibility before routing traffic. That avoids surprises during switchover.

sanjay: agree. We should surface a clear operator command: `redwoodctl quant-audit --profile model-v2.int8-1 --samples 1000` which runs a mini-eval and reports mismatch rates.
