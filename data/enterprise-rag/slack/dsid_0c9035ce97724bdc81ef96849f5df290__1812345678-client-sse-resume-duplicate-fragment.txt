aleksandr: Sounds like two contributing factors: (1) the server resumes by replaying the last committed fragment, and (2) the SDK's SSE consumer treats each `data:` as authoritative without checking the resume id/seq. If Last-Event-ID == lastSeenSeq we should drop the first event after reconnect.

aleksandr: Also saw this with auth refresh in the middle of reconnect. If token refresh triggers a slightly different backend path (model-variant routing) the server might re-emit cached tail fragments. That makes simple dedupe by model+seq safer.

josh: Do we emit a `id:` line in SSE with the seq? If so the client can track last seen `id:` and ignore the first event when they reconnect with the same id. If server only uses an internal seq in `data`, that's harder for generic clients.

kate: Our server currently sets `id: <lastEventId>` for resume, but the first event chunk still has the same id as the last one. Browsers' EventSource spec: if you set Last-Event-ID header it tries to resume, but implementations differ on whether they emit the event that matches the id. The mismatch across browsers + our custom Node SSE parser causes inconsistent duplicates.

aleksandr: Suggested SDK changes: 
- expose `event.id` to higher-level SDK `StreamChunk` metadata
- on reconnect, if `event.id == lastSeenId` then drop the first event chunk (configurable policy: drop|merge|emit)
- add an optional `resume_seq` header (e.g., `Redwood-Resume-Seq`) that is an integer we atomically ack on server side so server can avoid replaying the final committed event

aleksandr: Quick patch I'd propose for the node SDK: when the HTTP client reconnects set a small in-memory flag `skipNextIfSameId=true` and on first received `id` compare to `lastId`. If equal, ignore that first payload. This is low-risk and can be toggled by a param `resumeDedup=true`

josh: I like adding explicit seq header in the protocol long-term. Short term the SDK-side drop is easiest. We should also add integration tests that simulate partial final tokens and reconnects.
