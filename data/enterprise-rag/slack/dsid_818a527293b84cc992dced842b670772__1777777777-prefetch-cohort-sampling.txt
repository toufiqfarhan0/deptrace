mike: thinking loud — proposal to prefetch model variants for canary traffic to avoid cold-start noise during early ramps. idea: when a request is selected into canary cohort, trigger a lightweight prewarm for that variant and mark the request as "prefetch_cohort" so telemetry can separate it.

sara: curious — prefetch sounds useful but worried about sampling bias. if prefetch hits always precede user requests, will we artificially inflate perf for canary?

mike: good point. plan is to do sparse prefetching: only prewarm for a small fraction of canary buckets (e.g., 10%) and keep the rest cold to measure realistic latency. also add a telemetry tag "prefetch=true|false".

raj: need to think about quota implications. prefetch is extra tokens/compute. for hosted customers we should charge or deduct from burst quota? can't have hidden extra cost.

anne: from Console/UX side — we need a single toggle on the rollout page: "enable prefetch for canary (sparse)" with a config for sample_rate and prefetch_ttl. show a clear cost delta and metric breakdown.

mike: yes — UX should show estimated QPS overhead and expected latency delta. also plan to expose "prefetch_cohort" in per-route dashboards so PMs can filter.

sara: propose config shape:
```yaml
canary:
  fraction: 0.05
  sampling:
    mode: sparse
    prefetch_rate: 0.1  # fraction of canary requests that get prewarm
  prefetch:
    ttl_seconds: 30
    budget_limit: 1000_per_minute
```

raj: +1 on budget limit. also tie prefetch to capacity class: only allow prefetch on pool types that can absorb short spikes (dedicated pools or burst-enabled). block for shared hostless when costlier.

mike: agreed. implementation sketch: routing layer sets header `x-prefetch=true` when a request triggers prewarm and writes an event to prewarm queue. worker pops queue and warms the variant in the right pool. routing still returns a 202 for the actual warm request if prefetch route is a background call.

anne: how will telemetry separate true user latencies vs prefetch-influenced? need deterministic labeling.

sara: label by `x-prefetch-origin` header: values {direct,user,prewarm-hit}. then metrics pipeline can compute P95_excluding_prefetch or show both.

mike: example routing rule we prototyped:
```json
{
  "route":"/v1/generate",
  "canary":{
    "fraction":0.05,
    "cohort_key":"user_id_hash"
  },
  "prefetch":{
    "enabled":true,
    "sparse_rate":0.1,
    "ttl_seconds":30
  }
}
```

raj: one more nit: consistent hashing. if cohort assignment changes during rollout (due to rolling config), we may orphan prewarmed cache entries. need to surface miss-rate on cache and a cleanup policy.

mike: we'll add metric `prefetch_cache_miss_ratio` and a scoped cleanup job that expires prefetch keys after ttl + grace. also include a canary-level tag so cleanup is limited to that canary's prewarm keys.
