maya: Heads up — after we pushed the 535.86 driver + CUDA 12.2 roll last night, we've got a regression: NVLink topology isn't being detected on mixed A100 nodes. NCCL falls back to SHM -> SOCKET for most peer transfers, huge perf hit.

leo: which cluster/region?

maya: prod-gpu-eu, also seeing on staging-us-west. Only on racks that have a mix of kernel versions (5.15.x + 6.1.x) and some older A100-SXM nodes.

taylor: any logs or nccl topo dump? short snips are fine.

maya: paste:
```
$ nvidia-smi topo --matrix
    GPU0 GPU1 GPU2 CPU
GPU0  X   NV    PHB  SYS
GPU1 NV   X     PHB  SYS
GPU2 PHB  PHB   X    SYS
```
but nccl shows:
```
NCCL INFO Topo: NVLINK not usable between 0 and 1 (p2p query failed)
NCCL WARN All-to-all using SOCKET fallback for peer 0-1
NCCL INFO SHM disabled (IPC failure)
```

indra: SHM disabled often due to IPC namespace or missing /dev/shm mount in container. Are these in k8s pods with ipcMode? any change in runtime flags?

maya: pods are default, we didn't change --ipc. Container runtime didn't update, only driver and kernel modules. dmesg on one node:
```
[  428.123456] NVRM: GPU 0000:3b:00.0: P2P peer lookup failed, peer 0000:3a:00.0
[  428.123460] nvidia-mig: failed to query P2P capability
```

jun: Could be the kernel driver ABI mismatch — mixing dkms-built modules with packaged driver? Which package mechanism did we use for 535? rpm or runfile?

maya: runfile installer (we used for faster rollout). Some older nodes still had kernel module from 525 and we forced install but didn't rebuild DKMS properly.

leo: that explains P2P failures. If module symbols mismatch, NVLink P2P ioctl can fail and NCCL disables p2p. Workaround: put affected nodes into maintenance and roll back to 525, or rebuild kernel module via dkms and reboot.

taylor: timeline wise, can we isolate by node label and cordon? Also we should avoid full rollback if we can hotfix: rebuild modules and restart kubelet + container runtime to rebind devices.

maya: doing a canary: cordoned 2 nodes in prod-gpu-eu and initiated dkms rebuild + reboot. I'll report perf after.

ops-bot: Incident created: INC-2025-0783 - "NVLink/NCCL P2P regressions after 535 driver rollout". Pager on-call: leo, taylor.

indra: another mitigation: set NCCL_P2P_DISABLE=1 to force consistent path (explicit SOCKET) while we fix drivers — avoids random mixed behavior, but costs throughput. Also NCCL_SHM_DISABLE=1 if IPC is flaky.

jun: note: forcing SOCKET may hurt multi-node perf but keeps correctness; useful temporary flag for training jobs that can't tolerate nondeterministic fallbacks.

maya: perf numbers after canary rebuild: peer bandwidth for single-GPU pairs went from 3.2 GB/s (socket fallbacks) back to 72 GB/s when NVLink restored. Good sign.

taylor: good. Next steps: 
- create an automated check during driver rollout: run `nvidia-smi topo --matrix` + `nccl-tests` smoke to validate NVLink/SHM
- add DKMS verification in rollout playbook
- add node label to identify kernel-driver mismatches

maya: I'll open a PR to update the rollout runbook + add a k8s admission job that checks /dev/shm and ipc namespace for GPU pods. 

leo: also add a step: if module version mismatch detected, mark node drainable and block burst autoscaler from placing new GPU pods.

maya: noted. will follow up with timeline and postmortem notes.
