ben: Sounds like a stub-resolver / split-horizon mismatch. Are nodes using systemd-resolved (127.0.0.53) and that stub is forwarding to the wrong upstream during egress failover?

alice: /etc/resolv.conf on the nodes is a symlink to /run/systemd/resolve/stub-resolv.conf → points to 127.0.0.53. Containers inherit that unless kubelet --resolv-conf is set.

devex-miguel: We've seen caching TTLs amplify this when the external DNS path briefly returns NXDOMAIN. If the stub caches the NXDOMAIN for the TTL, it propagates for the whole duration.

infra-bot: [alert] 1752345690 - service: model-registry.internal - high error rate detected from eu-west-1 edge pool (5xx/lookup failures)

ben: Quick mitigation options:
- flush stub cache: `resolvectl flush-caches` or `systemd-resolve --flush-caches` on host
- restart systemd-resolved: `systemctl restart systemd-resolved`
- point kubelet to real resolv.conf (e.g., /run/systemd/resolve/resolv.conf) via `--resolv-conf` so pods use the upstream resolver directly
- as a pod-level change, set dnsPolicy: Default or use dnsConfig to point to 10.10.2.5

alice: We applied a temporary fix on 3 nodes: `systemctl restart systemd-resolved` + `resolvectl flush-caches`. Those nodes recovered and started pulling models again. But this is manual and will reoccur.

chao: Long-term we should fix kubelet config so pods don't rely on the stub. Also check the egress NAT LB health: if the LB flips upstream during rolling deploys, the stub may forward to an upstream that doesn't have the split-horizon zones.

ben: Also consider lowering negative caching TTLs on the internal DNS for critical hostnames (SOA / NXDOMAIN TTLs) and set `ndots:2` if some lookups are being forced through search path and failing.
