kevin: Can you paste the NACL rule list and any VPC flow logs showing REJECTs? NACLs are stateless and evaluated by rule number ascending — a DENY earlier can block return traffic even if later rules allow 443.

joan: NACL inbound/outbound rules they sent (abbrev):
```
Rule 100  ALLOW  0.0.0.0/0  TCP  80-80
Rule 110  DENY   0.0.0.0/0  TCP  32768-32790   <-- recently added
Rule 120  ALLOW  0.0.0.0/0  TCP  443-443
Rule *    DEFAULT DENY
```

lia: That DENY range is suspicious — ephemeral client ports often live in 32768-61000 on many OSes. Because NACLs are stateless, the return packet from service->client uses a high dest port (the client's ephemeral). If the DENY hits before the ALLOW for 443, the return will be dropped.

kevin: Confirmed from their VPC flow logs: sample line ->
```
REJECT  srcaddr=3.120.45.67 dstaddr=10.1.2.3 srcport=443 dstport=32770 protocol=6
```
This matches the RSTs in tcpdump. So packets from our service to the client's ephemeral port were REJECTed by a NACL.

joan: Customer's security team added that DENY to block some scanner noise, put it at rule 110. It inadvertently came before the 443 allow.

lia: Fix options: either remove/move the DENY to a higher rule number (evaluated later), or explicitly allow ephemeral ranges ahead of it. For example add
```
Rule 105 ALLOW 0.0.0.0/0 TCP 1024-65535
```
before the deny so return traffic is permitted. Or narrow the DENY to a smaller subrange that doesn't intersect typical ephemeral ranges.

kevin: Quick mitigation we recommended to customer: add rule 105 ALLOW 1024-65535 (or at least 32768-61000) on both inbound and outbound NACLs on the private subnet, then test. Also verify the public NAT subnet NACL isn't denying the return. Security note: NACL default DENY still applies to everything else.
