anya: @michael @devon quick summary from infra side: PrivateLink = least collateral attack surface (no route table changes in customer VPC) and aligns with zero-trust. Peering works but requires route management and potentially transitive routing controls if they use TGW. Major blockers we see:
- Customer policy forbids cross-account route propagation in some banks (peering/TGW becomes a hard no)
- App teams often block outbound ephemeral ports; we try to avoid those requirements.

anya: Minimal firewall/SG example (share with cust):
```
# Outbound from customer app subnets to Redwood Private endpoints
Allow TCP 443 -> vpce-<redwood-vpce-id>.execute-api.<region>.amazonaws.com (HTTPS to control plane)
Allow TCP 443 -> <model-serving-vpce-hostname> (if using regional model endpoints)
# If using NAT for egress to external S3/artifacts
Allow TCP 443 -> 52.34.12.34/32, 52.34.12.35/32 (Redwood egress IPs - example only)
```
Notes:
- We prefer customers whitelist the endpoint DNS (CNAME) instead of IPs when allowed; if they require IPs we provide a small set of stable egress IPs for Private deployments.
- No inbound ports required to customer VPC for PrivateLink; all connections initiated by customer resources to the VPCE.
