elaine: quick architecture check: we've been iterating on continuous-batching tradeoffs and I want to propose a lane-aware prefetch gate instead of a single global headroom knob. thoughts? :mag:

pranav: lane-aware? as in separate prefetch budgets per latency lane (fast, normal, background)?

elaine: exactly. idea is to keep aggressive prefetch for background/embeddings lane but conservative for low-latency chat lanes. avoids hurting p95 for chat while keeping throughput for background.

tom: sounds promising. question: how do we enforce fairness when tenants have mixed traffic across lanes? e.g., tenant A sends both chat and embedding requests.

yuki: we could track per-tenant per-lane credits. admission checks `credit >= reserve_tokens`, otherwise route to slower lane or apply probabilistic deprioritization.

pranav: reserve_tokens API again? we should standardize: `reserve_tokens(tenant, lane, tokens) -> bool` and `return_hint(eviction_cost_est)` from scheduler to batcher.

elaine: yes. smaller surface than earlier proposals. lane is just an enum: fast|normal|background. batcher uses lane to pick coalesce window and batching cap.

tom: implementation detail: background lane can have higher allowed headroom and a separate kv partition to reduce eviction interference. that requires some runtime support.

yuki: partitioning KV by lane reduces warmup churn but increases memory footprint. tradeoff: extra memory vs fewer cold misses. we should simulate with our memory model.

elaine: good point. Mike (not in thread) previously ran memory sims showing 15% extra KV memory reduced p95 by ~40ms under mixed load. But results depend on skew.

pranav: another thought: admission should expose a soft-credit system so that tenants can borrow against future budget during short bursts, with an amortized repayment schedule. helps PLG users who spike.

tom: careful: borrowing introduces long-tail fairness and billing complexity. need guardrails: max-borrow = X% of monthly commit or a per-tenant cap.
