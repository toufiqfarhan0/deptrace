morgan: quick question — can we do a header-sniffing fallback gateway to route older clients to the legacy handler while new clients go to the v3 runtime? goal is minimal SDK churn and a clean migration window.

tess: possible. what header are we sniffing? X-Redwood-Client-Version or an Accept media type? order matters. also security/validation implications.

raj: had a small PoC: Accept first, then X-Client-Version. Nginx-based sniff adds ~3-7ms tail in our microbench, but main problem was it split continuous batching across model pools.

kyla: important callout — continuous batching expects homogenous model signatures. If we route same endpoint to two model pools (v2 vs v3), batching will fragment and throughput drops. A translation layer that normalizes v2 payloads into the v3 shape and forwards to v3 runtime keeps batching intact.

morgan: translation layer seems attractive. two options: 1) proxy that rewrites request bodies/headers on the fly, 2) lightweight compat runtime that implements v2 semantics and calls v3 models internally. pros/cons?

tess: proxy is simplest to ship but brittle: edge cases in payload shapes and new features could break transformations. compat runtime is heavier but more robust and testable. also, we need to tag translated requests for telemetry and billing.

raj: +1 on tagging. Also need a graceful fallback: if translation fails, either return 409 with migration guidance or route to a dedicated v2 pool. SLA-wise prefer keep serving rather than erroring.

kyla: implementation sketch:
```
# pseudocode for gateway sidecar
if request.headers.get("X-Redwood-Client-Version") == "v2":
  try:
    body = transform_v2_to_v3(request.body)
    request.headers["X-Compat-Translated"] = "v2"
    forward_to_v3_runtime(body, headers)
  except TransformError:
    route_to_v2_pool_or_respond_migration_hint()
else:
  pass_through()
```
