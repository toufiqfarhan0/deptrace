aj: heads-up — i'm kicking off a short PRD check-in for API keys + scoped tokens + RBAC. enterprise customers asked for: per-project api keys, ephemeral scoped tokens for serverless, and project-level role bindings. want to align on scope/launch criteria and any hard edge-cases before we spin up an RFC.

aj: context: product needs a simple migration path from current org-level api keys, plus an opt-in scoped token flow that operators can use without requiring full oauth. proposed constraints below. please react/comment.

aj: proposed acceptance criteria (draft):
- API: create per-project API keys that map to (org_id, project_id, key_id) and support metadata tags.
- Scoped tokens: short-lived (max 1h default) bearer tokens minted from an API key with a restricted scope claim; revocation supports immediate invalidation.
- RBAC: support role bindings at org and project levels; roles: owner, admin, editor, reader.
- Backwards compat: existing org-level keys continue to work but are flagged deprecated in console.
- Audit: every token/key issuance/revocation must produce an audit event with actor, reason, and originating IP.
- Security: tokens must be HMAC-signed, and we need KMS integration for key rotation.

aj: launch criteria: docs, SDK support (node/python), console UI for creating project keys, simple migration CLI, automated tests, and one enterprise beta customer signed off.

marie: thanks aj — high-level looks good. can we trim scope for initial beta? my suggestion: ship per-project API keys + RBAC binding, delay scoped-token minting to next sprint unless a customer absolutely needs it.

sam.k: +1 to narrowing. scoped tokens add a lot (minting service, revocation store, short-liveness checks). can we do a minimal scoped workaround: issue limited-lifetime keys (expire-at metadata) and treat revocation as rotate/delete?

olivia: @aj @marie one more product ask: console UX must show effective permissions at project level (so SREs can quickly verify). also need an exportable CSV of bindings for audits.

kevin: technical edge-cases we should list:
- key compromise: we need immediate global revocation path + propagation to inference serving nodes (cache invalidation).
- token reuse: prevent reuse after revocation (requires server-side token blacklist or token incremental nonce).
- cross-org delegation: if a user is in multiple orgs, ensure tokens always scoped to explicit org/project.
- old SDKs: older SDKs that assume org-key format must error with clear guidance.

aj: good catches. for cache invalidation — we can push revocation events via existing routing bus, but need SLOs on propagation (e.g., 30s for hosted region). add that to ACs?

marie: yes add propagation SLO. also add acceptance test: simulated key compromise — revoke key and run end-to-end that confirms inference requests fail within SLO.

sam.k: need to decide token format now. proposal: compact JWT-ish structure but signed with KMS. sample:
```
Authorization: Bearer scoped-<B64(header).B64(payload).sig>
payload: {iss: "redwood", sub: "key:org:proj:keyid", exp: 1700000000, scopes: ["inference:read"], jti: "uuid"}
```
if we carry jti we can blacklist on revoke. downside: server must check jti store for every request (adds latency).

olivia: can we do lazy blacklist + short expiry to avoid DB hit for every request? e.g., 1m blacklist window then rely on exp, but that weakens revocation guarantees. tradeoff needs documenting.

kevin: for hosted: we can use an in-memory fast bloom + periodic reconcile to a central revocation log to reduce latency. for dedicated/private customers we should provide a toggle for strict revocation (DB check) vs performance mode.
