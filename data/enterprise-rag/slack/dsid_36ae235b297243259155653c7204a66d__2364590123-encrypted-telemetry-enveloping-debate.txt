alex_m: Heads-up — I prototyped an "envelope-first" shape for telemetry that keeps encrypted blobs but exposes a small set of indexed fields for console queries. Trying to avoid a big, expensive full-table backfill.

tara_s: can you paste the shape? curious how many denorm fields we need for dashboards.

alex_m: sure, basic idea:

```
-- new column
envelope jsonb NOT NULL DEFAULT '{}'

-- envelope: {
  "meta": {"route_id": "r-x", "tenant_id": "t-1", "ts": 1670000000},
  "indexed": {"event_kind": "route.metric", "status": "ok", "cost_tokens": 12},
  "payload_enc": "<base64-aes-gcm>"
}
```

daniel: so indexed.* are the fields we keep for queries and grouping. payload_enc is opaque to analytics unless we decrypt.

kate_p: big question: who holds keys? if we encrypt payloads customers' private keys or our KMS? this affects backfill strategy.

alex_m: plan is to use service KMS for initial rollout, with an option for customer-managed CMKs later. that keeps operations simpler for analytics owners.

mike_s: how do we handle legacy queries that expect top-level columns like route, user_id? are we duplicating them into indexed?

eva_r: yeah we should keep a tiny set denormalized for common console paths: route_id, tenant_id, event_kind, ts, cost_tokens, maybe status.

alex_m: exactly. dual-write approach for a transition window:
1) add envelope column + indexed columns (nullable)
2) application dual-write: write both old fields and envelope.indexed
3) backfill historical rows to fill envelope.indexed in chunks
4) shadow reads for console: read indexed first, fallback to parse legacy columns

tara_s: chunked backfill — do we have a safe chunk size? we don't want to lock the table.

mike_s: can do update ... limit style via id ranges, use low io concurrency. sample job script:

```
while true; do
 psql -c "WITH c AS (SELECT id FROM telemetry_events WHERE envelope->'indexed' IS NULL LIMIT 10000) \
 UPDATE telemetry_events t SET envelope = jsonb_build_object('meta', jsonb_build_object('ts', t.ts), 'indexed', jsonb_build_object('event_kind', t.event_kind, 'route_id', t.route_id, 'cost_tokens', t.cost_tokens)) FROM c WHERE t.id = c.id RETURNING t.id;"
 sleep 2
done
```

daniel: also recommend creating a partial index for the indexed json path to avoid scanning full table:

```
CREATE INDEX IF NOT EXISTS telemetry_idx_eventkind ON telemetry_events ((envelope->'indexed'->>'event_kind')) WHERE envelope IS NOT NULL;
```

kate_p: ops considerations: streaming consumers (metrics, billing) need to either read indexed fields or decrypt payload. For billing we'll keep cost_tokens in indexed to avoid decrypting.

eva_r: query patterns: console dashboards do a lot of time-bucketed group-bys and filters by tenant+route. we should add a composite index on (tenant_id, route_id, ts) — but keep it thin.

alex_m: agreed. also a compatibility view helps: telemetry_view -> selects indexed fields and falls back to legacy columns. Console reads from view.

mike_s: question about retention: encrypted payloads increase storage cost. propose we keep payload_enc for 90 days default, then purge or archive to S3 for long-term customers.

tara_s: privacy/regulatory: if payloads contain PII, encrypting is necessary but we must also ensure audit logs for decryption and key usage. ops-bot: add KMS audit hook.
