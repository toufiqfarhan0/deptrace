maria: Quick proposal — add a client-side compatibility shim that translates legacy X-RD-Routing headers into the new routing_policy JSON payload. Goal is to avoid a server-side breaking change while we migrate SDKs + console mappings.

maria: Implementation idea: minor SDK patch (non-breaking) that enables `compat.routingShim` by default for two releases, emits telemetry header `x-rdw-client-migration: legacy` and a deprecation warning in logs. After rollout we flip default off and remove shim in a future major.

maria: Example usage (JS):
```js
const client = new RedwoodClient({
  compat: { routingShim: true }
});
```

maria: Example usage (Python):
```py
client = RedwoodClient(compat={"routing_shim": True})
```

jake: +1 on minimizing server churn. A couple concerns: 1) quota enforcement — if shim allows old headers to become new policies we need to ensure quota checks still happen correctly. 2) auth/validation — do we need extra server-side validation to avoid policy escalation?

sophie: runtime note — KV cache keys currently include routing id. If shim silently rewrites routing id we might blow caches or cause cache misses. Suggest the shim also emit a "legacy-routing-id" tag so runtime can map old->new cache keys, or keep old id in request metadata for cache lookup.

maria: good point. plan: shim will attach `x-rdw-legacy-id` (internal only) and server runtime will consult both ids when looking up prefix/KV cache. That should avoid premature cache churn.
