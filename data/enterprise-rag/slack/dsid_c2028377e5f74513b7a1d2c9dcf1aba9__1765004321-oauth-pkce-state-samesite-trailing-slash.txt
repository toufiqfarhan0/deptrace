jess (security): SameSite=Lax will block cookie on POSTs coming from cross-site POSTs if the redirect counts as a unsafe method; however most OAuth providers redirect via GET. But mobile browsers and some browser privacy features can treat the redirect as cross-site navigations and drop cookies. Also possible: the redirect URI registered in Google Console has no trailing slash while the actual callback has trailing slash, so session cookie might be set on /auth/start and path mismatch could matter if cookie path is more restrictive. Two things to check: cookie Path attribute and whether app is setting SameSite=None; Secure for cross-site flows.

samir (eng): Additional gotcha we've seen with SPAs using PKCE: the app stores code_verifier in sessionStorage/localStorage in the browser, but if the client is using a universal link that opens in an embedded webview (e.g., mobile in-app browser) storage can get cleared between steps. Also, corporate SSO and IdP intermediate redirects sometimes change the origin (e.g., identity-proxy.company.com -> accounts.google.com -> app.customer.com) which can break storage/cookies.
