Maria Chen: FYI I ran the multi-workload probe to compare kernel selection effects across synthetic vs replay harnesses for three representative workloads (chat-short, long-ctx, emb-batch).

Maria Chen: Quick summary: synthetic says kernel auto->matmul-opt is ~12% cheaper and P50/P90 better, but replay showed P99 tail regressions for long-ctx and higher KV miss churn.

Maria Chen: command I used:
```
./tools/loadrun --harness replay \
  --workloads chat-short,long-ctx,emb-batch \
  --kernels auto,force-fp16,force-int8 \
  --ramp 300 --duration 1200 --trace \
  --replay-window s3://replays/2026-03/multiworkload/
```

Sam Ortiz: nice. what's the gap between synthetic and replay numerically?

Maria Chen: synthetic long-ctx P99 210ms, replay long-ctx P99 420ms (same client QPS). P50/P90 pretty similar.

Liam Patel: :eyes: that's a big tail delta. did the runtime pick different kernels per workload?

Maria Chen: yes — auto picked matmul-opt for long-ctx, force-int8 kept lower variance in replay. matmul-opt has higher transient memory pressure on KV slots which seems to cause more evictions during bursts.

Anya Gomez: do you see increased KV eviction metrics when the kernel changes?

Maria Chen: 2x increase in kv_eviction_rate and kv_load_miss for the matmul-opt traces during the replay bursts. Also observed more GC spikes in the worker process (short heaps) at the same times.

Raul Mendes: Could be gating: matmul-opt uses bigger temporary buffers per batch, reduces effective KV cache capacity -> more cold reads -> longer tail. Were batch shapes different between synthetic and replay?

Maria Chen: yes. synthetic uses fixed batch-shapes tuned for throughput (batch=8 mostly). Replay has more varied batch-shapes, more small batches and a few huge ones. Kernel selection heuristics prioritized throughput metric and didn't account for KV effective capacity.

Sam Ortiz: that explains autoscale behavior too? I remember seeing higher scale-up churn for that run.

Maria Chen: Exactly — because of transient tail, autoscaler observed sustained high apparent latency and triggered scale-up, which consumed burst credits from the Dedicated pool. We burned ~35% of burst credits in one test window.

Liam Patel: Oof. Did you measure scale-up time delta?

Maria Chen: scale-up latency (start->ready) unchanged (~45s), but end-to-end user-observed recovery took longer due to warmup/KV misses. So scale-up didn't solve tail because KV warmup dominated (~120-180s).
