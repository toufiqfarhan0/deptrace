eng-infra-joe: Also have them check conntrack / SNAT pool exhaustion — if many concurrent flows you can run out of source ports and see asymmetric return paths or resets. Commands:
```
sudo conntrack -L | wc -l
sysctl net.netfilter.nf_conntrack_max
cat /proc/sys/net/ipv4/ip_local_port_range
```
If `ip_local_port_range` is narrow (e.g., default 32768 60999) and they have heavy NAT, they might exhaust.

ashok: ICMP unreachable on path often points to PMTU or inspection device dropping fragments. But the immediate RSTs after SYN/ACK smell like a stateful ACL/NAT mismatch — e.g., a NACL deny on the return (source/destination reversed) or firewall that sees SNATed ports it doesn't expect. Can you paste NACL and SG entries?

customer-bob: Pasting redacted NACL rules (subnet 10.20.0.0/24):
```
100: ALLOW 0.0.0.0/0 443 TCP (outbound)
110: DENY 0.0.0.0/0 1024-65535 TCP (outbound)
120: ALLOW 0.0.0.0/0 ALL ICMP (outbound)
```
And inbound rules mirror similarly. We had assumed SG statefulness would handle this but the NACL has an explicit deny for 1024-65535 outbound and it has higher precedence than the 443 allow.

maria: Bingo — that NACL deny will drop the ephemeral return traffic for SNATed sessions. Remember NACLs are stateless: you must allow both sides. If client uses SNAT to a high source port, the NAT's return traffic needs the outbound NACL entry to permit the ephemeral port range. The `DENY 1024-65535` will match and drop.

eng-infra-joe: Quick remediation options:
- Add explicit ALLOW outbound 1024-65535 TCP for the subnet (priority < 110), or
- Narrow the deny to only the CIDR you need and avoid blocking ephemeral ranges, or
- Put a managed NAT gateway with proper SNAT port range scaling so less chance of port exhaustion and then allow those ephemeral ports.

ashok: Also check their firewall appliance — some devices terminate TLS or perform deep inspection and will RST sessions if TLS parameters don't match policies (ALPN mismatch, SNI rewrite). But given NACL deny above I think that's the root cause here.
