carlos: Quick RFC follow-up on the "transparent offload" ABI + the 'pagefold' heuristic. I sketched two options yesterday; want to capture tradeoffs before the next design sync.

anna: +1 to capturing pros/cons. can you paste the minimal API shapes?

carlos: Sure — super short. Option A (explicit):
```c
// allocate with offload capability
void* alloc(size_t bytes, alloc_flags_t flags /* OFFLOADABLE */);
// request explicit migration
int offload_to_host(void* ptr);
int restore_to_gpu(void* ptr);
```
Option B (implicit/pagefold): kernel marks pages as foldable via hint, runtime migrates when pressure/latency heuristics trigger. No explicit migrate call.

ben: Main runtime concerns: explicit gives clear ownership semantics and predictable latency for hot paths. implicit reduces API surface but can cause surprise stalls on synchronous inference paths.

maya: Also think about multi-tenant fairness. implicit migration + background async could be noisy — tenant A's fold hints might cause eviction of tenant B pages unless we have strong quotas.

carlos: Right. My notes on fragmentation: explicit offload lets us batch evictions by slab/cohort which reduces fragmentation amplification. pagefold needs a compaction pass to avoid leaving tiny resident fragments.

anna: What about KV cache reuse? If we offload entire KV slabs explicitly we can keep contiguous ranges on host and memcpy back in big chunks. With pagefold we might reconstitute tiny slices, hurting memcpy throughput.

ben: Has anyone measured the memcpy/PCIe perf cliff for small pages? I ran a micro yesterday — copying 256B pages is ~10x slower per-byte vs 4k/64k chunks. So fragmentation = cost.

maya: Agreed. For long-lived but cold tensors (embeddings that are rarely queried) implicit pagefold is nice. For short-lived activations we want explicit lifecycle control. Maybe hybrid?

carlos: Hybrid = explicit controls for allocator-owned slabs + pagefold hints for guest allocations. Implementation detail: expose an allocator flag OFFLOAD_MODE = {EXPLICIT, HINTED}. Default EXPLICIT for model weights / kvcache. HINTED for "user" allocations.

anna: That seems reasonable. What about paging/backpressure semantics? If host memory gets saturated, should we reject offload calls or fallback to compression/recompute? We need policy.

ben: Policy options: reject (OOME), throttle (backpressure to requester), degrade (quantize/compress), recompute. Recompute is expensive but avoids blocking. Throttle + queued async restore seems practical.

carlos: Good catch. Can we add telemetry hooks: per-tenant offload count, avg restore latency, avg fragment size? Those will guide thresholds.

maya: Yes — also expose a fast path: restore_to_gpu(ptr, /*sync=false*/). If sync=false we enqueue restore and return immediately with handle; user can poll. This reduces tail latency for request threads.

anna: Edge cases: what if pointer moves (compact) while there's an in-flight restore handle? We'll need stable identifiers (offload-token) vs raw ptrs. raw ptr -> token mapping in the allocator.

carlos: Exactly. Proposal: modify API:
```c
offload_token_t offload(void* ptr);
int poll_restore(offload_token_t t, void** out_ptr);
int restore_sync(offload_token_t t, void** out_ptr);
```
That decouples address space from lifecycle. Also helps multithreaded callers.

ben: Sounds good. One more: telemetry for fragmentation should include "coalesced memcpy efficiency" metric: bytes_moved / memcpy_calls and percentile.
