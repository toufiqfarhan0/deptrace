kai: idea: two-layer model. long-lived API key stays as a minting credential for the broker, not for traffic. runtime-only tokens are short-lived (minutes) and carry precise claims. equivalently:

```
# broker mints ephemeral actor token
POST /v1/broker/mint
Authorization: Bearer api-key-legacy-xxxxx
{ "actor": "svc:ingest", "project": "proj-42", "scopes": ["ingest.write"] }

# client calls runtime with ephemeral token + actor header
curl -H "Authorization: Bearer svc.ephemeral.eyJ..." \n     -H "X-Actor: svc:ingest:proj-42" \n     https://api.redwood.com/v1/ingest/events
```

kai: runtime verifies ephemeral JWT, enforces per-route allowlist configured in policy store. legacy API keys get a migration path: broker issues a mapped ephemeral token for them during canary.

mike: two concerns: 1) audit & identity — we must preserve orig caller for billing/audit. 2) performance — per-request JWT validation + policy lookup at edge could add latency.

mike: proposal to address 1) add X-Actor-Chain header that encodes origin -> broker -> leaf actor as a compressed claim (signed). keeps immutable trail in logs. address 2) keep a small in-memory policy cache at edge with tiny TTL + background refresh and local signature verification for tokens.

rachel: X-Actor-Chain sounds good. question on rotation/keys: ephemeral tokens signed by broker; should broker use HSM-backed keys and publish JWKS to edge? we need key rollover plan.

kai: yes: broker uses KMS/HSM-protected signing keys, publishes JWKS. edges fetch jwks and cache. token lifetimes short (<=5m) so jwk rotation windows small. we should also support proof-of-possession for high-sensitivity routes later.
