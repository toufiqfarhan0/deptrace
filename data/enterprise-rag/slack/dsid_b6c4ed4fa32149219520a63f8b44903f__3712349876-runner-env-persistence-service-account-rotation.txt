ryan: That points to the runner process holding the old JSON in memory (env var or credential helper). Self-hosted runners keep job workers running until restarted; if a job spawns a long-living helper (e.g., vault-agent or gcloud auth daemon) it can cache ADC.
sam: Quick checklist: 1) confirm repo secret updated (looks like yes), 2) check runner host for lingering processes like `gcloud auth application-default login` or a mounted file with old creds, 3) check Vault agent caches if you use sync-to-disk.
maria: We use a small vault-agent sidecar that writes /etc/creds/service.json and a process `creds-daemon` watches and sets env var. It looks like the daemon didn't reload after file overwrite; it keeps the old token in memory.
jen: Workaround: restart the actions runner service on that host and any credential helper processes. Command we ran: 

```
sudo systemctl restart actions.runner.myrepo.service
sudo pkill -f creds-daemon || true
```

maria: Restart fixed the stuck jobs. But we had a handful of CI jobs fail and retried, causing delays to deploy. We want to avoid future blast radius.
ryan: Longer term: avoid storing long-lived JSON keys in repo secrets. Consider workload identity federation or short-lived tokens from Vault with TTL < 1h. Also ensure your credential refresh path updates running processes (SIGHUP or agent API).
sam: Also audit roles — the rotated key had broad Editor rights. Principle of least privilege: create a narrowly-scoped role for the runner (only iam.serviceAccounts.actAs and the exact API permissions needed). That reduces impact if rotation/compromise happens.
