sam: Heads-up — our minimal Next Edge starter (sample app) shows an infinite spinner when a token refresh returns 401. Repro steps below, small repro repo attached in thread.

sam: Repro steps:
1) sign in via the starter (edge-ssr)
2) let access token expire (short local TTL)
3) perform a streaming request to /api/generate
4) UI spins, network shows repeating 401s and no retry recovery

sam: Logs:
```
server: POST /api/generate 401 "Unauthorized" (retries: 5)
client: GET /api/auth/refresh 401
```

sam: Using sdk-js v0.7.2 and the starter's built-in fetch wrapper. Looks like the SDK's automatic retry hits the auth refresh endpoint and re-triggers itself -> loop.

arun: Oof. Can you paste the fetch wrapper? curious if it's catching 401 and re-calling the same path.

sam: Sure:
```
// simplified
async function safeFetch(input, opts) {
  const res = await fetch(input, opts);
  if (res.status === 401) {
    await refreshToken(); // expected to fix
    return fetch(input, opts); // here it retries
  }
  return res;
}
```

alex: The bug is in the SDK interceptor. It retries any 401 globally, including /api/auth/refresh. So refreshToken() itself gets retried and returns 401 -> loop.

mia: Quick workaround: short-term, make refresh endpoint use a header the SDK ignores, or bypass the SDK retry for paths matching `/api/auth/refresh`.

mia: Example patch in the starter (client-side):
```
if (url.endsWith('/api/auth/refresh')) {
  return fetch(url, opts); // no SDK retry wrapper
}
```

alex: I've got a small SDK patch that checks "isRefreshRequest" before applying the global retry. Will open a PR. Also adding a guard to stop retrying after the refresh attempt fails once.
