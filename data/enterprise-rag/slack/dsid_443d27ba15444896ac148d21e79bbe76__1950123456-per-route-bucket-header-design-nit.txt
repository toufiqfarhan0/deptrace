Maria Chen: Quick question — for per-route rate limits, when we return 429 should we include a stable bucket id header? e.g. `X-RateLimit-Bucket` + `X-RateLimit-Limit`/`-Remaining` + `Retry-After`? Clients want to group by bucket for dashboards.

Samir Patel: +1 on the headers but worried about leaking internal routing info. Could we hash the bucket id? e.g. `bucket: sha256(route+window+quant)` so it's stable but opaque.

Devon Nguyen: Hashing SGTM. Also suggest returning limit/remaining on every response (200 and 429) so clients don't have to handle 2 code paths.

Shreyas Rao: My concern: adding headers on every 200 might be a breaking size/regression for a few lightweight clients, but header additions are usually fine. If we add versioning on header names we can iterate: `X-RW-RateLimit-Bucket-v1`.

Maria Chen: Good point about versioned names. Backcompat question: do we also put `Retry-After` in seconds only, or both seconds + HTTP-date? many SDKs parse seconds.

Samir Patel: Keep seconds in `Retry-After` (integer) and optionally `Retry-After-Date` (HTTP-date) if we want. But don't change body shape. If we need extra advice include JSON body `{\"retry_after\": 12}` on 429 for clients not reading headers.

Devon Nguyen: Can we publish a small compatibility note in the changelog: "new headers (v1): X-RW-RateLimit-Bucket-v1, X-RW-RateLimit-Limit-v1, X-RW-RateLimit-Remaining-v1, Retry-After" + example curl.
