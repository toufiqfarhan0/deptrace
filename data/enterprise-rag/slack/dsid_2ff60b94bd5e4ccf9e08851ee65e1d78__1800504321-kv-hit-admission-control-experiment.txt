mike: hmm that explains it. mixing cheap hot requests with expensive cold ones reduces effective batch token budget for the cold ones since batcher packs by token count not compute cost. result: cold requests wait longer and sometimes trigger fallback kernels?

kavya: exactly. also kernel selection heuristic prefers the kernel optimized for avg seq len across the batch; if many hot requests are short, kernel chosen may be the small-seq fused kernel, which then degrades perf for the cold long sequences (they miss vectorized path).

elaine: observed kernel switch in logs: "selected_kernel=attn_fused_small_seq (seq<=512)" for batches containing mix, whereas pure-cold batches would pick attn_vec_opt (better for long sequences). That flip costs ~6-9% for cold items.

hiro: proposal: make admission control cost-aware. instead of token_count budget, use estimated_compute_units = sum(request.tokens * cost_per_token_estimate(hit_or_miss)). Cost_per_token_estimate can be learned or static (e.g., miss=1.0, hit=0.25). Then constrain batch to e.g., <= 1000 compute units.

mike: +1. We should also add "kernel affinity" scoring: prefer batches where variance of estimated per-request cost is low, so avoid mixing extremes. Simple heuristic: if stddev(cost)/mean(cost) > 0.6, split the batch.

kavya: add queue aging to avoid long tails for small cheap requests — if a cheap request waits > X ms, flush early even if compute budget not full. prevents tiny requests from starving.

elaine: sketched change in config form:

batching:
