Alex: error is just JSON decoding complaining 'Unexpected EOF' — looks like we try to decode before complete object landed.

Mia: yup — seen this pattern. two quick paths: treat stream as NDJSON (newline-delimited) or use an incremental/stateful assembler that waits for balanced braces before feeding to JSONDecoder.

Mia: naive brace-counter pseudocode:
```
buffer += chunk
for byte in chunk:
  if byte == '{' -> depth++
  if byte == '}' -> depth--
  if depth == 0 -> emit object up to this index
```
note: need to handle strings/escaped braces inside strings (so skip when in-string).

Sam: also saw this in Go client last quarter. We switched to streaming token decoder (encoding/json.Decoder) which handles partial streams better: call Decoder.Token()/Decode into map until EOF for each object. That avoids manual brace counting.

Sam: another angle is backpressure: the client was queuing too many in-flight objects and the buffer grew until parse exploded. Check StreamOptions.maxBufferedBytes (SDK) or reduce read window on the socket.

Olivia: +1. In our Android tests we hit the same burst case. I added a small read-suspend when buffered bytes > 64KB and it stopped the OOM/partial parse noise. config we used: StreamOptions(maxBufferedBytes: 65536, maxInFlight: 8)

Olivia: for Swift specifically, I'd avoid trying to decode raw Data into a model until you confirm complete object boundary. I have a tiny utility (will paste in PR) that tracks in-string state, increments depth on '{', decrements on '}', and only slices once depth==0 and not inside a string. cheap and reliable.
