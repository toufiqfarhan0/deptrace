anya: quick thought — i'd like to extract billing/metering out of the runtime hot path into an async sidecar. main goals: cut tail latency variability, simplify runtime surface area, and make billing easier to iterate on without touching hotpath code.

sam: big +1 on reducing hotpath surface. two quick concerns: accuracy (no double-charge) and backpressure when sidecar is down.

jess: agree with sam. Also: we currently have a few places that depend on immediate usage checks (eg block on exceeded quota). how would that work?

mike: we probably keep a tiny sync credit check (local cache) for blocking decisions. everything else (meter emits, usage logs) can be batched async. local cache gets replenished from sidecar. if cache miss -> quick sync to billing service as fallback.

anya: exactly. proposed sketch:
- sidecar runs colocated with runtime process, exposes a small UDP/HTTP endpoint for non-blocking meter emits.
- sidecar batches and writes to billing ingestion with at-least-once semantics, dedupe via event ids.
- runtime keeps per-tenant local credit counters with TTL (e.g. 30s) used for allow/deny.
- on miss, runtime does synchronous credit check (cheap path) or downgrade to conservative deny depending on tier.

sam: dedupe/at-least-once is doable but we need idempotency keys. what about retries across restarts? needs durable buffer or persistent offset.

anya: sidecar will keep an on-disk WAL for outstanding batches and replay on restart. small bounded disk usage. also expose /health that indicates if it has pending writes beyond X minutes (so gateway can apply safeties).

jess: migration plan? can't flip everyone at once.

anya: canary by tenant cohorts + shadow mode: run sidecar in shadow (still emit from runtime) for a while, compare counts. then enable sidecar for non-blocking emits only for a cohort, later cut the runtime emit path.
