kevin: That sounds like the auth refresh + reconnect race we hit in the node sdk a while back. If the refresh flow aborts the stream and the browser reconnects with a new token, interleaved chunk fragments can be mis-ordered and the parser drops the tail. Are you rotating tokens?

[auth] refresh done, new token
[stream] recv chunk: \"data: {\"delta\":\" world\"}\\n\"\n[stream] parser emit: \"hello world\" ??? (stops after this)
```

sam: Can you paste the SSE raw frames? Important to see if there are empty lines or half-chunks like \"\\n\\n\" split across reconnects. Browsers do weird buffering behavior on abort.

marta: Raw frames show a split where the last-event-id header is present on reconnect, but the resume token in the payload duplicates a small partial JSON fragment. Example: ```
data: {\"delta\":\" par\"\\n\\ndata: {\"delta\":\"tial\"}\\n\\n```

kevin: Yep — parser code assumes chunk boundaries align with logical SSE events. When abort+reconnect interleaves fragments, we merge wrong and end up with truncated JSON => parser throws silently and stops. We need to make the client more tolerant: buffer partial 'data:' lines across reconnects and retry parse on later fragments.

sam: This also smells like SDK parity: our browser and node SDKs handle this differently. Node had a fix to coalesce fragments using last-event-id and a resume token; browser didn't. I'll add a small patch to the browser SDK to keep a rolling buffer of incomplete `data:` payloads and attempt reassembly on reconnect.
