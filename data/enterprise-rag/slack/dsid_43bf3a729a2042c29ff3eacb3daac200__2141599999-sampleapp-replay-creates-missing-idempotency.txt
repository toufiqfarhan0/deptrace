Samir Gupta: FYI discovered a nasty UX bug in the Python quickstart: client retries after a timeout can create duplicate resources. Repro in sample app.
Jules Carver: Oof. Did the retry increment reuse any idempotency header?
Samir Gupta: No header at all in the quickstart. Logs: ```
2025-11-02T10:03:21Z INFO request req=abc status=408 timeout
2025-11-02T10:03:22Z INFO retrying req=abc attempt=2 backoff=0.7s
2025-11-02T10:03:23Z INFO request req=def status=201 resource=itm-900
```
Priya Nair: So second attempt sent a new request id (def). Without an idempotency key the server treats it as a fresh create.
Samir Gupta: Exact. Minimal repro in quickstart: ```py
from redwood import RedwoodClient
client = RedwoodClient(api_key=os.getenv("API_KEY"))
client.create_project({"name":"demo"}, timeout=2)
```
Jules Carver: That's bad for demos. Customers will hit that in flaky networks. Two things: sample should demonstrate passing an idempotency key, and SDK should consider safer defaults for high-level write helpers.
Priya Nair: Agreed. My suggested changes: 1) Update quickstart to show `idempotency_key=str(uuid.uuid4())` usage and a short explanation. 2) Introduce an optional `auto_idempotency` parameter on helpers (default False) that generates a stable key for the call if enabled, and logs `X-Idempotency-Auto: true`.
Samir Gupta: I'd prefer we keep behaviour opt-in to avoid surprises for customers who rely on request uniqueness. But the quickstart should definitely opt-in in its example.
Jules Carver: Also we need to clarify which error codes we recommend auto-retrying on.
