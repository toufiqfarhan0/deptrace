rachel: Are we still flushing on any detected stop-token? That seems aggressive for toolcalls since tool output can be short and we may prefer to keep collecting tokens for other requests.

samir: Current policy snippet:
```
if accumulated_tokens >= token_budget_target or stop_token_detected:
    flush_batch()
```
I think we need nuance: stop_token should only force flush if it finishes a non-tool response or if toolcall_ready flag is true. Otherwise put request into a "tool-hold" queue with a small hold_window. risk: memory growth if many held toolcalls.

maya: Experimented with hold_window=200ms (was 50ms). Results: stalls reduced ~18%, avg batch size up to 3.2, but structured outputs got truncated occasionally because downstream tool executor timed out. Proposed compromise: extend hold_window + prefetch KV entries for candidate tool spans so we can resume without kernel swap penalty.
