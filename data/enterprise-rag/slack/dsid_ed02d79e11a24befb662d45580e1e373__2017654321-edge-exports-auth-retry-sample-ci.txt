tiago (runtime): Edge bundlers (Pages/Workers) often roll your code into an ESM bundle and differ in default interop. If your CJS build attaches methods to `module.exports` and your ESM build uses `export default`, the bundler might be resolving the wrong shape. Also some bundlers drop non-enumerable properties.

mike (sdk): Confirming — we had a similar bug: our auth helper was `module.exports = createAuth` in CJS and `export default createAuth` in ESM, but the runtime packaging ended up with `{ default: [Function] }` vs the function itself depending on how the edge runtime resolves packages. Edge consumers doing `import Redwood from '@redwood/inference-js'` expect the default export to be the client factory.

olivia (docs): For DX, we should standardize a single surface — both builds should export named and default bindings. Eg in src/index.ts: `export default createClient; export const createClient = createClient;` so both `import Redwood from` and `import { createClient } from` work.

anna (devex): Is that enough for auth+retry? The error was specifically `client.auth.getToken is not a function` — that's an instance method missing after import.

mike (sdk): That points to the runtime object shape changing during bundling. Another common culprit: we attach helpers on prototype in CJS path, but tree-shaking or transpilation in ESM build turned them into non-enumerable descriptors. Practical fix: add a thin compatibility shim at package root that always imports the ESM runtime and re-exports a normalized object shape. e.g. `dist/esm/interop.mjs` and `dist/cjs/interop.cjs` that both `module.exports = require('./index').default` / `export { default } from './index.js'` but also do `module.exports.createClient = module.exports.default` so both shapes are consistent.

tiago (runtime): Also watch for bundler polyfills — `node:*` imports get rewritten and some edge runtimes remove functions if they rely on Node builtins. But your stack trace suggests missing method, not missing builtin.
