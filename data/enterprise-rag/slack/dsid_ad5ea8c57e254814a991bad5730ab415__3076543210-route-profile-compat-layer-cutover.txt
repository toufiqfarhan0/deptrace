Maya R: Quick heads-up — we're proposing a schema change to better support route-level metadata for the console. Goal: add a canonical_route_id and a small indexed route_tags array (jsonb) so dashboards can filter/aggregate without expensive joins or per-request enrichment.

Dan K: Sounds sensible. Current pain: console queries join 3 tables and hit the telemetry store for tag lookups — slow and brittle. What's the migration surface?

Maya R: Two main parts: 1) introduce a write-side projection (console_route_profile) that denormalizes route metadata used by dashboards; 2) keep old tables but dual-write during rollout. Read paths will be switched to the projection via a read-adapter layer behind a feature flag.

Suresh P: Dual-write means we need idempotent writes and a shadow-backfill for preexisting routes. Also need to think about per-tenant cutover because some tenants have millions of routes.

Leigh H: I prefer a read-adapter approach over changing the console queries everywhere. Adapter can translate legacy route_id queries to canonical_route_id and fallback when projection is missing. Easier rollback.

Eli T: Agree. Implementation plan: create projection table, populate with a streaming backfill job (Dataflow), enable dual-write in the API server behind config, then flip console to read from adapter that prefers projection. Canary on ~5% tenants first.

Samira: What about indexes? If we add route_tags as jsonb we risk heavy GIN index maintenance. Need estimates: row counts, update rate, and tag cardinality.

Maya R: Preliminary numbers: projection ~120M rows, update rate ~4k/s at peak, average tags per route 2. We should use partial indexes for common predicates and a composite btree on (tenant_id, canonical_route_id). GIN on route_tags for ad-hoc filters but with careful maintenance windows.

Dan K: Backfill strategy? Full table rewrite heavy. Can we do streaming incremental backfill per-tenant and mark tenant as "projection_ready" when done?

Suresh P: Streaming per-tenant backfill + flag in tenant_migration table is safest. On read, adapter checks tenant_migration.projection_ready and uses projection only if true; otherwise falls back to legacy join.

Leigh H: That makes metrics and rollback simple. Also want a schema-version header in the read RPC so clients can assert which shape they get.

Eli T: SQL snippet for projection DDL prototype:
```sql
CREATE TABLE console_route_profile (
  tenant_id bigint NOT NULL,
  canonical_route_id uuid NOT NULL,
  primary_route_id uuid,
  route_tags jsonb DEFAULT '[]',
  last_updated timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, canonical_route_id)
);
CREATE INDEX ON console_route_profile (tenant_id, last_updated);
CREATE INDEX ON console_route_profile USING GIN (route_tags jsonb_path_ops);
```
