sofia: quick follow-up thread on the "soft transfer" from yesterday's RFC. want to flush out lifecycle edges when migrating active streaming sessions between proxies without dropping client sockets.
raj: sketch the end-to-end sequence pls; main worries: ordering, duplicate tokens, and cache correctness.
sofia: proposed sequence: client -> proxy-A (active stream). operator triggers rebalance; proxy-A marks session TRANSFERRING and requests a transfer slot from control plane. control plane issues short-lived Transfer-Token (X-Transfer-Token) scoped to target proxy-B. proxy-A begins a warmup phase: it mirrors upstream responses to proxy-B (control-plane tunnel) so B can hydrate ephemeral state (KV window, recent prefixes). proxy-B opens an upstream connection and attempts resume using the token. during warmup A continues serving client; both A and B may see overlapping output for a short grace window. once B signals readiness, control plane flips routing atomically to B; proxy-A tombstones after tombstone_ttl.
mike: overlap is fine functionally but raises two ops questions: 1) ordering/duplication when chunks arrive from two proxies, 2) billing double-counting.
sofia: answers:
- ordering: include chunk_seq + session_uuid in each chunk's metadata; dedupe by (session_uuid, chunk_seq). proxies also attach chunk-checksum to detect corruption. maintain a tombstone map for recent seqs during tombstone_ttl to avoid replay.
- billing: small overlap will cause duplicate token accounting. plan: metric transfer_overlap_tokens and a reconciliation job that attributes overlapped tokens to a single host for billing. make grace_ms conservative (default 150ms) so cost delta negligible.
jen: KV cache correctness hurts most workloads. if B resumes with cold KV it can degrade latency and produce different outputs. what's the plan for cache priming?
sofia: option A: stream a compact KV-delta (recent inserts/updates) from A to B during warmup over encrypted control channel. option B: allow B to prefetch prefetched prefixes from S3/cache based on session history. caveats: deltas can be big for long sessions and are model-specific. we should limit kv-prime to a sliding window (e.g., last N inserts) and provide a toggle.
raj: client retries complicate things: mobile client may retransmit a chunk during a flip. how to ensure idempotency across proxies?
mike: extend retry tokens: include origin_proxy_id + session_uuid + chunk_seq + signature. new proxy validates token signature and rejects duplicates where chunk_seq <= max_acked_seq. also expose a reject_code so client gets clear guidance.
sofia: sample config I prototyped:
```

  seq_sig_algo: rsa-sha256
  allow_cross_tenancy: false
```
