maya: Quick follow-up from the canary yesterday — we saw in-flight streaming requests get dropped when the edge binary rolled. Not a total outage, but a bunch of clients saw truncated streams. I want to sketch a couple approaches and get opinions.

maya: Problem summary: when we cut traffic to a new edge version, the old proxy has N inflight streaming sessions with KV-prefix state in memory. New proxy starts with different memory layout and can't continue. We need a handoff so the new proxy can resume or the old proxy can proxy-through until sessions finish.

alex: Can you paste the minimal repro logs?

maya: Sure — here's the edge log around the cutover:```
[edge-1] 2025-06-12T15:02:11Z INFO accept stream session id=anchor:abc123 seq=240
[edge-1] 2025-06-12T15:02:18Z INFO draining sessions 240->0 canary=true
[edge-2] 2025-06-12T15:02:19Z WARN unknown resume token id=abc123
[client] 2025-06-12T15:02:20Z ERROR stream truncated by server
```

maya: Proposal A (stateful proxy handoff): when canary starts, new proxy sends an RPC to old proxy `/handoff/anchor/{id}` to request a small checkpoint (KV pointers + last-seq). Old returns checkpoint blob and keeps proxying until acks. New rehydrates and continues stream. Pros: low client-visible impact. Cons: requires direct proxy-proxy RPCs, auth, and lifetime/GC semantics.

maya: Proposal B (stateless resume token): include an opaque `x-rdwn-resume` header on the initial response that encodes enough to reconstruct state from a shared store (control-plane checkpoint s3) e.g.:
```
x-rdwn-resume: v1;anchor=abc123;seq=240;store=s3://rdwn-checks/anchor/abc123
```
New proxy fetches checkpoint from store and resumes. Pros: simpler proxies, no proxied RPCs. Cons: higher resume latency (S3 fetch), needs durable store and GC, possible stale checkpoints if not flushed.

sam: Leaning toward B for simplicity and SRE ownership of GC. But we need a small fast-path for low-latency resumption (cold fetch is rough for short-lived streams).

alex: What about hybrid: keep a short-lived in-memory lease on the old proxy for T seconds and write the same checkpoint to the store. New proxy asks old proxy first (fast in-cluster RPC), falls back to store if old doesn't have lease. That minimizes S3 hits while avoiding permanent proxy-proxy coupling.

dari: Security + cross-region concern: if we allow proxy-proxy RPCs we must authenticate properly and respect tenant isolation (no tenant X leaking checkpoint to Y via misroute). How do we scope the lease?

maya: Good call — leases should include tenant-id and a MAC. Example token: `resume_token = HMAC(k_tenant, anchor|seq|expiry)` and we check tenant match on handoff RPC.

maya: For hybrid we also need atomicity: new edge must not claim resume and then fail to finish, leaving old proxy stopped. I sketched a tiny two-phase handshake:
1) new -> old: `handoff?anchor=abc123&claim=true` (old replies `ok` and keeps streaming until commit)
2) new rehydrates state and responds `commit=true` to control plane
3) control plane instructs old to gracefully drain that session after commit OR to continue proxying on failure.

alex: That control-plane step is important. We don't want dangling half-claimed sessions. Could we use existing runtime-leases service (eng-infra) to represent these anchors?

infra-bot: runtime-lease-service currently supports 30s leases with renewal APIs. Suggest bumping to 2m for handoff use-case.

sam: Tradeoffs:
- Complexity: hybrid adds proxy-proxy + control-plane + store path.
- Latency: stateless store path adds ~50-150ms depending on region.
- Reliability: stateful handoff reduces client retries but increases surface area for bugs during deployments.

dari: Also consider retries: if client library retries the same request on a new connection, resume token must be idempotent for truncated responses. We should define whether resume semantics are strong (exact token sequence) or weak (best-effort continue from nearest checkpoint). I vote for strong sequence numbers to keep evals deterministic.

maya: Implementation notes:
- Minimal token format: `v1|tenant:abc|anchor:abc123|seq:240|lease:inst-42|sig:...`
- Small checkpoint payload should include KV-cache digest + last-output-chunk checksum so we can verify continuity.
- Metrics: `edge.handoff.attempt`, `edge.handoff.success`, `edge.handoff.fallback_to_store`, `edge.resume.latency_ms`

alex: One more operational thing — how does this interact with early cancel through trailer metadata? If client cancels after resume but before commit we shouldn't leak resources. Need clear cleanup paths.

maya: Agree. Plan: old proxy keeps a short GC window (e.g., 60s) after session unclaimed. Control-plane can trigger fast GC if commit observed.

sam: I'd add a fallback policy: if resume fails and we can't proxy-through, we return `HTTP 409 Stream-Interrupted; Retry-After: 1` so clients can backoff-and-retry without double-processing.

dari: Tests: canary harness should include orchestrated rollouts with synthetic long-lived streams and region failover. Also add a fuzzer for malformed resume tokens.

maya: Next steps I propose: write a small RFC doc with sequence diagrams and opt for hybrid approach (lease + store) for now. I'll open a PR with diagrams and a minimal token spec.
