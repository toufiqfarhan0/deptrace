maya: hey everyone — Maya here, joined infra this week. quick question: what's the right way to request access to secrets (DB creds, service account keys) and KMS key use for a sprint task? also what's our rotation policy? :wave:

sam_devops: welcome! short answer: use the Secrets Request portal and include service name, env, reason, and approver. link: https://internal.redwood.dev/secrets-requests. for dev creds we prefer dynamic creds when possible.

lee_security: +1. more details:
- prefer dynamic, short-lived creds (via our connector) for databases/services.
- if you need a static secret, request a vault kv at `secret/apps/<service>/<env>` and include TTL/rotation cadence. default rotation is 90 days for standard secrets, 30 days for high-privilege keys.
- KMS (AWS) access requires `kms:Decrypt` / `kms:Encrypt` for the specific key arn; we gate via IAM role and an approval.

ash_manager: @maya I can approve for you — include me as approver in the request and tag the repo or service. if it's for a demo/local only, ask for read-only dev creds.

maya: thanks! any template I should copy into the request?

sam_devops: use this minimal template in the portal description field (paste):

```
service: my-service
env: dev
owner: maya
reason: running integration tests that require DB access
requested_policies: ["redwood-dev-data-read"]
requested_ttl: 24h
approver: ash_manager
```

sam_devops: and if you need a KMS key, add `kms_key_arn: arn:aws:kms:us-west-2:123456789012:key/abcd-efgh` and note the business justification. infra-sre will provision a key alias or grant decrypt access.

lee_security: how to consume once approved:
- short term: `vault login -method=aws role=<role>` then `vault kv get -field=password secret/apps/my-service/dev`
- long term: use our secrets SDK which pulls rotated secrets into runtime via environment variables (see docs).

lee_security: rotation basics: when a secret rotates we create a new version in Vault and update the binding for the service. you should not hardcode secret versions. steps: create new secret version -> update deployment to reference it -> revoke old tokens if necessary. for DB creds we have a rotation lambda that updates both the DB user password and the vault entry.

maya: if I accidentally leak a key (local laptop) who do I contact?

ash_manager: ping @eng-security and open an incident ticket. rotate the secret immediately and mark the ticket as high priority.

lee_security: additional notes:
- avoid storing long-lived plaintext in repos. use `transit` to encrypt blobs if you must store them in a repo.
- for Private deployments (on-prem) we use HSM-backed keys; reach out to infra for access patterns.
