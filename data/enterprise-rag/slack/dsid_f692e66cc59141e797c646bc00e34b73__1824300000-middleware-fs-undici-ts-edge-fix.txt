Marco: yep, we accidentally left a top-level `import { readFileSync } from 'fs'` in token-cache to lazily load a local store. Next Edge bundler resolves imports statically so it chokes.
Ana: two easy fixes: (1) move fs use behind a node-only entry (redwood-js-sdk/node) or (2) switch token cache to dynamic import inside an isNode check.
Priya: example patch: ```js
// inside lib/token-cache.js
export async function getToken() {
  if (typeof process !== 'undefined' && process.versions?.node) {
    const { readFileSync } = await import('fs') // dynamic import for node-only
    return readFileSync('/tmp/token', 'utf8')
  }
  return null
}
```
Jules: that fixed the build error locally, thanks. But we still saw a runtime failure in Edge: the SDK's fetch wrapper tries to use AbortController in a Node style import and bundler included undici, causing function size to blow up.

Priya: propose exports mapping: ```json

    "default": "./dist/edge.mjs"
  }

``` This gives consumers an explicit edge entrypoint.

Jules: minor UX note: our starter app's README told people to `import { createClient } from 'redwood-js-sdk'` and call it in middleware top-level. That caused hidden issues because sync initialization can try to read env or fs. We should update the guide to recommend creating the client inside the handler for edge middleware.
Ana: Also document the small adapter snippet for Next middleware: ```ts
// middleware.ts
import { createClient } from 'redwood-js-sdk/edge'
export async function middleware(req: Request) {
  const client = createClient({ apiKey: process.env.RW_KEY })
  const headers = Object.fromEntries(req.headers)
  const out = await client.generate({ prompt: 'hi', headers })
  return new Response(JSON.stringify(out))
}
``` That avoids Headers mutation and uses edge entrypoint.
