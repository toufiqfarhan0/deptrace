alex: Quick follow-up on the gateway retry scoring idea from last week's RFC — I'm leaning toward pushing the score calc down into the edge so a proxy can decide to hedge/hedge-cancel locally. Thoughts? :thinking:

maria: I can see the perf win (no RTT to control plane) but main worry is consistency — different proxies might make divergent decisions on the same request class. How do we keep behavioral parity?

chris: If we move scoring to the edge we need a tiny, versioned contract: inputs (route, upstream-sla, recent-latency-p95, upstream-healthy) -> normalized score. The contract must be stable across deploys. Also need a way to force global overrides (eg a rollback).

alex: Agreed on the contract. Thinking of a stable proto + a hash of the scoring config that the control plane can stamp into route config. If hash mismatches, proxy falls back to a simple default policy.

sara: For telemetry: emit both "local_score" and "control_score" during a grace period so we can compare. Small overhead but critical to detect drift. Also add a sampling flag for high-traffic routes.

chris: +1 on telemetry. Also watch out for statefulness — if scoring uses short-term moving averages we must clarify where the history lives (per-proxy vs centralized). Per-proxy is simpler but unaligned.

alex: Proposal: scoring inputs limited to route static attributes + recent latency window kept in-proxy (rolling 10s). Keep weights static and controlled from CP. That gives per-proxy short-term view but same lamdas.

lucy: Two operational notes: 1) Canary rollouts of a new scoring config must default to control-plane-enforced mode for canary targets, otherwise a bad scoring change could silently increase cost. 2) Add a kill-switch route-level flag to stop local hedging immediately.

chris: Implementation sketch (pseudo):
```
// run on request completion and on midflight stalls
score = base_weight(route) * (1 + p95_penalty/100) - age_seconds * age_decay
if (score > hedge_threshold) start_hedge();
```
This is intentionally simple so we avoid costly computations on hot paths.
