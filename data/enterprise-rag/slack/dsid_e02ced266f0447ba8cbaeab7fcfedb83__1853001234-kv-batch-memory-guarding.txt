sudha: hmm 32k in single request is brutal. Is the batching logic counting KV tokens per request or just output tokens?

mike: current admittance uses token_count = request.context_tokens + expected_completion_tokens. KV reserve is computed post-hoc by summing per-request kv_estimate where kv_estimate ~= context_tokens * kv_ratio (empirically ~0.55 for our models). So it underestimates heavy long-contexts and we end up over-committing when k-v cache allocations happen concurrently.

kevin: another factor: kernel selection picks the large GEMM kernel when max_seq in batch > 8192 which has higher temporary memory usage. So even if kv_estimates are accurate, kernel tmp buffers push us over.

mike: exact — profiling shows two peaks: kv map growth and kernel temporary workspace. They happen sequentially during token generation as the KV cache is materialized then the kernel runs.

anna: proposed heuristics: (1) introduce a soft per-batch KV token budget that accounts for kernel tmp memory headroom, (2) prefer ordering admission by descending short-context-first (SJF-ish) to reduce tail long-seq waiting, (3) split extreme requests (>16k) into streaming/partial-kv mode.

sudha: +1 for soft budgets. Can you sketch the math? what's the headroom factor?

mike: sketch: available_kv_mem = KV_MEM_LIMIT - reserved_system - kernel_tmp_estimate. kernel_tmp_estimate = max_seq_in_batch * kernel_tmp_per_token. soft_kv_tokens_budget = floor(available_kv_mem / avg_kv_bytes_per_token). For admission we require sum(request.kv_tokens) <= soft_kv_tokens_budget * (1 - slack_pct). slack_pct default 0.12.
