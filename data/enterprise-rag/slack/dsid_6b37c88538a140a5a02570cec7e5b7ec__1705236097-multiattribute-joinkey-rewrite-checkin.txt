alex: heads up — i'm proposing a schema tweak for quota storage: materialize a deterministic multi-attribute join_key (org|route|region) instead of relying on route_id alone. goal is to make console queries for per-tenant + cross-route aggregates much cheaper and avoid high-cardinality fanouts. any blockers?

maria: sounds promising. which console queries will change? dashboards? alerting?

alex: main consumers: per-route quota dashboards, billing rollups, and the console p99 query that joins metrics->route meta. also any analytics exports that group by route. the idea: new column join_key text, populated on write as md5(org||'|'||route||'|'||region) to keep stable length.

raj: big concern is backfill cost. rough numbers? how many rows will need rewriting?

alex: estimate ~1.2B telemetry rows in hot partitions across last 90d. streaming the join_key on writes is cheap, but backfill will be heavy. proposed approach: dual-write writes to add join_key downstream, run shadow read adapter for console, then backfill incrementally with rate limits.

jen: agree with dual-write + read-adapter. we should also add a compatibility read path: console queries try join_key first, fall back to route_id if null. That gives gradual rollout and easier rollback.

alex: plan sketch: 
1) add nullable join_key column (no index) and add dual-write in ingest service (feature-flagged).
2) deploy console read-adapter to prefer join_key when present; keep route_id fallback.
3) run controlled canary traffic for 48h and compare counts.
4) start backfill in small parallel workers throttled by RPS; monitor CPU and DB io.
5) once backfill >= 95% for 90d window, create index on (join_key, time DESC) using CONCURRENTLY.
6) after index build and validation, flip queries to use join_key only and drop fallback.
