Maya K: Quick Q — we're getting inconsistent error shapes from the API and SDKs. Need a short consensus on: 1) canonical exception classes we map to (client vs server vs rate limit vs auth), 2) where/how to log/request IDs (streaming + nonstreaming), and 3) how to treat mid-stream transient failures for retry/idempotency. Can we hash this out quickly?

Chen (SDK): Short answers first: map 4xx -> ClientError, 401/403 -> AuthError, 429 -> RateLimitError (include retry_after), 5xx -> ServerError. Always surface a request_id on the top-level exception (from header `x-rw-request-id`). For streaming, surface a final error event and attach request_id there too. Will paste a tiny Python example below.

Maya K: perfect, thanks. Can we standardize the header name? `x-rw-request-id` ok?

Chen (SDK): yep `x-rw-request-id` is the canonical header from the platform. SDKs should: 1) include it on exceptions as `request_id`, 2) log it at WARN/ERROR for failures, 3) attach to debug traces. Example mapping (Python):

```py
# sdk/exceptions.py
class SDKError(Exception): pass
class ClientError(SDKError): pass
class AuthError(ClientError): pass
class RateLimitError(ClientError): def __init__(self, retry_after=None, request_id=None): ...
class ServerError(SDKError): pass

# http -> exception
if status == 401: raise AuthError("unauth", request_id=headers.get('x-rw-request-id'))
if status == 429: raise RateLimitError(retry_after=headers.get('retry-after'), request_id=headers.get('x-rw-request-id'))
```

Samir: For streaming specifically — if a stream yields partial tokens then errors, what's recommended? surface a structured error frame so callers can correlate. E.g. final JSON event: `\{\"type\": \"error\", \"error\": \"context_lost\", \"request_id\": \"...\"\}`. That keeps token stream separate from control frames.

Liz: question: if stream fails transiently mid-response, do we recommend automatic retry or bubble error? My thinking: default bubble error to app; provide helper `resume_from_token_index` in SDK for apps that want auto-retry. Also require idempotency header for server-side retries.

Chen (SDK): agree. Rules: - Non-idempotent generation (no idempotency key) -> do NOT auto-retry on mid-stream errors. - If caller provides `Idempotency-Key` (or SDK generates a client-side `idempotency_key` and surfaces it), the service can safely resume or produce the same output on retry. SDKs should expose a `resume_token` when available.
