maya: Quick design thread — thinking about per-customer token ceilings that automatically route to a lower-cost model variant when a customer is above their budget for the billing period. Want to discuss API surface, routing policy config, and console rollout UX.

maya: Goals: predictable spend for customers, preserve latency SLOs for paid tiers, measurable tokens-saved metric, and easy audit trail for why a request was downgraded.

alex: Do we mean hard ceilings (reject) or graceful downgrade (route to quantized/XS)?

maya: Graceful downgrade. Reject only if strictly over hard limit and customer opted into strict enforcement. Default behavior: route->compatible cheaper variant and add header x-redwood-fallback: variant=quantized-xs;reason=token-ceil

sam: +1. Suggest thresholds be relative (e.g., 80% of monthly allotment triggers conservative fallback) not absolute counts — varies a lot by customer.

teresa: We need a clear signal in telemetry: fallback_reason, origin_variant, target_variant, tokens_before, tokens_after. Without that it's impossible to compute tokens_saved or false positives.

liao: Console wants a single toggle per customer tier + per-region override. UX: preview panel showing expected latency/cost delta and historical fallback rate if enabled. Can we emit a sim-run API?

maya: Yup — plan: routing policy + simulator endpoint + rollout flags. Prototype routing policy (WIP):

```
route_policy:
  id: "budget_downgrade_v1"
  triggers:
    - type: monthly_usage_ratio
      threshold: 0.8     # 80% of plan tokens
      action: fallback
  fallback:
    preferred_variants:
      - quantized-xs
      - quantized-s
    max_latency_increase_ms: 50
    header: "x-redwood-fallback"
```

alex: A few questions: 1) how do we pick compatible variant for function-calling or tool-heavy prompts? 2) max_latency_increase_ms might be non-sensical for some variants where latency actually improves but quality drops.

sam: For compatibility we should validate model capability matrix at deploy-time. If original model uses function-calling, only select variants that support it. If none, fallback -> region-level conservative route (maybe original model in other region) or soft reject.

teresa: Telemetry bot: please add metrics to the per-customer dashboard: fallback_count, fallback_rate, tokens_saved (estimate), avg_response_quality_delta (from eval hooks).

telemetry-bot: Added draft panels: https://dash.redwood.internal/d/usage/budget-downgrade — includes fallback_count & tokens_saved (est). Need eval hooks to populate quality_delta.

liao: Rollout plan suggestion: 1) sim-only for 2 weeks (no actual routing, just report), 2) canary to 5% of low-tier customers in one region, 3) expand to 25% after quality delta < 1% on eval set, 4) global. Console will show a per-tenant control and a history timeline.

alex: Billing question: if we route to a cheaper variant, do we bill based on original token usage or actual tokens emitted by variant? This affects revenue / unit economics.

maya: Billing team wants actual tokens consumed by the variant. But we need to tag events so invoice pipeline can attribute original request/customer and variant used. Add invoice_tag: budget_downgrade to routed requests.

sam: Edge case: multi-model responses where we call a heavy reranker after generation. If generation switched to XS but reranker remains heavy, savings smaller. Need to include pipeline-level budgeting and allow "budget-neutral" stages to opt-out.

teresa: Also important: propagate fallback reason to logs and traces so support can see why a user saw degraded quality. Add a linkable trace id in the console message.
