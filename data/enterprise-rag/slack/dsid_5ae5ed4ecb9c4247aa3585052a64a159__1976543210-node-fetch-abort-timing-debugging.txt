alex_sdk: This rings a bell. There's a bug in the v1.4.0 retry middleware where if a caller passes an external AbortSignal, we reuse that signal across retry attempts instead of creating a fresh AbortController per attempt. If the signal is aborted mid-retry window, it can cause the runtime to cancel the inflight attempt but not prevent a concurrent retry from being scheduled, which in combination with how undici streams body data can lead to multiple identical outgoing attempts.

alex_sdk: Short checklist/workarounds:
- Add an Idempotency-Key header for POST workloads until we patch.
- Avoid sharing a single long-lived AbortController across multiple requests; create a new controller per request.
- Upgrade to patch release 1.4.2 (contains the retry->new AbortController per try fix).

matt_eng: To reproduce locally try: remove idempotency header, run the attached repro with SDK 1.4.0 and undici 5.x. You should see 2+ outbound requests for one logical call when the original attempt times out. Also try toggling network throttling to force timeouts.

lia_customer: I tried with a new controller per request and the duplicates stopped. Can someone confirm the fix details/PR?

alex_sdk: Confirmed — PR #4567 fixes this by cloning signal semantics and buffering small JSON bodies for safe retries. Patch released as v1.4.2. Install with: `npm i @redwood/inference@1.4.2`. The change also adds a guard: we won't retry POST by default unless an Idempotency-Key is present.
