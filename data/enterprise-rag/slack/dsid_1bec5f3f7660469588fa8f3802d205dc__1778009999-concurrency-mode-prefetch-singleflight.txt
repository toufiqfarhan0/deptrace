Zoe: quick heads-up — reproducible bug in JS SDK where paginator + auth refresh + client-side throttle interact badly. I put together a tiny repro and some traces.

Michael: thanks. short summary of what you saw?

Zoe: when token expires mid-iteration we get a thundering herd of refreshes + retries. the SDK default prefetch=2 + maxConcurrency=6 leads to many refresh requests being counted against the same concurrency pool, causing the paginator to stall and then burst when tokens come back.

Ana: does refresh path acquire the same semaphore as page requests?

Zoe: yes. rough call graph:
```
prefetch enqueuer -> acquire(sema) -> send(page request)
page request -> 401 -> spawn refresh() -> refresh calls httpClient.send() which also acquire(sema)
```
that means refreshes compete with pages for the same permits.

Priya: odd. in py we separate auth path and we use a singleflight dedupe so only one refresh per expired token. js doesn't dedupe and refreshes count toward the page sema.

Michael: can you paste the repro snippet?

Zoe: minimal loop:
```
const it = client.items.paginate({ pageSize: 40, prefetch: 2 });
for await (const page of it) { await process(page.items); }
```
Auth token TTL set to 5s in the mock. After ~2 pages token expires.

Ana: logs?

Zoe: excerpt:
```
[10:02:01] prefetch page=1 started
[10:02:01] prefetch page=2 started
[10:02:03] resp 401 page=1
[10:02:03] refresh start r1
[10:02:03] refresh start r2
[10:02:03] prefetch page=3 started
[10:02:03] semaphore held=6
[10:02:04] refresh resp r1
[10:02:04] page=3 send started -> burst
[10:02:04] server 429 x10
```

Priya: that matches a classic saturation pattern. Short-term mitigation: recommend customers set `prefetch:0` or `maxConcurrency` conservative, and call `await client.auth.ensureFresh()` before starting long paginated jobs.

Michael: long-term fixes?

Ana: propose these changes:
- add singleflight/dedupe for refreshes (JS) so multiple 401s for same token wait on the same refresh promise
- decouple refresh path from page concurrency: refresh should not consume page sema permits (or have its own small pool)
- make `prefetch` opt-in; default to `prefetch:1` to match py/sdk parity
- introduce `concurrencyMode` config with two modes: `strict` (enforce semaphore across initial+retry+refresh) and `safe` (refreshes excluded from page quota)
- add telemetry: `sdk.concurrent_refreshes`, `sdk.prefetch_queue_depth`, `sdk.inflight_exceedances`

Zoe: agree. also found a secondary issue: retry wrapper in JS sometimes leaks permits when retries are scheduled via setTimeout and the original promise never releases on the error path. So we need a test to ensure `acquire()`/`release()` are balanced even on early cancel/retry.

Priya: good catch. add a unit that simulates a 429+immediate retry and assert sema count returns to zero.
