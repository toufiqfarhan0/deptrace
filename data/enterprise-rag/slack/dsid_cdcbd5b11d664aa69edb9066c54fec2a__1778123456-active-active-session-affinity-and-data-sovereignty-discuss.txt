Anika: Thinking through active-active for EU+US customers. Major constraint: some customers require EU-only writes. How do we keep latency low without violating residency? Thoughts?
Sam: Short answer: allow region-scoped writes + global reads. Writes go to customer's home region; reads served nearest region with async replication. :question:
Kevin: That works but watch for consistency model. Async replication => read-after-write might be stale. Option: sticky session or read-your-writes via write-forwarding or session tokens. :thinking:
Anika: Agree. If we do sticky sessions, how do we route long-lived keys (e.g., KV cache) vs stateless requests?
Lina: We should differentiate by route. Stateful (cache/long context) -> keep in home region. Stateless gen -> nearest region. Also add TTL based cache invalidation and 'consistency' hint in API.
Sam: Implementation sketch:
```
x-region-policy:
  write_scope: 'home-region'
  read_fallback: 'nearest'
  consistency: 'session' # read-your-writes
```
Use token that encodes home-region.
Kevin: Two tradeoffs: increased cross-region egress for write-forwarding; and complexity of routing layer. SLA impact: tail latency could spike if home region degraded.
Anika: What about failover? If home region is down, do we fail open (allow writes in other regions) or fail closed (reject writes until restored)?
Lina: For regulated customers, must fail closed. For general customers, we can fail open with a 'residency-break' audit log + opt-in. :clipboard:
Kevin: We should expose an API flag: residency_strict=true/false per workspace. Default true for enterprise contracts. Docs + billing exception.
Sam: Operationally, routing table stored in control plane with TTL. Push to edge routers. Rollback plan: if we detect >X% residency-break writes, auto-disable fail-open. :gear:
