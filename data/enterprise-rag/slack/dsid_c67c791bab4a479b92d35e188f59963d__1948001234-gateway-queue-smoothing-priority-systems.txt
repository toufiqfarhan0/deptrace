jules: Quick thought — should we add a short 'smoothing' admission queue in front of the gateway to avoid big client spikes instantly tripping hedging/fallbacks?

anika: +1, been worried about thundering bursts from client SDK retries. Smoothing could absorb a few hundred reqs and feed the runtime at a steady rate.

sachin: How would this interact with priority classes? We can't delay high-priority low-latency requests behind long-running retries.

maya: We should keep priority at admission time. Idea: per-client/concurrency limit -> priority queue (p0,p1,p2) -> smoothing window token-bucket. Higher priority dequeues first, but smoothing limits outgoing tokens to target RPS.

jules: That makes sense. Concern: streaming sessions are long lived and we don't want them queued for minutes. We need an escape hatch for established streams.

anika: Agreed. Treat STREAM sessions as "inflight" and exempt from smoothing after handshake. Only initial CONNECT/OPEN goes through admission.

sachin: What about retries and idempotency semantics? If a request is queued for some time then retried, we could get dupes. We should attach a short-lived admission token id so gateway can detect duplicate inflight attempts and drop duplicates.

maya: Sketch of config:

```
admission:
  concurrency_per_client: 20
  priorities: [critical, normal, background]
  smoothing:
    window_ms: 250
    max_tokens_per_window: 1000
  stream_exempt: true
  dedupe_ttl_s: 30
```

jules: Nice. Also want to expose metrics: queue_length_by_priority, smoothing_tokens_used, dedupe_hits. ingress-bot: metric queue.latency_p50: 120ms, queue.latency_p95: 1.8s (prod: us-east-1) :chart_with_upwards_trend:

anika: We should also consider preemptive eviction: when queue backs up > threshold, drop background at tail first and surface a clear error code so SDKs can back off.

sachin: And we need clear SLO tradeoffs documented — smoothing helps latency variance but increases tail for queued non-critical ops. Make it opt-in per route with a default profile.
