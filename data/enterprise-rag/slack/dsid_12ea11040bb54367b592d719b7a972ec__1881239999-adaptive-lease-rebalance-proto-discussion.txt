follow-up discussion on adaptive lease + rebalance policy, tradeoffs, telemetry, rollout plan

anna: Quick follow-up on the adaptive lease & rebalance approach we discussed yesterday. I sketched an experiment and have a few open questions.

mike: Nice, thanks. Brief recap?

anna: idea = give tenants short leases (e.g., 30-120s) tied to a soft credit pool; when pool low, evict oldest idle leases and rebalance to higher-priority tenants. Want to avoid noisy preemption.

sarah: How are we defining 'idle'? idle = KV cache untouched for N steps, or literally no active requests for T seconds?

anna: leaning towards a hybrid: active_req_gap > 20s && kv_hit_rate < 5% -> mark idle. active_req_gap handles bursty traffic, kv_hit_rate avoids evicting useful cached state.

jay: eviction granularity question: evict whole model instance vs per-tenant slot? Prefer per-tenant slot eviction to preserve hot-start locality and reduce cascade impact.

lena: Warmup cost concerns: evicting an instance may pay warm-token cost and add cold-start latency. Need to quantify.

mike: tradeoff: shorter leases = more churn -> higher token cost, but potentially lower 95p latency under contention. We should simulate for 30/60/120/300s.

autoscaler-bot: simulation run 2026-11-04T14:02Z: results attached: 30s leases -> +12% token-cost, -18% p95 latency; 300s leases -> -6% token-cost, +9% p95 latency. (see INF-4123)

sarah: Could do hybrid: short leases for low-QoS/preemptible tenants, long leases for reserved/enterprise. Policy per-tier seems necessary.

anna: Agreed. config sketch:
```
pool_policy:
  default_lease: 60
  tiers:
    reserved: {lease: 300, preemptible: false}
    burst: {lease: 30, preemptible: true, cooldown: 120}
```

jay: Admission control changes needed: track per-tenant headroom credits and block new burst allocations if credits exhausted to prevent starvation of steady workloads.

lena: Also add graceful relocation: when evicting, send a 2s draining window to in-flight requests and schedule async prefetch of likely-needed KV keys if reallocation is anticipated.

mike: How do we detect when reallocation is "likely"? based on recent request rate + time-of-day patterns? could be ML model but start simple heuristics.

anna: For rollout safety, propose canary 5% of pools -> monitor p95 latency and error-rate, auto-disable policy on +15% p95 or +0.5% error increase. Roll forward after 24h stable.
