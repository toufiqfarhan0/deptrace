jia: Proposed short-term fix: change audit-exporter so that: (a) enrichment (KMS decrypt + alias lookup) runs before pagination/export chunking, (b) if decrypt fails for any row for the caller, return 403 with message "export requires kms:decrypt-on-behalf" (don't emit partial CSV), and (c) console UI greys out CSV export option and shows a descriptive tooltip if user lacks decrypt scope.

alex: Also: add telemetry counter export_validation.failures.kms and a tenant-level alert if >5% of export rows fail decrypt. And add a clear error code for operators to triage.

nora: One nuance — pagination currently uses cursor-based slicing server-side. Right now we slice then enrich, which means skipped/blank rows change offsets and can result in row duplication or missing rows across paginated pages. We need to perform enrichment before pagination slicing or make cursor reflect post-enrichment ordering.

sam: That could increase memory pressure if we enrich the entire result set first. Any streaming approach?

jia: Yes — implement streaming enrichment with backpressure: read results from storage, enrich/decrypt per record in a bounded worker pool, emit rows to the paginator once enriched. That keeps peak memory bounded while ensuring pagination reflects enriched output. We'll need to wire the KMS client with pooled concurrency and timeouts.
