aj: That pattern rings a bell — many HTTP libs cache the SSLContext on the connector. If the file at /etc/our-ca.pem changes on disk, the running SSLContext won't pick it up. Workarounds: 1) recreate the AsyncClient after rotation; 2) disable connection pooling/keepalive so each request re-evaluates the trust store.
kevin: Confirmed on infra side — our dedicated edge does hot-rotate certs but client-side process needs to reload trustroots. We saw identical after rolling internal services. Quick workaround: signal processes to reload the client or restart the worker. Long term: SDK should support a reloadable ssl_context or accept a callback to re-init connectors.
olga: Security note — if you auto-reload a CA bundle from disk, ensure file permissions and update process is atomic (write to tmp + rename) to avoid partial reads. Also verify there are no stale KMS keys referencing old certs.
aj: For a quick code-level workaround, you can set the client to not reuse connections: pass `pool_limits=0` (httpx) or new connector with `keepalive_timeout=0` (aiohttp). Example (httpx):
```python
import httpx
from redwood import AsyncClient
client = AsyncClient(..., transport=httpx.AsyncHTTPTransport(retries=1, pool_limits=httpx.Limits(max_keepalive_connections=0)))
```
That forces new TLS handshakes each request so the new CA takes effect. Performance hit though.
kevin: Also, you can set env var in our infra to point to a single-file CA bundle: `export REDWOOD_CUSTOM_CA_BUNDLE=/etc/our-ca.pem` and have your deploy pipeline touch a sentinel file that app watches to recreate the client. We'll add a note in the Dedicated setup docs.
