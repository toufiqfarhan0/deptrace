harry: FYI noticed a nasty dup-index problem in the new Next ISR starter. On high traffic the server ISR regeneration plus edge embed calls lead to multiple index persists for the same content  causing repeated expensive rebuilds. repo: https://git.company/oss/next-isr-llama-starter

harry: mostly when ISR background revalidate runs at the same time as client nav that triggers an embed; we saw two separate processes both decide to build+persist because persist is not idempotent. logs show concurrent persists and different trace ids.

zoe: looks like a TOCTOU race. any auth retries mixed in? sometimes auth backoff can cause the first persist to fail and a retry to rebuild.
harry: yes we also saw intermittent auth refresh (401->200) during spikes. combined with naive retry, each process will re-run build-and-persist, not realizing another succeeded. snippet of the problematic persist call in starter:
```js
// naive persist
const idx = await LlamaIndex.buildFromDocs('docs', docs)
await idx.persist() // no idempotency => multiple writes
```
claire: mitigation: make persist idempotent or use an atomic compare-and-swap in KV. e.g. write a version key first, use KV's conditional put, or include checksum and upsert-if-missing. SDK should help here.
ethan: proposing starter change: have the build path attempt to create a "lock" key with TTL, run build only if lock acquired, otherwise wait & load. plus use a persist version header. example (starter sketch):
```js
// pseudo-idempotent persist
const version = await kv.get('docs/faq/version')
if (!version) {
  const gotLock = await kv.put('docs/faq/lock', process.pid, { nx: true, ttl: 30 })
  if (gotLock) {
    const idx = await LlamaIndex.buildFromDocs('docs', docs)
    await idx.persist({ meta: { checksum: sha256(idx.snapshot) } })
    await kv.put('docs/faq/version', idx.meta.checksum)
    await kv.del('docs/faq/lock')
  } else {
    // wait for version to appear and load
    await sleep(200)
  }
}
```
