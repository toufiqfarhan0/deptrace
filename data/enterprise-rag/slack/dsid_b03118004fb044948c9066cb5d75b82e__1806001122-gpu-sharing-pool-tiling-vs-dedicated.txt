tom: this is the classic packing problem — MIG partitions make many small accelerators, which is great for isolation but leads to many tiny free fragments. autoscaler can't easily consolidate because pods request different MIG profiles.

raj: can we make the autoscaler aware of MIG profiles? e.g., node groups per profile and set priorities?

sophie: we already have a couple nodepools labelled `gpu.mig=1g` and `gpu.mig=7g`. The problem is bursty batch jobs want larger slices and low-latency pods want tiny slices. Autoscaler keeps adding nodes of the wrong profile.

devon: two axes: (A) keep MIG pools but add a shared time-slice pool for best-effort batch; (B) keep fewer MIG partitions per node (coarser slices) to reduce fragmentation. Both have latency/cost tradeoffs.

maria: I'm leaning toward strategy A: dedicated low-latency MIG pools for realtime, and a separate time-sliced pool for throughput jobs. That lets us set different PDBs, QoS, and scaling rules.

tom: agree. For time-slicing we could use the new nvidia-smi time-slice driver + our runtime plugin. It reduces determinism though — jitter increases. Also requires node-level cgroup tuning (slice duration, preemption windows).
