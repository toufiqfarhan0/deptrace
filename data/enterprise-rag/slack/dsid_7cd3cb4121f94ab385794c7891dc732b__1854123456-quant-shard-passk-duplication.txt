Jonah K.: aha. That `np.random.seed(global_seed)` inside the loop is a classic. It forces the same RNG state for every example in the batch => identical candidate draws across examples. That'd reduce diversity per-example and could lower pass@k.

Akshay P.: but that would make samples identical across examples in the same batch, not across runs. The CI artifacts show repeated candidates within the same example's k samples too (e.g., sample1==sample2). Does this code create duplicates within the `samples` list? `np.random.choice` by default allows replacement.

Li Chen: right — two problems: (1) reseeding each example means the RNG sequence restarts and you'll get the same sequence of choices for every example in the batch; (2) `np.random.choice` is called with default `replace=True`, so duplicates inside the k samples are possible. Combined = bad.

Sophia L.: I'd expect duplicates to reduce pass@k because fewer unique candidates to cover references. That matches the drop. But why did this only appear after quantization?

Maya R.: good question. My guess: quantization changed per-inference latency and batching behavior; we moved more work into the C path and the Python-level timing changed so batches had different sizes/order, exposing the bug more frequently in CI. Additionally, our sharded eval runner has an ordering change that makes the bad code path hit more often for quantized models.

Jonah K.: can confirm: the optimized runtime switches to continuous batching and we changed the eval runner to use dynamic batch splitting for faster throughput. That changed how `batch` is constructed (sometimes single-example batches, sometimes large). The reseed bug only mattered when multiple examples were in the same batch (identical RNG state per example). Quant path increased multi-example batch frequency.

Akshay P.: quick patch: remove `np.random.seed` in the loop, and use a per-example RNG seeded from global + ex.id. And call `np.random.choice(..., replace=False)` when feasible. Example patch: 

```
for i, ex in enumerate(batch):
    rng = np.random.RandomState(global_seed + ex.id)  # deterministic per-ex
    probs = model.sample_probs(ex.context)
    samples_idx = rng.choice(len(probs), size=k, p=probs, replace=False)
    samples = [vocab[j] for j in samples_idx]
    record_samples(ex.id, samples)
```

Li Chen: that looks right. Need to be careful: `replace=False` fails if k > support(nonzero_probs). We should fallback to `replace=True` and dedup afterwards. Add a unit that simulates small-vocab edge cases.

Maya R.: also found another aggregator bug in metrics_agg.py — if shards have overlapping example ids due to a previous partitioning bug, the aggregator picks the first occurrence instead of merging candidate sets. I'll paste the aggregator line: `df = df.drop_duplicates(subset=['example_id'])` (no sort key).

Jonah K.: so two compounding issues: sampler reseed + aggregator drop_duplicates without deterministic sort => non-deterministic pick of shard. That explains some CI flakiness.
