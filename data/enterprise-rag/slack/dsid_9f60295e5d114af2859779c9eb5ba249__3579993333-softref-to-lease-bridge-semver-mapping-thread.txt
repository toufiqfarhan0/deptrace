alex: Quick follow-up from the rollout-metadata RFC: proposal to introduce a lightweight 'lease_bridge' layer to map existing soft refs/aliases to canonical leases/semver in the control plane. Rationale: many clients use alias semantics (latest, staging, my-tenant) and we need deterministic mapping during canaries without forcing clients to change.

maria: can you sketch what fields we'd add? trying to picture client vs server responsibilities.

alex: idea sketch: add optional fields on rollout manifests: `canonical_ref` (content-hash or semver tag), `lease_hint` (soft TTL preferred), and `compat_bands` (list of acceptable semver ranges). Server will resolve alias -> canonical_ref and emit a stable lease token. Clients optionally present `lease_token` for affinity. Backwards compatible: if none set we fall back to current behavior.

sam: +1 to backward compat. Concern: race where alias -> canonical flips mid-request. How do we guarantee idempotent fallback? Would need resolver version in responses.

alex: agree. include `resolver_epoch` in the mapping response and store it in telemetry. If client observes mismatch it can retry with `resolver_epoch` header. ops-bot: deploy-check: ensure header size stays small, prefer numeric epoch.

jin: curious about `compat_bands`—do we expect wildcard semver? example please.

alex: sample manifest snippet:
```json
{
  "alias": "staging",
  "canonical_ref": "model-v2.3.1",
  "lease_hint": "1800", // seconds
  "compat_bands": [">=2.0.0 <3.0.0", "~2.3"]
}
```
This expresses that staging maps to model-v2.3.1, clients that require compatibility can validate the returned canonical_ref against the compat_bands.

leo: small note: avoid freeform strings for bands in proto. Maybe we encode bands as enums + minor range pairs to make it verifiable in runtime without parsing semver text.

maria: also need migration path: many existing manifests set alias->alias chains. Do we flatten at write-time? ops-bot: ops-sanity: chain flattening at control-plane write is cheaper than resolving at runtime, but we must record provenance.

alex: plan: write-time normalization: flatten alias chains into a canonical_ref and record `provenance` tag (legacy_alias list). Add `legacy_alias` field for clients still reading old shapes.

sam: testing checklist? I can add unit tests for resolver epoch bumping and a small e2e for canary transition without 503s.

jin: infra question: lease tokens are sensitive—should they be opaque UUIDs or HMAC of canonical_ref+epoch? Ops prefers opaque to allow rotation.

leo: opaque UUID + server-side mapping is simplest. Add a TTL and revocation endpoint for rapid rollbacks.

maria: one more UX ask: console should show alias -> canonical drift alerts when canonical_ref changes more than X times in 24h.
