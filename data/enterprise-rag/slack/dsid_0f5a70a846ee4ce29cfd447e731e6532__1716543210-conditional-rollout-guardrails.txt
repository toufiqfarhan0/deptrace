Alejandra: heads-up — I'm going to propose a new guardrail for conditional rollouts in the console. Need buy-in on telemetry gating and UX before I file the RFC.
Samir: ok, outline the problem first. what's failing today?
Alejandra: two things: 1) people flip feature flags to 10% but forget to tie to quality metrics, so we surface regressions late. 2) console only supports percent-based rollouts, not predicate routing (eg route by customer tier or latency).
Riya: totally. Percent-only is too coarse for per-customer SLAs. We should support route predicates + percent. 
Ben: we also need safe defaults — a dry-run mode that records decisions without affecting live traffic. Helps validate routing expressions.
Alejandra: exactly. Proposed shape: a rollout config with: `condition` (a boolean expression), `percent`, `slo_checks` array, `telemetry_gate` config. Example: 
```yaml
conditional_rollouts:
  - name: low_latency_route
    condition: "request.region == 'eu' && customer.tier == 'gold'"
    percent: 20
    telemetry_gate:
      eval_window: 10m
      metrics:
        - name: p50_latency_ms
          threshold: 200
        - name: error_rate
          threshold: 0.01
    dry_run: true
```
Samir: love the example. A few questions: how do we evaluate the telemetry_gate? rolling windows? baseline comparison?
Riya: we should compare against a baseline version (current active config) and require no statistically significant regressions on any metric in `slo_checks` for X windows. Also allow custom aggregation (p50/p95/median).
Ben: and alerting — if gate fails, should auto-roll back percent to 0 or divert to fallback model? Both useful but need opt-in.
Alejandra: propose opt-in policy: `on_gate_fail: [notify, rollback_percent, route_to_fallback]` with default `[notify, rollback_percent]`.
