kevin: quick q about feature-flag inheritance — what's the canonical precedence across org / project / route / model? also how do canary audiences interplay across scopes?

lucy: short answer: most-specific wins. precedence = model > route > project > org. lower-level overrides replace higher-level defaults.

sam: to add — when a lower scope specifies a full config (enabled + audience + pct) it supplants the higher scope for requests that match that lower scope. higher scope only applies if no lower scope applies.

dana: here’s a tiny example to make it concrete:
```json
{
  "org": { "new_rerank": { "enabled": false, "max_canary_pct": 10 }},
  "project:search": { "new_rerank": { "enabled": true, "canary_pct": 5 }},
  "route:/search/vec": { "new_rerank": { "enabled": false }},
  "model:gpt-small": { "new_rerank": { "enabled": true, "canary_pct": 1 }}
}
```
Interpretation: requests hitting /search/vec see route override (disabled) even if project enables it. If route didn’t exist, model-level would apply for calls using gpt-small.

mohit: question — if route and model both define audiences (e.g., route targets beta-users, model targets 1% random), do we union/AND them or pick one?

ryan: we treat the most-specific matching scope as authoritative for that request. In practice that means: if the request is routed to a route that has a flag config, use the route config. If there is no route config but the model has one, use the model config. We do NOT merge audiences across scopes by default — overrides are replacements.

ryan: nuance: for multi-key requests (e.g., model-run invoked from many routes) the evaluation picks the scope closest to the request context. If you need combined targeting, explicitly define a route-level policy that references the model-level intent.

ryan: guardrails — enforcement we have/planned:
- org-level "max_canary_pct" is a ceiling for all lower scopes; lower scopes cannot exceed that number without an approval flow.
- auto-rollback triggers: error-rate + latency + output-quality regressions (configurable thresholds, default: error rate +15% or latency +25% over baseline)
- canary expansion requires audit log + release note when crossing 10% and explicit approval for >50%

lucy: extra Q — do these rules change between Hosted / Dedicated / Private deployments?

sam: behavior is consistent: scope precedence is product-level logic. For Private deployments the control plane still ships policy defaults but customers can opt to run local policy engine — semantics stay the same, but enforcement/approval flows may be local. Note: dedicated infra quotas/latency SLOs can block canary >X% programmatically.
