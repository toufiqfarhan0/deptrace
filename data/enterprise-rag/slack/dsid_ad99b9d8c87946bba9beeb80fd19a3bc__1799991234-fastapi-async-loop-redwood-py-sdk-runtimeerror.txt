jess_eng: yep that's the issue. uvicorn/fasapi runs an event loop. our sync wrapper uses asyncio.run() which raises if loop already running. We added the wrapper in 0.12.0 to make sync usage easier but missed the running-loop case. quick workaround for customer: use the async client inside a task and await, or run sync code in a thread. Example workaround:
```py
# workaround: run blocking sync call in threadpool
from concurrent.futures import ThreadPoolExecutor
import asyncio

executor = ThreadPoolExecutor(max_workers=1)

@app.on_event('startup')
async def start_job():
    loop = asyncio.get_running_loop()
    await loop.run_in_executor(executor, lambda: redwood.sync.Client(api_key=...).generate('hi'))
```

kyler_eng: adding to that — customers can also call the async API directly instead of using the sync veneer:
```py
async def start_job():
    async with redwood.AsyncClient(api_key=...) as c:
        await c.generate('hi')
```

jess_eng: for the long term we should change sync.Client to detect a running loop and avoid asyncio.run; fallback to submitting to loop if possible, or raise a clearer error pointing to the async client. Proposed patch in PR: if asyncio.get_running_loop() exists -> raise RuntimeError with guidance and link to docs. Alternatively detect if loop is running in a different thread and use asyncio.run_coroutine_threadsafe.
