maria: AWS KMS, us-west-2, using CMK alias/redwood/enc. rate looked like a burst from the rotation job. we triggered throttling and then our retry loop amplified it.

sre_lead: this is a near-miss for prod. good we caught in staging. main risks: creating new DEKs requires kms:GenerateDataKey, and decrypt for bootstrapping services. If KMS is slow we need a safe fallback to keep reads/writes for long-lived workloads.

security_eng: quick reminder — we cannot fall back to an unencrypted DEK or store plaintext on disk. any fallback must preserve audit trail and rotation semantics.

jon: currently flow is: service asks KMS -> GenerateDataKey -> store encrypted DEK alongside object. services cache plaintext DEK in memory for 30s TTL. rotate job generates new DEKs aggressively during rollout which caused large burst.

maria: proposed mitigations:
- enforce rate limit on rotation job (chunked, staggered).
- increase in-memory DEK cache TTL to 5m for production (with LRU + explicit revocation on rotation).
- add a circuit breaker: if KMS errors > 5/m, pause rotation and route to a slower fallback.

jon: agree. also add exponential backoff with full jitter for KMS calls. sample pseudo-config:
```
kms_backoff:
  base_ms: 50
  max_ms: 2000
  jitter: true
  max_retries: 6
```

security_eng: for fallback we can rely on previously-encrypted DEKs stored in DB. decrypt path: if KMS.Decrypt fails but we have a cached plaintext DEK, use it. if cached plaintext not present, we MUST NOT attempt to derive a new plaintext without calling KMS. so behavior:
1) try KMS.Decrypt (with backoff)
2) if fails and cached plaintext exists -> use cached plaintext and emit high-severity audit event
3) if fails and no cached plaintext -> fail request with 503 and clear message to client -> increment pager if threshold hit

sre_lead: +1. add audit fields: which key id, which service used cached DEK, and reason (KMS throttling). We need that in logs to satisfy compliance.
