Priya K.: quick note from staging: several prewarm jobs created nodes in an unexpected shard and admission later failed to consume the warmup credits. impact small but spiky, want design decision today
Dan S.: how small? numbers please
Priya K.: ~12 failures over 3 days, ~0.4% of prewarms. each failure meant tenant couldn't burst for ~30s until fallback path kicked in
Alex C.: ok. options on the table (brain dump):
 1) flatten: make warmup credits visible at the pool level instead of shard-level (fast reads, weaker isolation)
 2) transfer: keep credits per-shard but atomically transfer on prewarm finalize (safe, needs transfer protocol)
 3) borrow: let admission search sibling shards and claim a sibling credit with a short lease (best of both, race risk)
Matt P.: flatten removes a class of bugs but undermines per-tenant blast radius. enterprise customers will complain if credits cross AZs unintentionally
Sara N.: transfer is safe but introduces complexity: how to guarantee commit/rollback across operator restarts? do we need a two-phase commit?
Joan L.: two-phase commit at our scale is painful. instead consider idempotent transfer records: write transfer intent -> attach token to node -> finalize. a reconciliation job covers partials
Ryan G.: borrowing + lease seems attractive. design idea: admission calls `AcquireLease(pool, token_id, ttl=2s, siblings=true)` which returns lease_id if claimable. then admission commits with `ConsumeLease(lease_id)` async replication to ledger
Matt P.: where to store lease state? current ledger p99 is ~50ms so direct calls kill admission SLA
Sara N.: we can implement a local in-memory lease cache co-located with admission path. model: check cache first (sub-ms), if miss then fall back to remote call. maintain an async write-through for durability
Alex C.: cache opens risk of lost leases on host crash. propose: local cache + remote lease write with a short TTL. admission treats local lease as authoritative for TTL but remote commit must succeed eventually or trigger refund/cleanup
Priya K.: example flow (sketch):
```
# caller wants warmup credit
lease = AcquireLocalLease(token=tok123, ttl=2s)   # fast
if not lease: lease = RemoteAcquire(token=tok123)
if lease: start admission; async CommitRemote(lease)
else: reject
```

Dan S.: metrics we need while testing: `sibling_lease_fail_rate`, `double_spend_count`, `admission_tail_latency_ms`, `reconciliation_backlog`
Joan L.: also add `credits_resolved_shard` in audit logs so we can trace origin vs claimed shard
Ryan G.: scaling note: local cache memory usage grows with number of active admissions. cap by LRU and treat older entries as misses. eviction must trigger refund path for held leases
Matt P.: one more: concurrency. two admissions on different nodes could see cache miss and both call RemoteAcquire. remote must enforce atomicity. simplest: RemoteAcquire uses a CAS on the token record to set `leased_by=lease_id` if empty
Sara N.: CAS is ok but increases remote latency. that's why we rely on local cache for most cases. also implement a short optimistic backoff to reduce thundering herd
Alex C.: rollout plan suggestion:
- build prototype behind feature flag (sibling-lease + local cache)
- unit tests for race scenarios
- staging soak: enable on 5% prewarm traffic for 72h with synthetic contention
- canary: 10% live, monitor metrics Dan listed for 48h
- full rollout with per-tenant opt-out for enterprise accounts

Priya K.: acceptance criteria before broad rollout:
- `double_spend_count` == 0 (or tiny fraction < 1e-5)
- `admission_tail_latency_ms.p99` increase <= 10ms
- `reconciliation_backlog` stable and below threshold
