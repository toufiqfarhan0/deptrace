alex: Quick design review — preflight progress UI for the on‑prem setup. Screenshot: https://assets.redwood.dev/preflight/progress-v3.png. Focusing on copy + a11y for the network probes. Thoughts?
jordan: I like the compact pill but the labels feel vague when probes run in parallel. Users don't know which probe is active.
sam: Agree. For probes we should show 'step X of Y' when we know the list, otherwise fallback to 'Checking…' with an indeterminate spinner.
tess: A11y note: don't put aria-live on the entire progress bar. Screen readers announce every micro-update. Use a single role=status node with aria-live="polite" for the human-readable line.
jordan: Copy options: A) "Verifying network prerequisites…" B) "Checking network prerequisites…" Which is clearer?
alex: Leaning toward A (Verifying) — feels more authoritative for infra checks. But let's surface both in the user test.
sam: Implementation idea: expose data-step/data-total attrs and render the status line from them. Example snippet: <div role="status" aria-live="polite" aria-atomic="true">Verifying network prerequisites — step 2 of 6</div>
tess: Also avoid using aria-valuenow updates for each probe. That causes verbose reads. Keep the numeric progress on a single update string.
jordan: Microcopy for success state: instead of a terse "Success", use: "All prerequisites verified — you can continue" (short but actionable).
alex: Error flow: if a probe times out show inline CTA "Retry probe" and a secondary "Troubleshoot network" link. Keep toast messages minimal and not duplicative.
sam: I'll open a PR with the aria/status changes and both copy variants. Will add a small dev flag to force slow probe simulation for testing.
tess: I'll validate with VoiceOver and NVDA on staging once the PR is up. Also check that screen reader doesn't double‑announce when the step increments.
