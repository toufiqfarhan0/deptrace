Brian Murphy: API behavior notes:
- 429 responses will sometimes include `Retry-After` (seconds). If present, we should respect it.
- 408/409/425 are rare but we can treat as transient.
- 401/403/404 are never retry.
- Streaming responses are SSE over HTTP; when proxy drops you may see `ECONNRESET` / `UND_ERR_SOCKET` / `unexpected EOF`.

Ibrahim Khan: Proposed baseline (consistent w/ what we’ve done elsewhere):
- `connect_timeout`: 5s
- `request_timeout` (total): 60s for non-streaming
- retries: max 2 retries (3 attempts total)
- backoff: exponential w/ jitter starting 250ms, cap 4s
- retry only on: network errors (connect reset, DNS, timeouts), 429, 502/503/504
- respect `Retry-After` for 429 with upper bound (don’t sleep > 10s by default)

Dana Lo: 60s total might be too short for first token on some models if user sets huge context. But template should also cap max_tokens anyway.

Christine Wong: I’d prefer we’re strict on timeouts by default + document overrides. “Safe” = don’t hang processes, don’t DDOS ourselves on retries.

Monica Patel: For templates we also have ingestion/indexing steps (RAG) that might take longer than 60s, but those are local operations. For LLM calls, 60s seems ok.

Alex Martinez: The thing we should optimize for is: new user runs quickstart, gets a response, doesn’t get stuck. If someone needs longer, they can tune env vars.
