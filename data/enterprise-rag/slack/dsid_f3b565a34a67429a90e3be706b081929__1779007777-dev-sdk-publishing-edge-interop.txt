Alex Chen: thinking out loud — we need to pick a publishing strategy for the JS SDK that won't keep biting customers. goals: single install for Node + edge (Deno/Bun/Cloudflare), good typings, and predictable auth/retry behavior across runtimes. any strong opinions on dual-package vs single-package with conditional exports?
Kim Patel: +1 for single-package with conditional exports. fewer installs, easier to explain. but only if we can keep the CJS entrypoint stable for older Node.
Matt R.: conditional exports are great but the edge story is messy — Cloudflare & Deno require ESM and sometimes expect `module` field or a pure-ES build. Bun is weird too. We tried a `types` path remap last quarter and TS resolved to the CJS dts in some setups.
Samira Gomez: from DX/user reports: auth flow fails in edge runtimes when people import the top-level default and rely on `require()` shims. They see runtime error "require is not defined". We should provide clear examples for edge -- like `import { Redwood } from '@redwood/inference/edge'` or something.
Jordan (eng): idea: publish one package but build both ESM and CJS bundles and use conditional exports in package.json: top-level exports for `import` and `require`, plus separate `./edge` export that is ESM-only and smaller. That way sample apps for Cloudflare/Workers can import the explicit edge path. Example exports snippet: ```json
"exports": {
  ".": {
    "import": "./dist/index.mjs",
    "require": "./dist/index.cjs"
  },
  "./edge": {
    "import": "./dist/edge/index.mjs"
  }
}```
Kim Patel: that looks fine. two questions: 1) types — how do we point TS to the right d.ts for `./edge`? 2) runtime-detection code for retries/auth: make sure edge build doesn't bundle node-only libs.
Alex Chen: on types: add explicit `types` exports in the same conditional map. TS supports an "types" subkey in exports (modern TS). e.g.: ```json
"./edge": { "import": "./dist/edge/index.mjs", "types": "./dist/edge/index.d.ts" }```
