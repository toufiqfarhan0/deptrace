alex: Quick sync — we need a decision on the rerank response shape. Current chaos: sometimes we return raw logits, sometimes scaled scores, and console + billing expect 'score units'. We should pick something stable for routing/quotas and a compatibility shim for older clients.

maria: Agree. Raw logits are useful for downstream but not human-friendly. Console wants a consistent 0-100 or 0-1 band for dashboards.

jordan: Can we add a tiny envelope instead of replacing fields? e.g. `{score_type: \"normalized\", score: 0.83, raw: -1.24}`. That keeps raw around and gives normalized for UI + quotas.

samir: That seems fine but concern: high-cardinality `score_type` + `model_id` combos explode telemetry. We need to standardize a small enum: `raw_logit`, `prob`, `signed_confidence`.

evelyn: Also we need to define how normalization works. Is it softmax across candidates, min-max, or logistic mapping per-candidate? Different callers expect different semantics.

alex: Proposal: default to per-request softmax-normalized probability (prob), but include `raw_logit` for downstream users. For N=1 flows (single candidate scoring), `prob` = sigmoid(raw). Document this.

maria: For quotas we must avoid per-candidate multiply confusion. Billing expects a stable unit: `score_units = ceil(num_candidates * weight)`. Let's pick `weight=1` by default and allow per-tenant overrides.

jordan: UX: console should surface a toggle: show scores as `raw` / `prob` / `z-score`. Also show telemetry mapping so non-engineers don't misinterpret.

samir: Telemetry note: instrument `score_type` and `score_transform` as tags, but sample at 5% for high-volume tenants to control cardinality. Also hash-model-id into low-card buckets in dashboards.

evelyn: Backwards compatibility: older clients will still parse `score` as the previous value. We should add `score_v2` envelope and bump the API minor version. Add a `compat: { legacy_score: ... }` for a single deploy cycle.

jordan: Routing impact: when model capacity constrained, we may route to cheaper model variants. Need to keep `score` semantics invariant across variants. So normalization must be deterministic and model-agnostic for same candidate ordering.

samir: Deterministic normalization across models is impossible if models differ in output scale. Instead, console + routing should use `signed_confidence` that is calibrated per-model using stored mappings in Optimize. Or we stipulate `raw_logit` + per-model calibration metadata for routing decisions.

evelyn: I vote for shipping the envelope with `raw_logit` + `prob` (softmax per-request) and adding a `calibration_id` link to calibration metadata for the route. Routing/console can choose calibrated view if available.
