Morgan: Quick follow-up to the continuous-batcher RFC — proposing a clearer split between Scheduler and QueueManager to reduce coupling and make eviction/KV-pin lifecycle explicit.
Elaine: tl;dr?
Morgan: Scheduler: admission, placement, fast-path preempt decisions. QueueManager: canonical per-tenant headroom, long-lived eviction hysteresis, KV-cache pin lifecycle, durable queue state.
Raj: Who holds the canonical headroom counters? and how do we avoid races?
Morgan: QueueManager owns headroom counters. Scheduler queries and caches a short-lived lease token for fast admission. If admission would exceed a threshold of cached headroom, Scheduler must revalidate.
Tim: Risk: stale cache -> over-admit -> KV thrash during spikes.
Morgan: Agreed. Proposal:

```
lease = qm.read_headroom(tenant)
if req.tokens > lease.available * 0.6:
  lease = qm.refresh(tenant)
# admission proceeds only against validated lease
```

Raj: Keeps QM authoritative. What about eviction durability?
Morgan: QM decides eviction candidates and maintains hysteresis counters. Scheduler can request expedited eviction for SLOs, but QM applies policy and records durable state.
Elaine: If QM owns KV pins, we need an API to coordinate with runtime to actually drop entries.
Tim: Minimal control API: QM -> runtime: `evict_intent(tenant, keyset)` runtime -> `evict_ack(keyset, ts)`.
Morgan: Exactly. Async contract: QM issues intent, runtime attempts release, returns ack. Scheduler treats unacked intents as backpressure and avoids admitting dependent requests.
Raj: Telemetry? We need canonical metrics to debug headroom/inflight interactions.
Morgan: QM emits queue_depth, headroom_total, headroom_used, evictions/sec, kv_release_latency. Scheduler emits derived events: admission_from_cached_lease, rejected_on_stale_lease, expedite_eviction_requests.
