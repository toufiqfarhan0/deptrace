Anya: quick thread — we need a concise playbook for sampling thresholds + cost hedging for telemetry ingest. RFC left a handful of open tradeoffs and folks keep hitting spikes.
Sam: +1. can you list the gaps?
Anya: gaps: (1) who owns dynamic threshold tuning, (2) how to signal backpressure to SDKs, (3) safe fallbacks for late enrichment, (4) how to account cost attribution when we drop or compact events.
Leo: worth keeping the playbook operational-first. small decision matrix per service: expected qps, p50/p95 latency, burst profile, and business criticality -> map to sampling strategy.
Maria: curious about "cost hedging" — do you mean reserved budgets + automatic degradation policies?
Anya: yeah. both policy-level hedges (reserve budget, dedicated hot-path) and runtime hedges (priority buckets, shed low-priority telemetry).
Devon: question on priority buckets — how do we derive the priority? request-level metadata? model-serving vs background jobs have different cost tolerance.
Sam: priority should be driven by two things: tenant SLA tier + route tag. we can synthesize a numeric priority: priority = SLA_weight * 100 + route_weight. simpler to reason about than free-form labels.
Anya: example runtime rules we want in the playbook: 
1) If cluster_util > 85% -> start slow-path sampling on priority <= 200
2) If queue_latency > 250ms -> reject low-priority envelope writes with 429 and emit metric telemetry.shed.count
3) On memory pressure -> compact envelopes older than 2h into summary event

Leo: +1. need explicit safe fallback for late enrichment: we should write a lightweight skeleton event (minimal attrs + id) and schedule enrichment async, instead of blocking the ingest path.
Maria: this impacts cost attribution for those skeletons though — we need to tag them with origin_route and sampling_reason so billing can choose to attribute to the right tenant. propose fields: attribution_key, sampling_policy, origin_route.
Devon: agree. also add a deterministic sampling_id so we can reconstruct cohorts for rehydration if enrichment happens later.
Anya: good call. include small json example in the playbook: 
```
{"sampling_policy":"preemptive","sampling_id":"sha1(req_id|env)","attribution_key":"tenant:acct-123","origin_route":"model/generate","priority":150}
```
Sam: for dynamic thresholds, ops team should expose an admin API: `/v1/ingest/thresholds` with a simple schema: 
```
{"service":"trace-ingest","cpu_pct":70,"queue_ms":200,"priority_cutoffs":[100,200,500]}
```
Devon: we also need a low-friction SDK signal for backpressure: `ingest.backpressure({level: "low"|"med"|"high"})` so clients can decide to drop verbose spans pre-serialize.
Leo: agree — but we must avoid tight coupling. SDKs get only advisory signals and a recommended client-side policy. server authoritative decisions still happen on ingest.
Maria: telemetry for auditing: every shed event must emit an envelope with tags: {tenant, service, shed_reason, sampling_id} so we can roll up cost and impact. please make that mandatory in playbook.
Anya: on cost attribution when compaction happens (we drop full traces and keep summary) — we should emit a compaction_event that contains token counts saved and a link to original ids when available. cost system can use that to decrement token charge and assign residual cost to a "compaction reserve" pool if attribution is ambiguous.
Sam: pragmatic: include an ops runbook for spike: 
- immediate: flip conservative thresholds (cpu_pct += 10)
- short-term: enable priority_bucket=critical only (<=100)
- postmortem: run cohort analysis on shed events within 48h
