sam: That hex shows a null byte inserted into the JSON string. We had a runtime optimization landed last month that coalesces empty flush frames then writes a zero-length chunk to force a flush; with gzip + some proxies that can produce 0x00 bytes in the stream after decompression. The client streaming parser used to ignore NULs, but recent parser change tightened validity checks and now fails.

iris: Customer workaround: disable compression (Accept-Encoding: identity) or turn off streaming JSON mode and poll the response. Could also set the SDK option `allow_binary_sanitization=True` in py-sdk (not public) — not ideal.

anya: Customer provided a repro that reliably fails in their env. I reproduced locally by piping a crafted response into the SDK parser. Minimal python repro:

# repro.py
from redwood import streaming_parser
chunks = [b'{"role":"assistant","content":"Hello\\x00"}\\n', b'{"role":"assistant","content":"World"}\\n']

sam: OK I can reproduce with that. Root cause: streaming parser uses naive str() conversion on bytes before feeding to json.loads which doesn't strip embedded NUL; json.loads fails. Fix: use bytes.decode('utf-8', errors='surrogatepass') and strip NULs or treat them as harmless. I'll push a fix to py-sdk and ts-sdk to normalize bytes before parse.
