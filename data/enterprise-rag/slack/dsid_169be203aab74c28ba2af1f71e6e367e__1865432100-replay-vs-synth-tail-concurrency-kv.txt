Marta: Did you vary microbatch_size? we've seen microbatch=1 gives better tail but lower throughput; microbatch>=4 hides kernel launch latency but can create convoying for rare long requests. Which kernel was selected in those runs?

Arjun: Good call. I ran microbatch 1/4/8. Kernel selector picked the small-batch path for 1, fused attention kernels for >=4. Observed p99 jumps when fused attention chosen under mixed seq lengths.

Ryan: Profiling snapshot (top of stack simplified):```text
CPU: scheduler waits -> rpc handler -> batching loop -> enqueue to GPU
GPU: kernel_launch -> cudaMemcpyAsync (KV restore) -> kernel stall (waiting for stream sync)
```Main hotspots are memcpy + per-request KV restore on replay where prefix reuse is low. nvprof shows frequent short memcpy ops that serialize.

Gabe: My hypothesis: synthetic poisson with fixed concurrency overestimates prefix reuse because requests overlap differently than real clients (bursty open/close patterns). So synthetic hides KV restore cost and reduces measured p99. We should replay with preserved client concurrency (not just timestamps) or generate synthetic with bursty ON/OFF sessions.

Emily: Agreed. Also, we need consistent metric definitions. Are we capturing client-observed p99 (end-to-end) or server-side scheduling-only p99? I think previous runs mixed them. We should standardize on client-observed latency for SLOs.

Marta: For visibility: add KV cache hit ratio and per-request KV bytes restored into the perf logs. Suggested log line:```text
