dana: Quick RFC follow-up: idea to add a compact 'intent' claim to issued API keys so gateways can make cheap allow/deny decisions for hot paths without hitting full RBAC. Not meant to replace RBAC, just a performant hint.

mark: I'm wary. How do we avoid intent creep — everyone adding their own intents and it becomes a mess?

yvonne: agree that's the main risk. proposal: maintain a small canonical registry (<=12 intents) and require a short justification when requesting new ones. approvals go through security/product.

dana: also version the intent vocabulary. key metadata includes an intent_version; services read it so semantics can evolve.

emily: can we see an example key blob?

dana: example (minimal):

```json
{"key_id":"kp_abc123","intent":"vector:write","intent_version":"1","issued_by":"console","sig":"hmac_v1:..."}
```

mark: signature is critical. gateway must validate the sig (HMAC) to prevent client forging intent. rotation through KMS.

yvonne: gateway flow suggestion: read X-RW-Intent header or key blob, verify signature, check route-policy map. if policy explicitly allows intent for this route, return 200. otherwise forward request to authz service for full evaluation.

emily: logging: every short-circuit decision should emit a structured audit event with key_id, route, intent, decision, verifier_result. that helps detect drift and misclassification.

dana: migration plan: 1) Advisory only: gateway adds X-RW-Intent header to requests (no enforcement) for two release cycles. 2) Telemetry collection and confusion report (intent used vs actual authz decisions). 3) Opt-in enforcement on low-risk routes. 4) Gradual expansion and SDK helpers for services to validate intents locally.

mark: revocation/rotation question: if we blacklist a key, gateway cache must evict quickly. we should have a fast revocation cache with TTL ~30s and a push invalidation path.

yvonne: agreed. also add per-intent risk levels: LOW, MEDIUM, HIGH. default fail-policy when signature validation or registry lookup fails is per-intent: LOW -> fail-open with alert, HIGH -> fail-closed.

emily: ops ask: are we ok with any fail-open behavior? even low-risk can be abused. maybe only allow fail-open for internal ingestion endpoints that already have rate limits.

dana: that's sensible. we'll make fail-policy configurable per-route+intent.

mark: please include a dashboard in the RFC: intents by route, short-circuit rate, signature failures, revocation hits. those metrics will guide rollout.

yvonne: one more: require an audit tag in the key request when requesting HIGH intents to trigger extra review.
