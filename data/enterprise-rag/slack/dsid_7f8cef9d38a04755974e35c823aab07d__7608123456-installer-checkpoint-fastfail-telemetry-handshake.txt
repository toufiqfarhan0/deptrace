Anya: Heads up — prototyping an 'installer checkpoint' for long-running in-place upgrades. Goals: validate staged files/signatures mid-upgrade, support a fast-fail rollback without re-pulling full image, and atomically capture a tiny telemetry bundle (hashes + installer logs) for postmortem. Want quick feedback on interface and failure modes.

Matt: How is this different from the current staged-activation flow? Does this mean operator has to keep two images live during upgrades?

Anya: It's complementary. staged-activation assumes full content transfer + activation window. The checkpoint is for cases where we patch in-place (no reimage). Operator retains current content but we record a checkpoint marker and a small "incomplete" tombstone. Rollback operates by metadata revert rather than full re-pull.

Ravi: Integrity and privacy questions: telemetry must not leak secrets or PII. Proposal: telemetry bundle = [manifest-delta.json, installer.log.gz, signature.sig]. Signature covers manifest-delta and uses a KMS-backed key. For chunked artifacts include a Merkle proof for any referenced chunks.

Samir: Ops note — many private/air-gapped installs cannot auto-upload telemetry. So the upload must be optional and support local export (USB) or operator pull. Also need retention policy: minimum local retention of 7d before auto-purge, configurable.

Alina: API surface thought: installer POSTs checkpoint to local operator socket `/var/run/redwood-installer.sock` with payload: `{checkpoint_id, state, hashes, artifacts:[...], signature}`. Operator decides retention/uplink. For low-bandwidth devices we should support a compact fallback (base64 tarball or compressed diff).

Anya: Example minimal payload: 
```
{
  "checkpoint_id":"cp-20260321-01",
  "state":"checkpointed",
  "hashes":["sha256:..."],
  "signature":"sig-v1",
  "min_action":"rollback" // no reapply
}
```

Matt: Rollback semantics: operator should offer two modes: "lazy-revert" (adjust manifest pointers, fast) and "hard-swap" (swap symlinked roots/atomic fs move). Lazy is faster but brittle across multi-component changes. Which should be default?

Ravi: Recommend default=lazy-revert but with safety gates: require atomic marker file and a configurable GC window. Also add an operator CLI: `redwood-operator finalize-checkpoint --id cp-... --promote` to convert a checkpoint into a permanent state (and trigger artifact GC).

Samir: Monitoring/observability: emit metrics `installer.checkpoint.attempt`, `installer.checkpoint.success`, `installer.checkpoint.rollback`. All log lines should include `checkpoint_id` and a trace-id for correlation. Important: never include user prompt payloads or other sensitive inputs in these logs.

Alina: Rollout policy: Hosted/Dedicated we can auto-upload telemetry to our backend; Private/Airgap default = agent-export-only (operator chooses export mechanism). UX doc should require operator ACK before automatic finalize.
