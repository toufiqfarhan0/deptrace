Darren: This smells like pre-chunker fragmentation. We previously tuned for latency (emit early), but if fragments are too small we pay full syscall/kernel path per fragment. Sidecar used to coalesce, but we reworked that for backpressure.
Joni: Also worth noting: kernel selector has a tie-breaker that picks the generic small-kernel for seq_len < 32 based on a single-sample window. If many mini-requests hit, the kernel path is slower than the mid-sized kernel for our microbursts. Could be compounding.
Samir: Quick canary I ran at 600 concurrent streams: disabling prechunk coalescing dropped host CPU by ~5% but P99 L7 latency went up ~8% (more bytes/packets per stream). Tradeoff.
Alex: Numbers from the canary (avg of 3 runs):
- baseline: host_cpu=38.6%, tokens/s=182k, ingress_p99_ms=42
- no-coalesce: host_cpu=34.9%, tokens/s=177k, ingress_p99_ms=45
So CPU improved but some latency tail worsened.
Maria: Thoughts on a balanced approach? We need to reduce syscall noise without regressing latency too much.
Darren: Proposal: change prechunk target to enforce a 512B minimum fragment and re-introduce a sidecar flush coalescer that groups smallwrites for ~150us max. That keeps latency bounded but reduces syscall count.
Joni: On the kernel side: update kernel selector heuristic to use a sliding avg of observed seq_len (5m window) and prefer the kernel with better average throughput, not just per-request stat. Also add a quick fallback: if decode time per token > threshold, switch kernel for next N requests.
Samir: KV cache behavior: profiler shows eviction thrash keyed by exact fragment boundaries. Per-fragment keys blow up the shard working set. We should canonicalize kvcache keys by prefix-hash (first 64 bytes) to coalesce similar fragments. Quick microbench shows kvcache hit-rate +9% with prefix coalescing.
