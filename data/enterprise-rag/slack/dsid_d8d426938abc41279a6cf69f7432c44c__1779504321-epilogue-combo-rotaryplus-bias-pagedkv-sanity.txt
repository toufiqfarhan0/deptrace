sara: Hypothesis: combining rotary and bias into a single epilogue increases the number of scattered stores (writes to KV pages) and breaks page-alignment assumptions, which causes extra page faults under paged-KV. That would explain the tail.

leo: Interesting. If fused epilogue does more frequent t_write ops to KV backing memory, paged-KV's eviction policy might be thrashing. Did you test with a larger KV page size or with atomic-free write path?

jia: I ran two quick diffs: (1) disable epilogue fusion -> p99 dropped to ~48ms but p50 increased ~+1ms; (2) increase page_size=131072 -> p99 went to ~72ms (better but still worse than non-fused). So fusion helps avg latency but hurts tail on paged workloads.

matt: That tradeoff aligns with our production patterns: interactive chat cares about tail. We should avoid fused-epilogue for paged-KV heavy routes unless we fix write alignment.

sara: Suggested short-term mitigations: 
- add an alignment pass in epilogue to coalesce writes to page-aligned buffers before committing to KV memory
- change kernel-chooser rule: for paged_kv=true && seq <= 256 && fused_epilogue enabled -> prefer unfused fallback if observed p99 > threshold
