marta: Quick follow-up from the ABI minimization RFC — thinking we should explore a tiny "feature-negotiator" protocol instead of shipping full manifests to every runtime. The idea: control-plane sends a compact capability vector + version, runtime adapts locally. Pros: much smaller wire format, faster fallbacks, simpler private deploy MV. Cons: negotiation logic moves into adapters.
kevin: sounds promising. question: where do secrets/KMS creds live in that flow? if adapters need to decide based on capability bits, they might also need to pull keys or claim access.
sam: agree with kev. also telemetry: if adapter behavior diverges per-capability we need to tie quality metrics back to the capability vector for regression alerts. otherwise optimize/break silently.
marta: good points. envisioning capability vector as small bitmask + opt-in metadata url for >tiny cases. auth still controlled by control-plane but runtime can fetch a short-lived claim: e.g. control-plane issues a signed token scoped to capabilities (TTL short). adapters validate token locally, then pull any extra secrets from customer KMS only when needed.
alex: can we keep a canonical compatibility fallback? flow: if negotiator version mismatch -> fall back to compatibility-mode v0 (the old full-manifest path). That keeps safe rollback.
kevin: careful: fallbacks amplify attack surface. need to ensure fallback path has same auth constraints. Also rate-limiting and quota enforcement must be preserved across both flows.
marta: agreed — fallback must be identical policy-wise. we can encode policy id into the token so runtime enforces same quotas/role checks.
sam: telemetry implementation detail: include capability vector in traces and per-route metrics. small change to our tracing lib, add tag: redwood.capvec=v1. Also add lineage id for rollout correlation.
kevin: what about private deployments where control-plane is customer-managed? they might not accept signed tokens from our control-plane. we need a mode: allow local-signing or pre-shared signing key distribution for private. That increases ops complexity but is doable.
alex: tradeoff: either we add PKI/bootstrap logic for private or we keep manifest-heavy older approach for private only. Which do we prefer long-term?
marta: long-term we want same UX across hosted/dedicated/private. I'm leaning PKI bootstrap with explicit rotation steps in onboarding docs. Short-term we can gate private to old manifest until we ship the bootstrap UX.
