elaine: Heads-up — security requested a short design decision on DEK/KEK call frequency and audit surface for envelope encryption. trying to keep it actionable for the oncall runbook.

raj: +1. main constraints: 1) minimize KMS calls for cost/latency, 2) maintain auditability for key usage, 3) ensure quick rotation/eviction on compromise.

sam: Proposed baseline: cache unwrapped DEKs in a local keystore with TTL 15m, refresh on use after TTL, and backoff/refresh jitter. keep KEK unwrap calls to KMS only on cache miss / rotation events.

maria: question — for multi-tenant customers do we cache per-tenant DEK or global? also RBAC: who can trigger KEK unwraps in emergencies?

elaine: per-tenant DEK cache. reason: limits blast radius and helps audit mapping (key usage -> tenant). RBAC: only a small sec/admin group + emergency runbook service account can request KEK unwraps. those calls are logged via KMS audit.

raj: about audit: ensure we send enriched context with each KMS request where supported (e.g., AWS: requestContext/externalId? we can add attributes in CloudTrail via encryptionContext). record caller, tenant_id, operation_id, and reason (if manual). on GCP/Azure use equivalent fields and centralize logs in SIEM.

sam: example snippet for unwrap path we discussed: ```python
# pseudo
dek = local_cache.get(tenant_id)
if not dek or dek.age > TTL:
    dek = kms_unwrap(kek_key_id, wrapped_dek, context={"tenant": tenant_id, "op_id": op})
    local_cache.set(tenant_id, dek, ttl=TTL + jitter())
return dek
```

maria: two followups: 1) TTL length tradeoffs? 2) what about long-lived streaming sessions holding DEKs in memory?

raj: TTL tradeoff: shorter TTL reduces exposure if DEK compromised but increases KMS cost/latency. For most request patterns 15m-1h is reasonable. Use adaptive TTL: high QPS tenants get slightly longer TTL (30-60m) to reduce calls. For low-QPS or high-security tenants we set 5-15m.

sam: streaming sessions: prefer ephemeral DEK derivation for session keys — derive per-connection ephemeral keys from DEK using HKDF with session nonce; those session keys can be rotated frequently without KMS hits. document this in SDK.

maria: good. what about rotation? if KEK rotates we need to rewrap DEKs and invalidate caches. how to push invalidation safely?

elaine: rotation plan: 1) pre-wrap DEKs with new KEK during maintenance window (async background job that rewraps and updates metadata), 2) once majority rewrapped, flip pointer to prefer new KEK; 3) on KEK change, force cache-invalidation events + short grace TTL (e.g., 30s) for in-memory caches to allow live requests during cutover. 4) audit all unwrap/rewrap ops.

raj: implement an event channel for invalidation (pub/sub). when rotation starts publish message: {"event":"kek-rotation","kek_id":"kek-v2","affected_tenants":[...],"ts":...}. services subscribed will drop tenant DEK caches or set them to bump TTL to 0.

sam: small note: ensure we have rate-limited rewrap workers to avoid KMS quota bursts. add exponential backoff and concurrency caps per KMS key.

maria: vuln triage scenario: if we detect potential exfiltration of unwrapped DEKs, steps?

elaine: incident steps (short): 1) rotate KEK immediately (create new KEK and disable old for new unwraps), 2) force cache invalidation across fleet, 3) schedule rewraps for DEKs with new KEK, 4) audit logs correlate unwrap timestamps + caller metadata, 5) notify affected customers per policy, 6) rotate application-level data keys if exfiltration confirmed. document this in postmortem template.

raj: RBAC changes needed: create dedicated service account for rewrap/rotation with narrow perms, audit-only role for non-admins, and emergency breakglass role with time-limited MFA. log role elevation events.

sam: KMS quotas: AWS KMS has hard limits for Decrypt/Encrypt calls. Mitigation: async rewraps, caching, batching rewraps in jobs, regional key splits to spread load. record quota usage in observability.

maria: anything about encryptionContext leakage privacy? careful not to put PII in context. use tenant_id hash or opaque id.

elaine: agreed. use non-sensitive identifiers in encryptionContext, store mapping in our internal db with access controls.
