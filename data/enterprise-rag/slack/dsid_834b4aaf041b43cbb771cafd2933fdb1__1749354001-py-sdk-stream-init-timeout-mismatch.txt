sam: can you confirm the exact sdk version? we changed some streaming internals around v0.12.x and added tight handshakes in a couple spots.
maria: they report using redwood==0.12.1.
kevin: looking. v0.12.1 introduced a short internal "stream init" timeout intended to fail fast for broken proxies. it defaults to 3s and lives outside the requests timeout tuple. that explains the 3.0. the tuple still controls connect/read for the main request, but the SSE/chunked handshake is guarded separately.

kevin: immediate workaround: set environment variable REDWOOD_STREAM_INIT_TIMEOUT to a higher value (seconds) or instantiate Client with the keyword stream_init_timeout to increase that handshake allowance. Example that the customer confirmed works:

```python
client = Client(api_key="sk-...", timeout=(60,600), retries=0, stream_init_timeout=90)
stream = client.generate_stream(...)
for c in stream:
    print(c.text)
```

kevin: important note: with retries enabled you will see duplicated partial outputs if a retry happens after the first partial stream succeeded. we recommend disabling automatic retries for streaming requests (retries=0) and implementing idempotency at the app layer (request ids, dedupe of partial chunks).

liz: for support copy: tell customers to bump both the requests tuple read and the stream_init_timeout on v0.12.x. older versions (<0.11) used the requests default which was more forgiving, and newer patch (planned) will align behavior.
