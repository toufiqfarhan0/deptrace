leo.t: thinking about the ephemeral connector model: we mint per-tenant "leases" (connector sessions) that bind a tenant agent -> regional relay instance + nat-ip. need to nail lease protocol semantics and backpressure when the nat pool is near exhaustion. wanted quick takes before i draft an RFC.

nina_s: high level: what are the invariants we need from the lease? e.g., single-owner lease per tenant, predictable renewal timing, observable revocation, and graceful connection drainage on revoke.

leo.t: yes. invariants: (1) at most one active lease per tenant per region, (2) lease contains connector_id, nat_ip, cert_serial, expires_at, and a renew_nonce, (3) renew endpoint must be idempotent and cheap, (4) revoke should be immediate but allow short drain window for in-flight calls.

patrick: for backpressure, we should provide three signals to agents: ACCEPT (grant), QUEUE (soft backoff), and REJECT (hard). QUEUE returns retry-after and a queue-position token. that lets agents back off rather than hammering.

ops_cli: ops constraints: we can't let queue grow arbitrarily. need per-region queue depth, an overflow policy (spill to hosted or fail), and alerting for queue saturation. also audit trail for who got what nat_ip.

nina_s: renewal cadence: I'd prefer short-lived leases (5-15m) to limit exposure, but renew endpoint hit-rate will be high. we need efficient cache + db write pattern: renew should extend lease if caller proves possession (TLS + token). Use optimistic update + vector clock?

leo.t: sketch of API below. renew must be idempotent:

```
POST /v1/lease/renew
Authorization: Bearer <short_jwt>
{ "tenant_id": "t-42", "connector_id": "c-abc", "renew_nonce": "n-001" }

200 OK
{ "status": "ACCEPT", "expires_at": "2026-06-10T12:34:56Z", "nat_ip": "198.51.100.23", "cert": "..." }

202 QUEUE
{ "status": "QUEUE", "retry_after": 45, "queue_token": "q-zz" }

429 REJECT
{ "status": "REJECT", "reason": "nat_pool_exhausted" }
```

Renew must be cheap and avoid a distributed lock on nat allocation. we can pre-assign a small burst slot and use a local atomic counter in relay to serve transient spikes. longer allocations hit central allocator.

patrick: pre-assigned burst slots per relay is a good idea. also consider a grace window where an expired lease can be reactivated quickly if the same connector comes back within X seconds to avoid churn. maybe 60s hold.

ops_cli: draining semantics: on revoke we transition lease -> draining with a draining_until timestamp. relay stops issuing new sockets bound to that connector, but existing requests continue until draining_until. also expose a /v1/lease/force-revoke for emergency. must be audited.

nina_s: revocation propagation and consistency: relays should subscribe to a revocation stream (kafka) with sequence numbers. on partition we should fail-safe: either conservative fail-open (allow traffic) or fail-closed (deny). which one? security prefers fail-closed, but availability wants fail-open with telemetry. we need product input.

leo.t: product note: for private tenants allowlist use cases, failing open across revocation is risky. propose fail-closed for revocation critical paths (suspend/compromise) and fail-open for soft ops events (relay restart). define categories of events.

patrick: metrics to publish: leases_granted_total, leases_active, leases_expired, nat_pool_utilization, renew_queue_length, renew_latency_p50/p95, revoke_propagation_lag_seconds. add per-tenant last_seen_connector.

ops_cli: runbook: if nat_pool_utilization > 85% trigger autoscale and alert; if >95% start rejecting new leases and send admin page. routing fallback: when rejecting, we can optionally route to hosted control-plane if tenant opt-in. require explicit opt-in during onboarding.

nina_s: about queue tokens: they should be redeemable exactly once. queue token -> when granted we issue cert + nat_ip and invalidate token. also prevent token replay by binding token to connector's pubkey.

leo.t: security: lease issuance requires three proofs: short_jwt (time-limited, signed by control plane), client-sig over nonce (possession of private key), and optional mTLS during transport. cert TTL short (1h). maintain revocation list in central db and push deltas.

patrick: scale concerns: renews are N per minute per tenant. we should give clients a jittered renew schedule to avoid spikes. also support long-lived "stable" mode for whitelisted tenants (paid tier) with less churn and reserved nat ips.

ops_cli: compatibility: connectors should be able to present a header x-connector-lease to downstream logs for traceability. console should surface current lease map for tenant admins.

leo.t: open implementation questions i want feedback on: (1) default lease TTL (5m/10m/15m)? (2) hold window for recent-expired leases (30s/60s/120s)? (3) policy for queue overflow (spill to hosted vs immediate reject)? (4) fail-open vs fail-closed defaults for revocation stream partition?

nina_s: my picks: 10m TTL, 60s hold, overflow -> spill to hosted only if tenant opted in, default revocation partition -> fail-closed for security-critical ops else fail-open.

patrick: +1 for 10m and 60s. queue overflow -> reject by default; ops can enable hosted spill for select tenants.
