mina: Heads-up: hit an annoying race when doing onboarding with redwoodctl local-serve + auth on my Linux laptop (WSL2).
dave: what happened?
mina: flow is: `redwoodctl local-serve --cache ./tmp` then in another shell `redwoodctl auth login`. login opens browser to callback localhost:0 or a random port and the local-serve sometimes binds the same port first, causing the auth client to fail with `ECONNREFUSED` or 'callback mismatch'.
oscar: we default to ephemeral ports for the auth callback if the configured port is 0. That was to avoid collisions on shared dev machines, but doesn't play nice with local-serve which probes ports for health.
mina: exact error:
```
$ redwoodctl auth login
Opening browser for authentication at http://127.0.0.1:52345/callback
Waiting for callback... failed: connect ECONNREFUSED 127.0.0.1:52345
No profiles found after login
```
dave: ugh. And `local-serve` logs show it grabbed a port in the same ephemeral range right before the auth client tried to open. We need a deterministic callback port or explicit docs for setting one.
oscar: quick workaround: `redwoodctl auth login --callback-port 29999` or set env `REDWOOD_AUTH_PORT=29999` then run login. That avoids the race.
mina: workaround worked for me. But for new users this is pretty confusing.
dave: filing a fix: make auth client prefer a reserved port range for dev (e.g., 29900-29999) and add a CLI flag to pin callback port with a clear error when it's in use.
oscar: yep also update local-serve to check for the node-based auth listener and avoid pre-binding port 29999 by default.
mina: could we also improve the error message? "No profiles found after login" feels useless here. Something like "Login failed: callback port refused (ECONNREFUSED). Try --callback-port or set REDWOOD_AUTH_PORT." would help support.
