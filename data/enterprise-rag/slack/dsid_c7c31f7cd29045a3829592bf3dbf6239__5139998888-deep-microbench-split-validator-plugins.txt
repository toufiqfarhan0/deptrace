Marta: Quick design note 1: I want us to formally split onboarding benches into two lanes: microbench (fast, local smoke checks, <5s) and deepbench (distributed, fidelity checks, minutes-hours). We keep the sampler common but emit lane_hint. Pros/cons?

Diego: Strong +1. Microbench should focus on regressions we can catch cheaply (token-level diffs, obvious hallucinations). Deepbench runs heavier evals (nshot, long context, bolstered metrics).

Priya: Implementation ask: we need a compact artifact schema so orchestrator and downstream tools can consume results regardless of lane. Minimal fields: batch_id, lane, model_id, seed, runtime_profile, metrics[], artifact_uri, provenance_tag.

Sam: For validators we should make a plugin interface: validate(artifact_uri, policy) -> {pass|fail|triage}. Triage can attach suggested auto-actions: rerun-deepbench, mark-golden, escalate. Plugins run in isolated sandboxes and can be local-only for private deployments.

Marta: Good. Also: auto-triage rules. If microbench shows token_edits > X and deepbench not yet run, create a scheduled deepbench ticket and mark model state=under-investigation. If deepbench fails critical metrics we mark admission:blocked.

Diego: Note on reproducibility: artifact_uri must include fingerprint + immutable snapshot id. Validators must log inputs used (seed, KV-state). This is crucial for incident replay.

Priya: Security: in private mode validators run entirely inside customer infra and report only high-level verdicts (pass/fail) + stable fingerprints. No payloads or raw logs leave the VPC.

Sam: Edge case: flaky samples. Validator plugins should return flakiness_score. If score > threshold we auto-tag sample flaky and reduce its sampling weight. Sampler policy picks that up.

Marta: Orchestration change: make lane scheduling orthogonal to GPU pools. Microbench can use small CPU/GPU sandboxes with cached KV to speed up. Deepbench routes to burst pools and respects per-tenant quotas.

Diego: API sketch for validator plugin registration: POST /validators { name, capabilities:[micro,deep], sandbox_type: docker|wasm|local, allowed_modes:[hosted,dedicated,private], webhook_on_triage }

Priya: Observability: emit linked timeline events: sample_selected -> micro_result -> validator_verdict -> action_taken -> deep_result (if scheduled). Console can present lineage.

Sam: One more: rollout safety net. If deepbench rejects and sampler already promoted model to canary, orchestrator should be able to retroactively pause canary traffic via rollout controller hook. That means onboarding platform needs a small write path into rollout system with auth.
