architecture

alex: quick RFC follow-up — proposing a lightweight "checkpoint-carryforward" for offline upgrades. idea: the airgapped installer keeps a small signed checkpoint manifest that records applied deltas + last-accepted-signers. operators can carry that checkpoint forward on media to the next site and the verifier only needs to validate the checkpoint signature chain rather than re-verify every blob. thoughts?

maria: curious — is the checkpoint just metadata or does it reference content hashes?

alex: metadata only, plus compact list of artifact hashes. minimal: {seq: 42, hashes: [...], signers: [...], expiry: ts}. no heavy content copy.

cheng: how do we avoid replay/rollback attacks if a checkpoint is copied between sites and then an old checkpoint is reintroduced?

alex: include monotonic seq + per-operator attestation. verifier rejects if seq <= local seq unless operator-override. also suggest a short-lived carry token bound to operator and media serial.

sara: operator-override scares me. that's a human bypass. prefer crypto-bound anti-rollback: offline checkpoint includes a prev-checkpoint-hash so chain integrity is verifiable.

jamie: +1 for chain integrity. But what if media gets lost mid-carry? we need a resume protocol. maybe carryforward artifacts are chunked and signed per-chunk so partial transfers are detectable and resumable.

dan: chunking sounds right. we should enumerate constraints: 1) must work over USB + tape, 2) operate with limited RAM, 3) verifier must be constant-memory for header-only checks when possible.

maria: operational question: who rotates the signing key? signer-handoff complexity is the core of this thread. if an org rotates keys frequently, how does a carryforward avoid invalidating the chain?

alex: propose a signer-handoff ticket: when switching signers, create a short-lived cross-signature that proves continuity: old-signer signs new-signer-pubkey + checkpoint-seq. store these cross-sigs in the checkpoint history (small). verifier accepts either signer if cross-sig chain exists.

security-bot: alert: cross-signatures increase attack surface. need explicit verification rules in the RFC: limit chain depth, require CA-backable identity, and define revocation semantics.

cheng: what about a blackhole scenario where someone forges cross-sig? must require old private key, so it's only possible during legitimate handoff. but edge case: compromised old key — we need revocation markers distributed with next checkpoint and optionally via ops-console once connected.

ops-bot: note: implementability note — we can't assume online revocation for pure airgap. revocation will be best-effort: next physical carry should surface revocation tombstones. offline verifier must expose a clear 'stale-key' state and a recovery plan.

jamie: on the verifier boundary: avoid making verifier understand full key lifecycle. keep the verifier minimal: 1) validate checkpoint chain, 2) check cross-signatures up to N hops, 3) require operator confirm if crossing threshold. heavyweight ops can use the console helper when online.

sara: rollback mitigation: add a monotonic checkpoint anchor embedded into the installer runtime (meta-seq persisted to disk). when applying a checkpoint with lower seq, fail unless operator explicitly runs 'redwood-apply --force-rollback' with a signed operator token.

alex: sample minimal checkpoint snippet for RFC (pseudo):
```json
{
  "seq": 42,
  "prev_hash": "sha256:...",
  "artifacts": ["sha256:aa..","sha256:bb.."],
  "cross_sigs": [{"from":"old-key-id","sig":"..."}],
  "expiry": 1700000000
}
```

maria: expiry is good but offline clocks differ. we should accept a grace window and prefer seq/chain checks over strict expiry.

cheng: performance: verifying many cross_sigs on-device could be slow. limit cross_sigs to 2 and keep sig algorithm Ed25519. also support batched verification in C to be fast on low-end devices.

dan: storage GC: checkpoints will accumulate. propose checkpoint pruning rules: keep last K checkpoints + any checkpoints referenced by un-applied deltas. provide a compact 'index' for fast lookup.

jamie: upgrade safety: when applying a delta that changes activation semantics (e.g., new service user), require an extra 'activation manifest' signed by ops to be present in the checkpoint. prevents silent privilege changes over carryforward.

security-bot: also require audit log snippet in checkpoint for changes to critical components. small and only hashes of logs acceptable.

alex: operational flow recap in plain steps for RFC: 1) operator exports checkpoint from site A -> signed checkpoint + chunked artifacts. 2) carry media to site B. 3) verifier on B validates chain, cross-sigs, seq, artifact hashes. 4) if passes, apply deltas incrementally with atomic replace. 5) write new checkpoint and persist. 6) garbage collect old checkpoints per policy.

maria: and add explicit 'handoff failure' playbook: if verification fails, reject media and generate a signed 'error-report' to ship back for offline forensics.

alex: decision proposal: add this carryforward + cross-sign-handoff pattern to RFC as opt-in feature behind a flag; require disabled-by-default until we implement tooling for operator tokens and cross-sign UI. owner: alex + jamie.
