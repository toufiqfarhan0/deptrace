anya: quick sync — thinking about a migration away from global prefix ownership to a hotset-affinity pin model to reduce eviction thrash. thoughts?
liam: curious — what's the core invariant we need to keep? read-after-write? single-writer for prefix metadata?
sanjay: single-writer for ownership is still ideal for correctness, but we can relax residency guarantees for hot prefixes via pins. goal is lower eviction churn without adding cross-shard races.
mei: can you sketch the pin API? TTLs? priority buckets?
anya: rough sketch: `POST /prefixes/{p}/pin` body `{ owner: shard_id, mode: "soft"|"hard", ttl_ms: 300000, weight: 1 }`
anya: semantics: hard = prevents eviction unless explicit demote; soft = eviction score reduced but still evictable under memory pressure. pins tracked by owner shard only.
liam: how does handoff look when we need to move a prefix to another shard? race if both shards think they have a pin.
sanjay: handoff plan: source issues a `handoff-intent` marker in metadata, new owner attempts to acquire a lease; after acquiring lease it sends `acquire-pins-for-prefix` RPC to source; source transfers active pins (and in-progress inflight contexts) and marks prefix demoted locally. need to guarantee idempotence.
julia: and if the source dies mid-handoff? fallback: ephemeral pins expire using TTL; we need a small safety TTL > typical RPC window. also add `pin-epoch` to reject stale transfers.
mei: metrics we should add: pin-count, soft-vs-hard ratio, average pin-ttl, pin-transfer-latency, failed-handoffs, eviction-after-pin events.
liam: big tradeoff: pin bookkeeping increases per-prefix metadata — memory + perf. do we compress pins into a single bitset or keep small fixed-size vec?
anya: proposal: encode pins as a lightweight 32-bit token with refcount and epoch for common cases; fall back to a small vector only when >N pins (rare). keep pin membounded.
sanjay: correctness checklist: 1) no two shards think they are authoritative writer for same prefix without lease; 2) eviction must consult current pin epoch; 3) handoff must preserve in-flight KV mutations (apply logs or forward requests); 4) demote must wait on inflight-reader drain or snapshot.
julia: about (3): do we require an apply-log transfer or can we rely on central durable store? depends on latency target. apply-log transfer keeps tail latency but is more complex.
anya: agree. aim for a hybrid: if inflight mutations <= threshold, transfer; else fallback to marking prefix read-only and fast-sync via durable store + background state reconciliation.
mei: API & telemetry change list for PR: `pin` RPC, `unpin`, `list-pins`, `pin-metrics`, `handoff-intent`, `pin-epoch` fields. CLI: `infractl prefix pin --prefix p --mode soft --ttl 5m`.
liam: also need eviction policy tweak: when calculating eviction score, if `hard_pin` then score = -INF, if `soft_pin` subtract X from score. add a knob per-tenant.
sanjay: can we support multi-tenant fairness with pins? pins could be tenant-scoped and share global budget; otherwise one tenant could hog pins and OOM others.
anya: yes, include tenant quotas: `max_pins_per_tenant`, `pin_memory_quota`. default conservative. ops can tune at region level.
