maria: Quick sync — gateway is doing proto->JSON + auth rewrite; we've got mismatched quotas and fuzzy telemetry. Thinking about moving quota enforcement downstream (runtime) and keeping gateway dumb. Thoughts?

jon: +1 to enforcement at runtime. Gateway loses token context on streaming and KV cache hits, so ops can't reconcile per-model costs.

ash: Concern: enforcement downstream requires reliable identity propagation. We currently terminate TLS and map creds at the edge. Proposal: propagate `x-rw-actor: <svc>@<env>` and sign with `x-rw-sig`.

lee: Also: retries from gateway today can double-count quotas. We need idempotency semantics.

maria: Agreed. We could add `Idempotency-Key` and a lightweight request-hash check at runtime to dedupe. Prefer per-route quota config surfaced in Console (not buried per-service).

jon: Hybrid approach might work: gateway forwards protobuf payloads intact and attaches `x-rw-routing-hints` for the runtime. Gateway keeps only simple conn-level rate limits; runtime does token/accounting enforcement.

ash: On proto vs JSON: keeping protobuf end-to-end preserves schema and avoids double-parse telemetry divergence. Web clients still want JSON — small translate module near the edge can handle browser clients.

lee: Edge translate adds CPU. Might be better as an Envoy filter or tiny sidecar colocated with the edge proxy to avoid adding hop latency.

maria: Rollout UX needs to support canaries by route header and by tenant. Console should show per-tenant latency, per-tenant token breakdown, and a fallback count (how often we hit a fallback model).

jon: We should add a dashboard panel: `quota-exactness` that compares gateway-reported usage vs runtime-reported usage over time. That'll highlight blindspots.

ash: Implementation sketch: 1) standardize propagated headers. 2) require idempotency keys for retries. 3) runtime enforcement + nightly reconciliation job. 4) console UI for per-route canary controls and signals. 5) 10% canary on staging first.
