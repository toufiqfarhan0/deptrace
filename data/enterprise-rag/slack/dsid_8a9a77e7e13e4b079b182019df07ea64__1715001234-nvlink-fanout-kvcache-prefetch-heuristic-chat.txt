alex: That fallback line is the giveaway. If a peercopy can't allocate pinned staging or NVLink queues are saturated, the runtime falls back to pageable -> CPU -> DMA which is 5-10x slower and blocks the scheduler. Which host allocation path is the prefetch using? hostMalloc or cudaHostRegister?

maria: Currently runtime uses the default host allocator for prefetch pages (malloc + maybe implicit register at copy time). We experimented with cudaHostAlloc earlier but reverted for GC/complexity reasons. Hypothesis: small prefetches to many GPUs (fanout) cause head-of-line congestion on NVLink and then the driver decides to do pageable copies for some chunks.

kevin: Two quick experiments to narrow it down:
1) Force pinning: use cudaHostRegister / cudaHostAlloc for prefetch buffers and re-run the same workload. If peercopy latencies collapse, it's pinned/pageable issue.
2) Change prefetch ordering: group prefetches by destination GPU (so we do depth-first per dest) rather than scatter. That reduces simultaneous distinct NVLink endpoints and should lower contention.

sam: Also check the KV cache heuristic — if we prefetch across 8 GPUs in round-robin, NVLink fanout is worse than grouping contiguous ranges. We might want a grouping heuristic that batches contiguous keys for the same dest GPU.
