Sam (ML): Quick clarification: our rerank endpoint treats `query` as a top-level string (or simple object in some SDKs), and expects candidates to be a list of items to score (strings or {id,text}). `documents` is a separate shape used by the search API where passages are optionally nested. We do NOT implicitly expand `documents` -> `candidates`. If a request includes both, the reranker will only score whatever is in `candidates`. If `candidates` is present and empty, some SDKs might try to infer, but that's unreliable and can cause validation errors.

Sam (ML): TL;DR: two different models:
- `search/documents` flow: you index docs with passages and call the search endpoint (or use our search+rerank pipeline)
- `rerank` flow: you pass `query` (string) and `candidates` (list). Each candidate should be the exact text (or object) you want scored relative to the query.

Alex (Eng): Also watch the `query` shape in their payload — they used `"query": { "text": "..." }`. Our API expects `"query": "..."` (simple string) for rerank. The nested object is accepted by the search endpoints but not by rerank, which can cause a 400. Example of validation error: `{"error":"Invalid schema: query must be string for rerank"}`.

Joel (Support): Customer also complained about latency when they sent 800 candidates at once. Note: we support batching but there are recommended limits. Current soft limit for rerank candidates is 200 per request; above that you'll see increased latency and throttling. Recommend chunking into 50-100 candidate batches for responsiveness and consistent scoring.
