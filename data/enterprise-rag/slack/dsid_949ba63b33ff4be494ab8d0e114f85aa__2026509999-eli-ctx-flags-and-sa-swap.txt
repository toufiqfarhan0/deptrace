Priya (DevEx): easiest pattern: create a flattened, minified kubeconfig that only contains the prod context and point KUBECONFIG to that for the session. example: 

```
kubectl config use-context prod-usw2
kubectl config view --minify --flatten > ~/.kube/prod-only
export KUBECONFIG=~/.kube/prod-only
```

That way your okta merged config won't interfere. Add `export KUBECONFIG=~/.kube/prod-only` to a short-lived terminal session or a small wrapper script.

Sam K: about impersonation / SA tokens — you can check RBAC with `kubectl auth can-i --as=system:serviceaccount:team-a:ci-bot create jobs -n prod`. If you need to run a command as that SA from your laptop, and the cluster supports it, use `kubectl create token`:

```
kubectl -n prod create token ci-bot --duration=10m
# take that token and create a temporary kubeconfig user
kubectl config set-credentials ci-bot --token=<TOKEN>
kubectl config set-context ci-bot-context --user=ci-bot --cluster=prod-cluster --namespace=prod
kubectl config use-context ci-bot-context
```

Note: `kubectl create token` requires k8s >= 1.24 and the ability to create token for that SA.

Maya: if the cluster doesn't support `create token`, the fallback is reading the SA secret (but that's discouraged for long-lived tokens). example: 

```
kubectl -n prod get sa ci-bot -o jsonpath='{.secrets[0].name}'
kubectl -n prod get secret <secret-name> -o go-template='{{index .data "token"}}' | base64 --decode
```

Only do that for debugging and rotate / delete token after. ask infra for a short-lived token if possible.
