ellie: Quick q about chat/completions streaming and function/tool calling. Do we stream partial function arguments as plain text in choices[].delta or emit a separate streaming event type? Example concern: parsing JSON args when they get split across chunks.

ellie: e.g. client expects to call local tool: {\"name\":\"search\", \"arguments\": {\"q\": \"how to...\"}} — how do we deliver that in streaming?

priya: Short answer: we stream fragments inside choices[].delta.function_call.arguments_fragment (plain UTF-8 text). Clients are responsible for concatenating fragments and JSON-parsing when the final chunk arrives. We emit a final chunk that includes the complete function_call object in full in the last delta (choices[].delta.function_call.complete = true) and also return the non-streaming style message at the end for backwards compatibility. :white_check_mark:

priya: Example (newline-delimited streaming events, simplified):
```json
{ "event": "delta", "choices": [{ "delta": { "role": "assistant" } }] }
{ "event": "delta", "choices": [{ "delta": { "function_call": { "name": "search", "arguments_fragment": "{\"q\": \"how to train" } } }] }
{ "event": "delta", "choices": [{ "delta": { "function_call": { "arguments_fragment": " large language models\" } } }] }
{ "event": "done", "choices": [{ "message": { "role": "assistant", "function_call": { "name": "search", "arguments": { "q": "how to train large language models" } } }, "finish_reason": "function_call" }] }
```

priya: Important rules: 1) fragments are opaque UTF-8; do NOT insert separators. 2) final "done" event includes the assembled message object so legacy/non-streaming clients get the same shape. 3) if the argument JSON cannot be safely split (e.g., binary or multi-byte split), we support an alternative streaming field arguments_base64_fragment — server will switch to base64 fragments when a split would break UTF-8 validity.

sam: Will this break older clients that only look for choices[].message? How will runtime signal that a streaming session contains a function_call?

priya: It should not break them. Non-streaming responses still return choices[].message.function_call as before. For streaming clients: initial deltas may not include a function_call key until fragments start; we will emit an early meta-delta: {"event":"delta","choices":[{"delta":{"function_call":{"name":"search","started":true}}}]} so clients can pre-allocate or display a tool UI. That meta-delta is optional but recommended for long-running tool args.

```js
// pseudocode: reassemble fragments
let buffer = ''
onDelta = (delta) => {
  if (delta.function_call) {
    if (delta.function_call.arguments_fragment) buffer += delta.function_call.arguments_fragment
    if (delta.function_call.arguments_base64_fragment) buffer += atob(delta.function_call.arguments_base64_fragment)
    if (delta.function_call.complete) {
      try {
        const args = JSON.parse(buffer)
        callTool(delta.function_call.name, args)
      } catch (e) {
        // fallback: fetch non-streaming response or surface error
      }
    }
  }
}
```
