ana: Heads up, hitting intermittent 401s from Workers when using the JS SDK ESM build. Only happens on retries. First call usually OK. Anyone familiar with Worker-specific header gotchas?

ana: Minimal sandbox: import sdk from 'redwood-inference'; const c = new sdk({ apiKey: RW_KEY }); addEventListener('fetch', e => e.respondWith(c.text.generate({ prompt: 'hi' })))

rachel: That pattern is common. Two likely problems: 1) headers are reused or mutated between attempts, 2) our retry serializer loses header prototypes. Workers expect Headers or arrays, not plain objects.

theo: I saw this too. Our Node runtime uses an internal Headers-like plain object to optimize, which works in Node but fails in edge runtimes where the fetch implementation is strict. When we stringify options for retry we drop the Headers prototype.

ana: Example of issue in SDK runtime:
```js
const opts = { method: 'POST', headers: runtimeHeaders };
return fetch(url, opts);
```
where runtimeHeaders was reused.

pat: Fix ideas:
- always use new Headers(base) before mutating
- when serializing for retry, store header entries: Array.from(headers)
- provide an explicit edge ESM entrypoint that avoids node: polyfills (no buffer/process)

rachel: +1. Also add an exports map in package.json: 
{"./runtime": {"import":"./dist/node/runtime.js","default":"./dist/node/runtime.cjs"},"./runtime.edge":"./dist/edge/runtime.js"}
so bundlers can pick runtime.edge for worker targets. Document in README.

theo: TS typing note: Users importing the ESM edge entry in workers get ambient node types pulled in by devDependencies sometimes. Publishing a lightweight dist/edge/index.d.ts with HeadersInit typed from web lib avoids that leak.

ana: Short-term workaround I dropped into our worker:
```js
const headers = new Headers();
for (const [k,v] of requestHeaders) headers.append(k, v);
headers.set('Authorization', `Bearer ${RW_KEY}`);
await fetch(url, { method: 'POST', headers });
```
That fixed retries for me.
