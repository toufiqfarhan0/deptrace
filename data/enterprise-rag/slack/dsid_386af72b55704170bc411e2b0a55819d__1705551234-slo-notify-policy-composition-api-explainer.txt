Maya: Quick question for the group — we need to nail the API semantics for composing notify policies in the console. If multiple policies match a request (global default + tenant override + route-specific), should the platform merge actions, pick a winner by priority, or have an explicit fallthrough chain? Trying to align console UX, routing logic, and quotas.

Jorge: Context: most customers will have a small set of defaults and then 1–2 tenant overrides. If we merge naively we risk fanout explosion (double notifications). If we pick a single policy by priority, operators lose expressivity.

Priya: My vote = merge actions but dedupe at delivery + enforce per-tenant fanout budget. Also include explicit precedence rules: higher priority policies augment lower ones unless they set `terminal: true`. That lets teams opt out/short-circuit.

Ben: Merge+dedupe sounds OK but we need predictable metrics. If a policy says `suppress: true` and another says `notify: email`, what's final? I think `suppress` should win if any policy requests suppression. We can't have half-suppressed fanout.

Lucy: Telemetry requirement: console needs to show the \"effective\" policy computation for a route (what matched, what was merged, what was suppressed). We need tags for `matched_policy_ids`, `final_action`, `dedup_count`, `suppressed=true/false`, and `fanout_cost`. Also capture `policy_resolution_path` for debugging.

Maya: Draft API proposal (pseudo-JSON) — feedback welcome:

```
{
  "policies": [
    {"id":"global-1","matcher":"*","priority":10,"action":{"type":"notify","channels":["email"]}},
    {"id":"tenant-42-override","matcher":"tenant:42","priority":20,"action":{"type":"suppress"},"terminal":true}
  ],
  "resolution": "merge", // or "first-wins" or "chain"
  "dedupe": true
}
```

Jorge: Suggest `resolution` default to `chain` with `terminal` semantics. Chain = apply in priority order; actions accumulate but `suppress` terminates the chain. Cleaner for audits.

Priya: We also need quota metadata at policy-level so the routing layer can fast-reject or rate-limit before heavy fanout. Something like `fanout_budget:{limit:100/day, window:\"24h\"}`.

Ben: UX question — console should render an \"effective policy\" preview when you edit a policy, including sample payloads showing which channels would be called and the estimated fanout cost. That will help customers avoid accidental noisy merges.

Lucy: For telemetry names I propose: `slo_notify.policy_evaluation` (counter), `slo_notify.fanout_attempts` (histogram), `slo_notify.suppressed` (counter). Tag keys: `tenant_id`, `route_id`, `policy_ids`, `final_action`, `deduped`.
