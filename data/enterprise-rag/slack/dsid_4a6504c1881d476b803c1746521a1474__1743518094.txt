Jonas Weber: Quick q for folks thinking about model metadata + generated release notes — what eval metrics (if any) are safe to summarize publicly? We’ve got the internal metadata fields in the schema, but for customer-visible notes we need something consistent + defensible.

Jonas Weber: Specifically: can we say things like “+X% on Redwood standard QA suite” / “no regressions detected” / “reduced refusals” etc, without over-claiming?

Sana Farid: We can, but we need a strict policy, otherwise we’ll end up with “statistically significant” being used loosely.

Sana Farid: I’d strongly recommend v1 public notes only allow:
- directional statements (“improved”, “no material change”, “regression detected and mitigated”) 
- plus a confidence qualifier (“high confidence”, “limited evidence”) 
…and avoid raw numbers unless we’re extremely sure the measurement is stable + non-sensitive.

Quentin Harris: +1. Also we should avoid naming internal eval sets (leaks too much about our coverage / customer prompts). If we mention a benchmark, keep it to truly public benchmarks.

Wei Chen: From docs POV: we also need language that doesn’t sound like marketing. If we say “improved quality”, customers will ask “how measured?” and “why did my use case get worse?”

Wei Chen: “No regressions detected on Redwood’s standard evaluation suite” feels safer than “quality improved by 4%”. But even that needs definition.

Paula Mendes: + what we discussed in product: release notes need to help customers make rollout decisions (canary/A-B), but we can’t imply guarantees.

Jada Williams: On the Console side we’re already planning to show “evidence” internally (eval run IDs, baseline comparisons) behind RBAC. Public should be constrained.

Jonas Weber: OK, so what’s the bar for “no regressions detected”? We’ll get roasted if someone shows a counterexample.

Sana Farid: Proposal (for public claims):
1) Use “no *material* regressions detected” instead of “no regressions”.
2) Require minimum sample size per eval bucket + multiple seeds (where applicable).
3) Require an effect-size threshold + CI not crossing 0.

Sana Farid: E.g. for pairwise win-rate style evals:
- min N=1,000 comparisons overall (or per critical slice)
- use 95% CI on win-rate delta
- claim “improved” only if CI lower bound > +1% (numbers TBD)
- claim “no material change” if CI within [-1%, +1%]
- claim “possible regression” if CI upper bound < -1% (but that probably becomes internal-only unless we ship with mitigation)

Quentin Harris: That seems reasonable. Also we need to split “quality” into families. Some of these are safety metrics, not “quality”.

Quentin Harris: For public notes I’d rather we use categories already in taxonomy:
- Quality (general helpfulness / instruction following)
- Safety/Policy (toxicity, self-harm, disallowed content handling)
- Reliability (format adherence / tool call schema compliance)

Wei Chen: Agree. Also the style guide we’re drafting has a “do not claim” list. We should add:
- don’t mention p-values
- don’t mention specific internal prompts
- don’t mention exact exploit coverage

Marissa Cole: Jumping in — we need something that scales for release engineering. Connor is pushing for an automated template that doesn’t require a human to interpret stats every time.

Connor O'Brien: yup. If we need a stats review on every metadata promotion we’ll bottleneck releases.

Connor O'Brien: Ideally the pipeline computes a small number of “public-safe assertions” and the release note generator picks from those.

Sana Farid: That’s doable. We can have the eval harness output a structured summary object, e.g.:
- `quality_claim_public`: one of {IMPROVED, NO_MATERIAL_CHANGE, REGRESSION_MITIGATED, NOT_EVALUATED}
- `quality_confidence_public`: {HIGH, MEDIUM, LOW}
- `quality_scope_public`: {GENERAL, TOOL_CALLING, JSON_SCHEMA, SAFETY_POLICY}

Sana Farid: The exact thresholds should be centralized in the eval system config so it’s consistent across models.

Jonas Weber: +1. Also for guardrails outcomes (policy engine): can we say “updated safety classifier thresholds” publicly? or too spicy?

Quentin Harris: I think we can say “Updated safety filtering behavior” only if it’s framed as policy adherence / safety improvement, but we should never say what the thresholds are or the trigger details.

Wei Chen: Docs preference:
- “Improved safety policy adherence in edge cases.”
- “Expanded refusal coverage for disallowed content categories.”
But only if we’re sure it doesn’t imply we previously allowed something.

Paula Mendes: Also remember enterprise customers: they want to know if outputs could change. Even a safety tweak can be a “behavior change” for them.

Jada Williams: From schema perspective, we already have “breaking vs non-breaking” semantics. A safety tightening could be “non-breaking” technically, but it *is* behavior. We should tag it as “behavior_change: yes” in public notes.

Sana Farid: Careful: “behavior_change” might cause every release to look scary. Maybe keep it as “Customer impact” field in the note:
- None expected
- Minor (edge cases)
- Moderate (format/safety)
- High (response structure / deprecations)

Jonas Weber: Question: can we ever show metric deltas publicly (like “refusal rate decreased by 2%”)?

Sana Farid: Generally no in v1. If we ever do, it should be:
- on a public benchmark
- with a stable measurement protocol
- and ideally expressed as a range not a point estimate

Sana Farid: Also refusal rate is super sensitive because it depends on the prompt distribution. Customers will interpret it as “model refuses less for my prompts” which may not hold.

Quentin Harris: + it can be gamed. If we publish exact deltas, people will reverse engineer what we care about.

Wei Chen: Strongly prefer no numbers for v1. Use “improved” / “no material change” + internal evidence link hidden behind RBAC.

Marissa Cole: Makes sense. Let’s lock a v1 policy:
