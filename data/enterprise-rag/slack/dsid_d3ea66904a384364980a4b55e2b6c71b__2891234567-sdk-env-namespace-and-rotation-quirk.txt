maria: Quick heads-up — ran into a weird auth edge with SDKs + env var rotation this morning. We had an org key set (REDWOOD_ORG_KEY) and then injected a project key (REDWOOD_PROJECT_KEY) during a deploy, but the long‑running worker kept using the org key even after env var updated.

samir: @maria can you paste repro? sounds like caching in the client (we've seen that before).

maria: Repro (node):
```js
// start process with REDWOOD_ORG_KEY=org-xxx
const client = new RedwoodClient({});
// later, export REDWOOD_PROJECT_KEY=proj-yyy and rotate creds
// worker reuses `client` and still authenticates as org-xxx
await client.generate({ prompt: 'hi' });
```
No restart, just env change + key rotation on vault side.

eli: This matches a bug we saw in python (singleton session caches headers). There's an open issue but different languages handle it differently: python had an explicit refresh method, node didn't.

maria: Two asks: 1) What's the canonical env precedence we want across SDKs (REDWOOD_API_KEY, REDWOOD_PROJECT_KEY, REDWOOD_ORG_KEY etc.)? 2) Should SDKs automatically detect env changes and refresh creds for long‑lived processes?

samir: For parity propose precedence: 1) REDWOOD_API_KEY 2) REDWOOD_PROJECT_KEY 3) REDWOOD_ORG_KEY. Make that explicit in all SDKs and docs.

eli: +1. For long‑running processes we shouldn't silently keep using the old key. Options: a) expose `client.refreshCredentials()` b) watch env var every N seconds (configurable) c) let user re-init client. I prefer (a) + docs for (c).

maria: If we add (a) we should also log a warning when client sees 401 then reauth, so users know rotation happened. Also add a sample app that demonstrates rotate-in-place flow.
