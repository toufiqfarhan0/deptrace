sanjay: That smells like PMTU blackholing — DF set so endpoints never get reduced MSS. Quick checks: run `ip link` on both nodes and `tcpdump -n -vv 'icmp and icmp[0]==3'` on the egress path to confirm.

tess: Confirmed: GPU nodes advertise NIC MTU 9000 but our overlay (geneve) drops to ~1420 for workload traffic. Packets travel host->tunnel->host, and when they hit a lower-MTU transit hop they get ICMP frag-needed, but due to DF the large TCP segments never shrink, so gRPC stalls.

ashley: For immediate mitigation I pushed two things onto the gateway nodes:
```
# enable MTU probing
sysctl -w net.ipv4.tcp_mtu_probing=1
# clamp MSS for new TCP connections
iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

mario: Rolled the iptables change to canary gateways in az-a and az-b. Streams recovered on the affected jobs in ~2–3 minutes :white_check_mark:. Will propagate if no regressions.

sanjay: Long-term fixes: pick one — increase encap/tunnel MTU for the CNI (calico/mesh) so workload MTU stays high; use host-network or host-eni for GPU pools; or request jumbo-frame support end-to-end on the cloud transit path. Each has trade-offs (cost, ops complexity, region support). We should avoid mixing RDMA-enabled hosts with tunnelled workloads unless we control the entire path.

tess: +1 on tagging RDMA/GPU pools to avoid overlay. Also keep an eye on kernel offloads (GSO/GRO) — sometimes offload interacts badly with encap and produces weird-sized packets.
