carol: Oof — per-ingress rps=20 is tiny for a marketing burst. Also `limit-connections` is global per worker connection, might cause queuing. Two pieces: 
- allow a reasonable `burst` at the gateway/token-bucket so short spikes don't immediately 429
- make sure Redis scaling and connection pool are sized so claim ops don't block under burst

carol: Suggested quick mitigation (apply immediately): increase nginx annotations and add buffering + disable request limiting at ingress so the gateway itself enforces bucket logic. Example patch: 
```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/limit-rps: "100"
    nginx.ingress.kubernetes.io/limit-rps-burst: "400"  # custom plugin support
    nginx.ingress.kubernetes.io/proxy-buffering: "on"
    nginx.ingress.kubernetes.io/proxy-buffers: "8 16k"
```

ben: And gateway config change (in their helm values) to increase bucket burst and add short jitter to refill to avoid thundering herd. Example for our gateway helm values:

ben: Yes — conntrack exhaustion can cause request timeouts and retries which look like more load. Suggest raising `net.netfilter.nf_conntrack_max` and enabling `sysctl` on nodes, and ensuring `keepalive` between ingress <-> gateway to reduce new connections. Example sysctl: 
```bash
sysctl -w net.netfilter.nf_conntrack_max=262144
```
Also ensure nginx proxy `keepalive` is enabled: 
```yaml
nginx.ingress.kubernetes.io/proxy-connect-timeout: "5s"
nginx.ingress.kubernetes.io/proxy-read-timeout: "60s"
nginx.ingress.kubernetes.io/proxy-send-timeout: "60s"
nginx.ingress.kubernetes.io/proxy-http-version: "1.1"
nginx.ingress.kubernetes.io/proxy-set-headers: "ingress-nginx/custom-headers"
```
