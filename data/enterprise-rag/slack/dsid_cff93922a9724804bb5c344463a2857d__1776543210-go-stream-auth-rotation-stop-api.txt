nina: Ran into a blocking issue in the Go SDK generator during a sampleapp demo. iterator.Next() hangs when the client tries to refresh creds mid-stream and the refresh request blocks.

omar: annoying. can you share a tiny repro?

nina: yep. start a streaming Generator with a short context deadline, rotate creds server-side to force a refresh, and Next() never returns even after ctx.Done(). snippet: 
```go
ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
defer cancel()
iter, _ := client.Generator.Stream(ctx, req)
for iter.Next() {
  // handle chunk
}
// loop never unblocks if refresh stalls
```

zach: two root causes: (1) refresh HTTP call in SDK goroutine doesn't use the request context so it can block indefinitely, (2) iterator has no public Close/Stop so consumers can't force teardown.

omar: mitigation plan: patch the SDK so refresh requests are req.WithContext(iterCtx) and add an iterator.Stop() that cancels internal ctx and closes channels. also cap refresh retry/backoff so it doesn't loop forever when network blackholes occur.

nina: agree. for sampleapp, show the proper pattern: use context.WithCancel for long-lived streams and defer iter.Stop(). add a short note about rotating credentials safely.

zach: tests: add a server that sleeps on /refresh and assert that calling iter.Stop() or cancelling ctx returns quickly. also add a test to ensure refresh bails when iter ctx is cancelled.

omar: API decision: keep Generator.Stream(ctx, ...) signature unchanged. expose (Stop() error) on the iterator interface. Implementation can create child ctx + cancel and close internal event chan on Stop.
