ada: quick sync - we've been seeing enqueue latency spikes in enrichment during load tests. thinking we need a formal deferred-enrich contract + backpressure policy.

omar: can you summarise the problem in one line? is this correctness or cost?

ada: one-liner: heavy enrichers (geo/db lookups) slow down ingest and cause big queues; either we block upstream (bad latency) or we accept large queues and delayed attribute resolution (bad for billing and alerts).

niki: agreed. we already do some async enrichment but the contract is fuzzy: how long can attributes be missing before it breaks downstream tooling?

priya: finance needs cost numbers ASAP. if enrichment resolves later, cost attribution shifts and dashboards show jumpy numbers. we need deterministic provisional buckets.

devops-bot: FYI: observed enrichment-queue depth reached 85% at 10k rps simulation at 03:12 UTC.

ada: proposal: define a Deferred-Enrich contract with 3 parts: (1) an ingress envelope with guaranteed core keys (request_id, tenant, route) and an enrich_token; (2) bounded async enrich queue with per-tenant quotas and a soft-deadline T_async (default 5s) after which enrichment is abandoned; (3) provisional attribution: when unresolved, metrics use token->provisional-bucket.

omar: what's the token? similar to cost-token discussed earlier? low-card hint?

niki: yes a small opaque token (sha1(route+tenant+shortstamp)) that maps to a coarse bucket. we store mapping when enrichment completes. prevents exploding cardinality.

priya: how do we reconcile dashboards? we need a window where provisional metrics are shown and then materialized ones replace them. ops needs both to audit.

ada: plan: the console shows a dual-series: provisional (near real-time) + reconciled (after enrichment). Reconciled data is the source-of-truth for billing. show a reconciliation lag histogram.

omar: edge case: if enrichment resolves to a different tenant (misroute), we must not charge wrong account. is that possible?

niki: only if request routing is wrong. but we should enforce tenant verification during enrichment resolution and drop mismatches with an alert.

priya: SLA question: we expose an ingestion P99 latency SLO of 200ms. Deferred enrich helps by moving heavy work out, but how do we ensure end-to-end observability SLOs (like trace completeness) for debugging?

ada: tradeoff: keep a small pre-enrich step (<50ms) to extract debug-level flags and critical attributes. Full enrichment is optional. For debug captures, we backpressure and do a sync enrich path (feature-flagged).

devops-bot: Note: sync-enrich feature-flag currently OFF for production; can enable for canaries.

omar: backpressure policy idea: allow bounded queue per-tenant with three outcomes when full: 1) drop non-critical enrich tasks (cheap), 2) degrade to token-only fallback, 3) shed oldest. Which do we prefer?

niki: prefer deterministic: if queue full, convert enrichment to token-only (no enrich) and emit a droppped_enrich counter. That keeps latency predictable.

priya: counters for dropped_enrich must be included in billing reconciliation so finance knows what's provisional.

ada: also add a circuit detector: if dropped_enrich rate > threshold (0.5%) for N minutes, trigger autoscale or open a fallback that routes to a high-capacity enrich pool.

omar: implementable details? where does the queue live? proxy? sidecar? central enrich service?

niki: suggestion: keep queue inside enrichment service (central), with a tiny acceptor at proxy that only enqueues a pointer. This avoids proxy memory blowup.

priya: will this change data retention? we might keep the original slim envelope for a short TTL until reconciliation finishes. need docs.

ada: yes TTL: envelope TTL = max(T_async + reconciliation_window, 1h) default 1h; sampled canonical traces unaffected.

omar: testing plan? load tests + reconciliation accuracy check. we should simulate long enrichment delays and verify provisional->reconciled mapping correctness under churn.
