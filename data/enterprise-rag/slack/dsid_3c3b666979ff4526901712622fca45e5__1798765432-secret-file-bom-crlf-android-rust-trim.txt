sam: yup, usually trailing newline or CRLF in the secret file. mounted secrets often have a final newline. do a quick hex check: `xxd -g 1 -u /run/secrets/API_KEY | head`

kevin: also watch out for BOM / zero-width chars if the secret was edited on windows. `file -b --mime-encoding /run/secrets/API_KEY` can hint, but hex is best.

linda: quick reproduce test — curl with header built from cat: `curl -H \"Authorization: Basic $(echo -n \"user:$(cat /run/secrets/API_KEY)\" | base64)\" https://api.redwood.example/v1/ping -v`  — if that works, it's client-side.

maria: i ran `cat /run/secrets/API_KEY | xxd` and saw `0a` at the end. so newline. but when i `echo -n` it still 401s from Android client.

sam: Android/Java clients sometimes base64-encode a string that accidentally includes the newline if you use `new String(Files.readAllBytes(path))` without `.trim()`. Also `BufferedReader.readLine()` removes newline but `read()` will not.

kevin: for Rust reqwest folks — common pitfall: `let key = std::fs::read_to_string("/run/secrets/API_KEY")?; let header = format!("Basic {}", base64::engine::general_purpose::STANDARD.encode(format!("{}:{}", username, key)));` If `key` contains `\n` you'll encode it. Use `let key = std::fs::read_to_string(path)?.trim_end_matches(["\n","\r"]).to_string();` or `trim()` before format.

linda: another gotcha: systemd units with `EnvironmentFile=/etc/myapp/secret` will include the newline in the variable value unless the file has `KEY=value` formatting. If you `ExecStart=/usr/bin/myapp` and then rely on `EnvironmentFile` with a bare file that is just the key, you can end up with weird whitespace. Best to mount as file and read+trim in app.

maria: thanks — i modified Android code: `String key = new String(Files.readAllBytes(secretPath), StandardCharsets.UTF_8).trim();` then build `Authorization` as `Basic Base64.getEncoder().encodeToString((username + ":" + key).getBytes(StandardCharsets.UTF_8))`. still 401 though.

sam: try verifying what the client actually sends. Use a local proxy (mitmproxy) or log the header with `log.d` (masking) to confirm no extra spaces. Also check URL-safe vs standard base64 mismatch — Java's `Base64.getUrlEncoder()` vs `getEncoder()` is easy to confuse.

maria: good call — turned on a short-lived proxy and saw header had an extra `\r` at end after trimming. seems the secret file had CRLF (0d 0a). my `trim()` removed only `\n`?

kevin: Java `.trim()` removes all whitespace incl `\r` I think, but if you're doing manual substring operations it can miss. On Android there's `String.trim()` which should drop `\r` too. Maybe the file contains a non-printing char (zero-width no-break space U+FEFF). run `xxd` and check `ef bb bf` for BOM.

maria: ran `xxd` — saw `ef bb bf 31 32 33 0d 0a` — BOM + CRLF. fixed by stripping BOM and CRLF in our deploy script: `sed -i '1s/^\xEF\xBB\xBF//' /run/secrets/API_KEY && tr -d '\r' < /run/secrets/API_KEY > /run/secrets/API_KEY.clean` then mount the clean file.
