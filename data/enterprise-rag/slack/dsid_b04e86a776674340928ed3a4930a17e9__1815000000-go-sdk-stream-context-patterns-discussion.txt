Alex: Quick heads-up — while running the Go sample generator streaming example I hit a cancel/leak issue. The sample uses a non-cancellable ctx and the loop never exits on SIGINT.

Alex: Minimal snippet from the sample app:
```go
func main() {
  ctx := context.Background()
  stream, _ := client.GeneratorStream(ctx, req)
  for tok := range stream {
    fmt.Print(tok.Text)
  }
}
```
This makes Ctrl+C not stop the program and we leak a goroutine. Repro: run sample, ctrl+c, check `ps` shows stuck process. gist with repro: https://gist.github.com/alex/repro-gen-stream-leak

Maya: I saw the same yesterday. Repro'd locally. The problem is the internal recv goroutine blocks on server Recv() and context cancel doesn't get wired into that call — so the goroutine never returns. :sob:

Sam: I think this is partly due to our GeneratorStream API ergonomics. Right now it exposes a plain channel/iterator-like flow which hides cancellation semantics. Two practical fixes: (A) return a Stream object with an explicit Close()/Err() contract (match net/http Body Close pattern), or (B) make Recv(ctx) explicit so cancellation is caller-driven. I prefer A for ergonomics.

Maya: +1 to Stream.Close(). Example suggestion:
```go
type GenStream interface {
  Recv() (Token, error)
  Close() error
}
// usage
ctx, cancel := context.WithCancel(context.Background())
stream, _ := client.GeneratorStream(ctx, req)
defer stream.Close()
for {
  tok, err := stream.Recv()
  if err != nil { break }
  fmt.Print(tok.Text)
}
```
That makes it explicit and avoids leaking if callers use defer.

Praveen: also flag: auth rotation + streaming is another edge. If the auth token refresh happens mid-stream we currently bubble a 401 and the stream code does a naive reconnect that races with Close(), leading to double-close panics in rare cases. We should make the stream retry/auth-refresh logic stream-aware (idempotent reconnect or backoff + explicit terminal errors).
