emma: repro summary: create vite react-ts app, install our SDK (local build), use `import Redwood from '@redwood/inference-js'` then build for SSR and run on worker/node. sophie: so default import -> interop wrapper problem. Does named import avoid it?

emma: yes, switching to `import { RedwoodClient } from '@redwood/inference-js'` bypasses the runtime flake. Looks like some bundlers transform the package into a CJS-shaped chunk so runtime code ends up calling an object instead of the function.

noah: quick matrix?

emma: tested locally:
- Vite dev server: OK (optimizeDeps keeps ESM)
- Vite build SSR -> edge: FAIL unless `ssr.noExternal` includes the package
- Rollup prod build: FAIL when commonjs plugin isn't configured for node_modules
- Webpack: older configs that treat node_modules as CJS fallback can hit it too

build-bot: CI flakiness: sample-app-edge-auth (#721) shows same 401/retry pattern in nightly runs.

sophie: immediate app workarounds?

emma: Workarounds we validated:
- Use named imports: `import { RedwoodClient } ...` (recommended)
- Vite: add `ssr: { noExternal: ['@redwood/inference-js'] }` in vite.config.ts or add to `optimizeDeps.include`
- Rollup: ensure `@rollup/plugin-commonjs` includes node_modules or mark package as external to preserve ESM entrypoint
- Webpack: enable .mjs handling / treat package as ESM in module.rules
- TS: as a last resort set `esModuleInterop: true` and `allowSyntheticDefaultImports: true` in tsconfig to quiet editor errors

noah: package-side fixes?

emma: proposed options:
1) add a tiny ESM-only entry (index.mjs) that re-exports named symbols (no default) so bundlers get a stable ESM shape
2) add conditional exports in package.json: { "import": "./dist/index.mjs", "require": "./dist/index.cjs" }
3) publish types for both entrypoints and avoid relying on a default export in the ESM entry
