mira: hey, hitting a weird intermittent 401 when using AsyncClient inside an anyio TaskGroup. looks like token refresh races across tasks. repro below.

mira: minimal pattern:
```py
from anyio import create_task_group
from redwood import AsyncClient

client = AsyncClient()  # shared at module scope

async def work(i):
    await client.generate("hello")  # sometimes 401 here

async def handler():
    async with create_task_group() as tg:
        for i in range(8):
            tg.start_soon(work, i)

# run under uvicorn (anyio)
```

mira: logs show one task does the refresh and gets a new token, others keep using the old cached token and hit 401, then all retry and hammer refresh endpoint.

mira: noticed it only happens when running with anyio/trio backend; not reproducible with plain asyncio loop.

kyle: hmmm. are you using contextvars inside the SDK to store the token? sounds like contextvar propagation across task groups might be part of this. :thinking:

mira: yes the SDK stores a token in a contextvar per-client to avoid global state. i assumed anyio would preserve contextvars between parent and child tasks, but maybe task group does something odd with trio?

jess: anyio/trio have different semantics for contextvar copies, especially if a task is started from a different thread or an anyio worker. but usually contextvars should propagate to child tasks at start. do you have a tiny log of token ids?

mira: pasted snippet from logs:
```
[1723456792] task=3 token=tok_abc (valid)
[1723456792] task=5 token=tok_abc (401 -> refresh started)
[1723456793] task=3 token=tok_def (got refreshed by task 5)
[1723456793] task=5 token=tok_def (continuing request but still 401)
```

mira: looks like task 3 sees the new token nearly immediately, but its in-flight request still fails (maybe token changed mid-request on server?)

kyle: what does your retry logic look like? is the SDK doing an automatic refresh + retry inside the same request context? race there could cause double refreshes.

mira: SDK flow: on 401, attempt refresh (async, acquires a small in-process mutex per-client), update contextvar token, then retry original request. i thought mutex should prevent concurrent refreshes, but it seems multiple tasks enter refresh path.

jess: ah — contextvar + async mutex interplay can be surprising. if the mutex instance is stored in a contextvar, different tasks might have different copies, so the lock isn't shared. is the client storing the lock on the contextvar too?

mira: god no, the lock is an attribute on the AsyncClient instance (self._refresh_lock = anyio.Lock()). token is in contextvar.

jess: ok. then maybe what's happening is: both tasks detect 401 and both await the same lock, but the token used for the failing request was captured earlier (header already built). task 1 acquires lock, refreshes token, updates contextvar, releases lock. task 2 then refreshes too because it still thinks token is invalid (it re-runs its refresh logic since it still sees the prior 401). result: double refreshes and a brief window where some requests used old token.

kyle: that sounds plausible. two related mitigations: 1) ensure the check+refresh is done under the same lock (i.e., after acquiring the lock, re-check token value to see if someone else already refreshed), 2) avoid using contextvar for the token when you have a shared client object — store token on the client instance and make header-building read that attribute under a lock.

mira: i can try (1) quickly. currently code is:
```py
async def request(...):
    resp = await do_request()
    if resp.status == 401:
        async with self._refresh_lock:
            await self._refresh_token()
        return await do_request()
```

mira: so we refresh unconditionally once we win the lock. we don't re-check after getting the lock whether the token changed already.

jess: change to:
```py
if resp.status == 401:
    async with self._refresh_lock:
        if token_matches_header():
            await self._refresh_token()
    return await do_request()
```

jess: i.e., after acquiring the lock, check whether the header/token used by the original request still matches current token; if not, skip refresh because someone else already did it.

kyle: ^ that's the classic double-check. also consider making token storage consistent: either keep token on the client instance (self._token) and use contextvars only for per-request overrides, or keep everything in contextvars but ensure refresh lock is also in shared instance. mixing can bite.

mira: oh — side note: when i switched uvicorn to asyncio backend (--loop asyncio) the repro disappeared. that matches anyio/trio scheduling amplifying the race.
