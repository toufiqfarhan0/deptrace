naveen: quick sync — following the CP separation RFC: idea to run short-lived regional anchors (minutes->hours) to reduce single-point-of-failure and enable faster maintenance. thoughts?
linda: I like the smaller blast radius. main concern is how control-plane identity and certs move during anchor churn (esp private installs).
raj: we could keep a long-lived signing service in the global controlplane and issue short-lived leaf certs for anchors. anchor rotates, gets new leaf cert from signer. no secret movement.
olga: signing service = good. but private installs may not be able to reach global signer. need an air-gapped fallback (local signer or offline-signed bundle).
raj: yes — offline bundle approach: periodically generate anchor cert bundles that customers upload. bundles expire after N hours. ops can push new bundles for scheduled rotations.
linda: discovery options: SRV, small regional registry endpoint, or consul-style gossip. SRV is simplest for hosted. private should allow local registry file or environment override.
naveen: agreed. propose discovery order: explicit env override (admin), local registry (file/socket), SRV/registry, fallback to global. clients should respect short timeouts for local and slightly longer for registry.
raj: client contract suggestion: try local registry 50ms, SRV 150ms, global 500ms. if registry returns multiple anchors prefer same AZ, then region, then cross-region.
olga: streaming implications: long-lived streams require reconnect semantics that preserve incremental KV syncs. plan: keep session IDs and allow resumption to pick up KV window. if resumption fails, fallback to cold bootstrap.
linda: how do we avoid double-writing during failover for writes to prefix cache? we need a leader handoff signal — anchor publishes "handoff" window where writes are redirected to both old+new for X seconds.
naveen: leader handoff window is sensible. ops surface must expose states: active, draining, standby, maintenance. infra-bot should emit events when anchors flip. infra-bot: anchor us-east-1 rotated -> new-id=b3f9, state=draining
raj: metric needs: handoff_duration, cache_warmup_bytes, anchor_failover_count, stream_resume_success_rate. add a tracing tag with anchor_id for debugging.
olga: cache warmup: prefer prioritized streaming of hot prefixes. we should provide a prewarm API on anchors: /v1/prefetch?prefixes=... which is authenticated and rate-limited. for private installs, prewarm could run from on-prem agents.
naveen: bandwidth model: warmup of top-100 prefixes ~ 20MB per anchor for medium customers. maria (cc) should validate with actual cluster telemetry.
linda: ops: allow manual force-cutover with option to block writes for 30s to ensure consistency for critical customers. document risk.
raj: SDKs should surface sticky session tokens that bind to anchor_id and expire. servers validate sticky token to allow connection re-use. revoke tokens on handoff.
olga: also add a graceful drain probe: /healthz?drain=true that returns 200 until active connections drop below threshold then returns 503. that lets LB automation move traffic safely.
