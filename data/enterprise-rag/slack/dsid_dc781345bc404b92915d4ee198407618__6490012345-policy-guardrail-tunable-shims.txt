maria: heads-up — after yesterday's load test the routing policy kept sending low-cost models to a latency-sensitive tenant. we need a guardrail layer of tunables to prevent cost-first choices from violating per-tenant latency SLOs.

jason: ugh. saw that. where do you want the tunables to live? policy graph, runtime flags, or tenant config?

maria: high-level: configurable penalties/overrides that can be evaluated quickly at the router. should be editable without a full policy recompile. want both global defaults and per-tenant overrides.

tian: so a two-tier approach: compile-time defaults baked into the policy for fast eval, plus a hot-reloadable tunables blob that the router checks before final scoring. sounds ok.

oliver: careful — making the runtime check too heavy kills tail latency. we should keep the hot tunables to < 1 additional lookup and simple arithmetic. no JS or Wasm in the per-request path.

maria: agreed. plan: store tunables as a small protobuf with a version hash; apply via config CDN + in-memory watch. router logic: on match, apply precomputed delta_score from tunables then continue normal scoring.

jason: can you sketch the tunable schema? example fields?

maria: draft: 

```
message Tunables {
  string id = 1; // version
  repeated TenantRule tenant_rules = 2;
}
message TenantRule {
  string tenant_id = 1; // '*' for global
  double latency_penalty_ms = 2; // convert to score delta by function
  double cost_bonus = 3; // negative reduces penalty for cheaper models
  bool force_region = 4; // optional region tag
  int64 expires_at = 5; // epoch
}
```

tian: converting latency_penalty_ms to a score delta needs a deterministic function so behavior is unit-testable. e.g. delta = sigmoid((observed - target)/scale) * weight. keep the function in runtime lib.

jason: and we need to guarantee monotonicity so tenants can't create non-intuitive flips. add docstrings and unit tests.

oliver: question: how do we reconcile tunables with existing policy penalties? precedence rules are critical. proposal: tunables apply after policy graph scores but before tie-breakers. tunables can only increase latency penalties beyond a max floor set in compile-time policy (compile-time floor <= tunable).

maria: good call. also add an emergency override: the operator can set a hard-sla mask that short-circuits to region/priority variants for specific tenant IDs (useful during incidents).

jason: ops will want audit logs. every application of a tunable should emit an event: {tenant, tunable_id, model, delta_applied, reason}. store in event-store and surface in console.

tian: telemetry: we should measure pre-tunable score, post-tunable score, and final decision. tag traces so we can query: "requests where tunable moved decision to higher-cost model".

oliver: safeties: 1) limit tunable churn rate (reject > N updates/min per tenant), 2) require signed tunables for private deployments, 3) TTL/expires to prevent stale sticky overrides.

maria: long-term: if this pattern stabilizes, we can move simple tunables into the policy DSL as an explicit first-class concept (less indirection). for now keep as separate blob for faster iteration.
