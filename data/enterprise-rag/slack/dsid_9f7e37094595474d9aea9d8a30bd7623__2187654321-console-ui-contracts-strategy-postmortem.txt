Jonathan Park: Quick follow-up from the UI/Query composition RFC — we need to decide where RBAC gates live for panel-level filtering. Do we push down authz to the query router or keep it as a post-filter in the console?
Maya Singh: My leaning is pushdown when we can. Filtering earlier avoids expensive fetches + reduces telemetry noise. But it complicates the router API.
Priya Raman: Pushdown is better for cost, but we must preserve the same audit trail. If router filters, we need hook to emit decision logs for audit and SLOs.
Sam B.: Concern: pushdown increases coupling between query layer and auth model. Any schema changes in RBAC means router deploys. How do we avoid churn?
Maya Singh: Option: thin policy API + stable 'allowed-ids' contract. Authz service computes allowed view keys per user; router accepts list and applies WHERE tenant_id IN (...) or pre-filter.
Jonathan Park: That helps. Tradeoffs: 1) extra roundtrip to auth service 2) potential for long IN lists. Could use tenant-ACL cache with TTL.
Priya Raman: For long lists use a temporary allowlist table in the router DB (populated by auth service) so queries can join on ephemeral token. Keeps SQL sane.
Sam B.: Agree. Also need to decide materialization surface: some panels rely on pre-aggregated projections. If router filters, those projections need tenant-aware partitioning.
Maya Singh: Proposal: migration plan
- Phase 0: keep post-filter approach, add decision logging
- Phase 1: implement authz service endpoint v2 that returns allowlist token
- Phase 2: router supports allowlist token join and pushes filter
- Phase 3: migrate projections to tenant-partitioned views and enable per-panel pushdown
Jonathan Park: Rollout controls: feature-flag per-tenant + canary group. For canary we should run shadow queries with pushdown enabled and compare result diffs.
