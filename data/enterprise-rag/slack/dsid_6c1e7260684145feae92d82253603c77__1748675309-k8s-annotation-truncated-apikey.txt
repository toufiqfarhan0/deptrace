lee: hmm. We had a k8s manifest change that moved the API key into a pod annotation for easier rollout (annotation: `redwood.com/api-key`). Kubernetes annotations have size limits and tooling sometimes truncates long values when writing to etcd. @deploy-bot can you show the recent rollout events for acme-connector?

deploy-bot: Deployment acme-connector v2.3.1 rolled at 2025-11-03T18:12Z. Applied patch: set metadata.annotations.redwood.com/api-key -> (value length 324). Warning: annotation value truncated to 256 chars by apiserver.

sunil: bingo. If the annotation was truncated at write time, the running pod would see a truncated key, and the client would be sending that truncated value to our API. That explains the short hex dump.

lee: To confirm: can ops re-fetch the annotation on a running pod? `kubectl get pod acme-connector-... -o jsonpath='{.metadata.annotations.redwood.com/api-key}' | wc -c`

marta: ops ran it and returned `256`. Their expected key length is 324.

sunil: Root cause: using pod annotations for secrets. Annotations are limited (apiserver/enforced), and some apiservers silently truncate. We should never store secrets there.

lee: Action plan: 1) Rollback annotation change for ACME connector and redeploy with the API key loaded from a Kubernetes Secret (mounted env var). 2) Notify customer and provide temporary test key. 3) Add validation in our deploy tooling to reject annotation > 200 chars for keys.

marta: Customer accepted a temporary test key, patched connector to use a mounted secret, redeployed and confirmed success:
