anya: quick follow-up to the GQ/MQ RFC — we ran microbenchmarks across 3 representative workloads (chatty dialog, long-context summarization, retrieval-heavy RAG). TL;DR: different kernels win on different slices, we need a simple heuristic + safe fallback for the runtime before we build a full policy engine.

sam: can you paste the top numbers? short bullets please.

anya: sure. high-level: 1) chatty dialog (many short queries per sample) -> MQ wins for throughput (up to 18% tokens/s) and slightly better tail on A100. 2) long single-query sequences -> GQ has lower memory and slightly lower latency for single-query decode (P50). 3) mixed workloads (RAG) -> hybrid runs best when we route short-query calls to MQ and long context to GQ; batching interactions matter.

priya: did you vary kv-cache hit rate? that often flips the result.

anya: yes — we included cache-hit 0%, 50%, 90%. MQ advantage shrinks when cache hit high because MQ's extra per-query overhead amortizes less. put simply: if kv-cache_hit_rate >= 0.8 and avg_queries_per_request <= 1.2 -> prefer GQ.

matt: do we have a compact heuristic we can ship quickly? we should avoid inspector-level decisions in each call.

anya: proposal (pseudocode):
```
# decision inputs: avg_queries, seq_len, cache_hit, head_count, hardware_label
if avg_queries > 1.5 and hardware_label in ["A100","H100"]:
    decision = "MQ"
elif seq_len > 2048 or cache_hit >= 0.8:
    decision = "GQ"
else:
    decision = "GQ"  # default to lower-memory kernel
# fallback: if chosen kernel fails (OOM or kernel not loaded) -> fallback to compatible variant with reason tag
```

lee: hardware_label check worries me for Dedicated/private customers who have mixed fleets. we should make hardware-agnostic defaults and allow overrides.

priya: agree. maybe a per-deployment capability vector: {supports_mq, supports_gq, max_seq_len, quantized_kernels}. runtime reads that once and uses it to clamp the heuristic.

sam: we need an interface boundary here. runtime currently just picks a kernel internally. propose we extend the kernel selection API to return: `{attention_mode: "GQ"|"MQ"|"HYBRID", reason: "avg_queries>1.5", profile_tag: "v1"}`. callers (compiler/loader) can then log and enforce fallbacks.

anya: yes — minimal schema makes metrics + AB testing easier. also add a small numeric confidence score so we can route canaries.

matt: what about continuous batching? if a batch mixes short and long queries, do we split the batch and run two kernels? cost and latency tradeoffs.

priya: we should allow batch-splitting when imbalance > threshold (e.g., >30% long samples). Splitting costs extra enqueuing but avoids worst-case tail. Add heuristic: batch_split = (stddev(seq_len)/mean(seq_len)) > 0.35.

lee: note: splitting may defeat prefix caching because fragments decode in different order. need to ensure KV cache keys still align.

anya: good catch — we need to keep ordering guarantees: when splitting, dispatch parts to kernels but preserve request-level ordering and merge KVs back. This is doable but non-trivial; flagging as medium-term refactor.

sam: failure modes? OOM, kernel not compiled, quantized kernel mismatch. Fallback strategy should be: 1) try chosen kernel; 2) if OOM -> reduce batch or switch to GQ; 3) if kernel absent -> load fallback or use interpreter path (slower). Log reason codes.
