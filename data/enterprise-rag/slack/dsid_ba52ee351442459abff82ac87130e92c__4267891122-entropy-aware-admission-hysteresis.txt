liz: quick sync: i'm prototyping an 'entropy-aware admission' patch to reduce oscillation when continuous-batcher faces heterogeneous tenant mixes. goal: smooth admission decisions so small bursts don't trigger global reshuffles.
omar: can you explain entropy here? high-level term mapping for the team pls.
liz: sure. entropy = diversity score of incoming request sizes + deadlines over a short window. when entropy spikes, admission gains a hysteresis term so we avoid aggressive lane reshaping.
diego: how does that interact with the current admission credit model? we already have per-tenant credits and soft preemption.
liz: two layers: keep per-tenant credits. add admission_hysteresis in the allocator which multiplies the threshold for opening new micro-lanes or triggering preemptions. pseudo-config:

```
entropy_admission {
  window_ms: 250
  entropy_threshold: 0.35
  hysteresis_mult: 1.8
  max_hysteresis_ms: 200
  enable_shadow: true
}
```

pri: telemetry hooks? need things to debug when we see regressions.

liz: planned metrics: entropy_score, hysteresis_applied{true|false}, admissions_blocked_by_hysteresis, lane_open_events, per-tenant admission_delay_ms_sampled. also add trace tag: X-Admission-Hysteresis when admission delays exceed 5ms.
omar: sequence and kv-cache concerns? delaying admission could hurt prefix locality or extend kv-cache retention windows.
diego: plus longer in-queue time increases chance of tail latency. how do we bound impact?
liz: the hysteresis is conservative: it only raises the admission threshold for opening new lanes (so we pack more) and caps the additional delay per-request to max_hysteresis_ms. important: it won27t preempt already-allocated slots.
pri: rollout plan?
liz: shadow first for 24h on a replica pool, then 5% -> 25% -> 100% over 10 days. automatic rollback if per-tenant p99 increases >12% for 10m or entropy_score stays > threshold for >1h.
omar: how do adapters see this? they read slab ids and deadlines; will we add headers?
liz: we add two headers: X-Admission-Delay-ms (0 if none) and X-Admission-Entropy-Score. adapters that need strict locality can opt-out with route config allow_entropy=false. default keep compatibility.
diego: edge case: when a single tenant dominates with low entropy, hysteresis shouldn't block opening lanes for that tenant. is there per-tenant override?
liz: yes, we compute both global_entropy and tenant_entropy. hysteresis applies only if global_entropy > threshold AND tenant_entropy < 0.9*global_entropy. basically avoid hurting dominated workloads.
pri: what about cost tradeoffs? packing better reduces GPU kernel launch overhead, but could increase token latency for some queries. need cost delta estimate in PR.
liz: i ran microbench sims: median token cost down ~6% on mixed traces; p50 latency unchanged, p99 increases ~3-5% for small fraction of tenants. will include the sim code.
omar: provide failure mode plan. if we see degraded tail while entropy is low/high, what's the kill-switch?
liz: config kill-switch admission_hysteresis.enabled=false. also fast-roll-back rule: if cluster_p99_penalty >10% for 3m, autoset disabled. ci-bot: can we add an automated perf job that runs the mixed-workload replay nightly?

pri: how does this interact with existing tilt/steer ideas? might be orthogonal but could mask other optimizations.
liz: true. note in RFC follow-up: order of ops matters. entropy-hysteresis runs before lane-steering and before slab-tilt. decisions are best-effort hints; downstream rebalancers still allowed to move requests but will see hysteresis tags and be more conservative.
diego: what about fairness? If hysteresis increases packing, we may delay tiny tenants behind large ones. ensure tenant-weight preserved.
liz: admission maintains fair_share invariants; hysteresis can't reduce allocated credits below min_guarantee. config example:

```
admission_defaults {
  min_guarantee_tokens_per_sec: 50
  hysteresis_min_respect: true
}
```
