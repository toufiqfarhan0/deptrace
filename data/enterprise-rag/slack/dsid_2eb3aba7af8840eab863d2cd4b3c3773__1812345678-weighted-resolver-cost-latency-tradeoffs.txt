alex: quick follow-up from the weighted-resolver RFC — want to propose a simpler runtime path to cut per-request CPU and reduce p95. idea: precompute tenant-weighted buckets (tiny set) and do a cheap resolver at request time, only falling back to full scoring in ambiguous cases.

maria: sounds sensible. how would region failover work? if eu region has outage we need deterministic behavior that doesn't violate cost budgets.

kevin: two-tier approach IMO: 1) prefilter by hard constraints (region, tier, model compatibility) 2) weighted-bucket resolver using precomputed weights 3) full score eval only when bucket scores are within delta. priority: for enterprise tier we treat latency SLO > cost; for free tier cost > latency.

sasha: ops ask that the resolver emits decision_reason and candidate_snapshot_id. without snapshot id it's impossible to map telemetry to policy versions during rollouts. also include estimated_latency and estimated_cost in telemetry.

jun: rough example config to discuss (pseudo):

```
policy {
  buckets: ["fast","cheap"]
  weights: {"fast":0.7, "cheap":0.3}
  hard_constraints: {region: ["us","eu"]}
  overrides: {region: {"eu": "cheap"}}
}
```

liz: runtime caching idea: cache resolver decisions for 10s keyed by (tenant, model, region, prefix_hash) with LRU eviction. should drastically reduce eval QPS.

alex: caveat: caching by prefix_hash can mask transient latency issues for small interactive sessions. maybe bypass cache for first N requests per session or sample 1% to measure real p95 and invalidate if mismatch.

maria: we also need atomic hot-reload for policy snapshots: apply new snapshot atomically and keep previous for rollback. add snapshot_id to cache key so rollout doesn't reuse stale decisions.

kevin: tradeoffs recap: per-request scoring = optimal route selection but adds ~5-8ms p95 overhead (and CPU). precompute+cache = much better p95 but more occasional suboptimal selections that cost slightly more tokens or route to a higher-cost instance. we need SLO-driven selection: if request has tight latency SLO, prefer precomputed fast bucket; if cost-sensitive and relaxed latency, prefer cheap bucket.

sasha: telemetry schema request: resolver_decision {route_id, version_id, candidate_snapshot_id, decision_reason, estimated_cost, estimated_latency, resolver_type}. plus summary counters: resolver_misses, resolver_evictions, fallback_count.

jun: proposed runtime API boundary for resolver: resolver.resolve(request_meta) -> {route_id, metadata_reason, version_id, estimated_cost, estimated_latency}. runtime should treat that blob as opaque beyond route_id and estimated metrics. no runtime-level scoring logic.

alex: agreed. keep resolver contract small. add explicit fallback chain in contract: route -> region_fallback -> tier_fallback -> default_model. runtime should implement fallback chain semantics, not the policy DSL.

liz: about model rollouts: when model variant changes, invalidate cached decisions for affected model+tenant+prefix combos. candidate_snapshot_id in cache key, per maria. also add a short TTL (10s) to avoid long-lived staleness.

maria: security note: policy snapshots should be signed and verified by runtime before applying. audits need consistent snapshot ids.
