kenji (eng): main concerns: cost amplification (duplicate tokens), correctness (dedupe on server), and observability. If we race two full requests we could double token spend. We need a telemetry plan to measure wasted tokens and a server-side idempotency/dedupe story.

samir (sdk): API sketch — keeping the simple path tiny and advanced path explicit: 
```js
// simple (90% case)
await client.generate(prompt, { timeoutMs: 300 });

// advanced (opt-in)
await client.generate(prompt, {
  timeoutMs: 300,              // total deadline for the call
  phaseDeadlines: { connect: 50, firstByte: 200 },
  hedging: { replicas: 2, strategy: "race", minStaggerMs: 20 },
  retry: { maxAttempts: 1 }     // explicit: hedging disables extra client retries by default
});
```
Notes: default SDK behavior is backward compatible (no hedging). For streaming, hedging only races until first chunk (firstByte) and then cancels other inflight branches. Using AbortController for cancellation.

maria (PM): Draft acceptance criteria (please review):
```
- API: top-level `timeoutMs` exists. Optional `hedging` object for advanced users.
- Backwards compatible: default behavior unchanged.
- Retries interaction: hedging enabled => client retries limited (document exact policy).
- Streaming: hedging races only until first chunk; SDK cancels losers cleanly.
- Server: supports hedging dedupe + billing attribution header.
- Metrics: p50/p95 latency delta, tokens consumed per logical request, hedged request ratio, hedging-success-rate (winner reduces latency).
- Tests: unit tests for cancellation/abort, integration with runtime mocking delayed replicas, e2e with sample app.
- Docs: migration + examples for JS/Python + pattern guide.
- Launch criteria: opt-in customers show p95 improvement >= 20% with <=5% token overhead on average; no data-loss or ordering regressions in streaming.
```
