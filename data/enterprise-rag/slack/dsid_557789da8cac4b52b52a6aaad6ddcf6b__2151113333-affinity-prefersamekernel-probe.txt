alex: Quick follow-up from the GQA/MQA kernel selection RFC — found a case where grouped-query lanes with partial KV overlap get routed to different kernels and thrash the KV cache. Proposal: add an 'affinity_score' hint to the kernel selector and a simple threshold to prefer same-kernel placement when overlap > X.

mira: Can you paste the micro-traffic example? :thinking:

alex: Sure — imagine two queries A,B where A shares ~70% KV keys with B. If the selector treats them independently the small-batch path wins and we pay repeated decode + cache warmups. Load test snapshot: p50 token latency 2x, GPU memory churn 1.4x for those flows.

sam: Hmm. Is overlap computed on query text or tokenized KV cache keys? We should avoid expensive compute on the hot path.

alex: Good call. Plan: compute overlap in the query-collector stage using hashed-key sketches (Bloom/Count-Min). The sketch is updated off the critical path; the selector reads a precomputed pairwise affinity score. Pseudocode:
```
affinity = sketch.similarity(q1.sketch, q2.sketch)
if affinity > 0.6 and cost_delta < 1.2:
    prefer_same_kernel()
```

mira: Where does cost_delta come from?

alex: From the kernel cost model table — we already keep per-kernel profiles (latency_per_token, mem_pressure, quant_support). We estimate token_cost_ratio between candidate kernels.

jamal: Two concerns: (1) correctness when one query requires a quantized kernel and the other expects FP32, (2) tail-latency risk if we force same-kernel placement and it adds queuing.

sam: For (1) only apply affinity when the intersection of compatible feature-sets is non-empty (e.g., both support Q4/kv-accel). For (2) cap the extra queuing with an early-exit: if queue_time_estimate > tail_threshold then fall back to normal selection.

alex: Agreed. Also propose a soft mode: 'soft_affinity' where selector prefers same-kernel but will not break SLOs; this can be controlled via customer routing policy and a global feature flag.
