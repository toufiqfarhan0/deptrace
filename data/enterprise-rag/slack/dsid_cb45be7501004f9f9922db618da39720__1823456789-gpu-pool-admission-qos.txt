Raj: Short version: accounting now computes an "effective_tokens" that adds kv and reservation overhead. Formula we used during rollout: 
```
effective_tokens = tokens_in + tokens_out + ceil(kv_hits/16)*16 + (reserved_gb * 8)
per_gpu_tpm_capacity = floor(gpu_token_rate / effective_tokens)
```
Mike: That reserved_gb*8 term was added to model streaming to prevent noisy small requests from starving memory. It effectively charges a flat token cost per request which bumps low-token requests a lot.
Sophia: Right — if batch_size drops, avg tokens per request falls but the per-request reservation stays constant, so accounted TPM goes down even though observed per-token throughput didn't.
Ada: Ok, makes sense. For admission control we should treat reservation as a request-level fixed cost and batching as an amortized token cost. Proposal:
- compute per-GPU available_token_budget = static_gpu_budget - sum(active_reservations)
- maintain EWMA of avg_tokens_per_request per route/pool
- admission check: if (projected_tokens + reservation_costs) > budget -> queue or apply backpressure
Config sketch:
```
admission:
  window: 30s
  ewma_alpha: 0.2
  reserve_per_request_gb: 4
  backlog_high: 200
```
Raj: Also call out the RPM vs TPM mismatch — throttling purely on TPM can still allow too many concurrent short requests (high RPM) and blow out request slots / scheduling overhead. We need a dual-threshold: tokens AND requests.
Mike: +1. Dual-threshold admission: require both token_budget check and request_slot check. If tokens ok but request_slots exhausted -> queue. If request_slots ok but token_budget exceeded -> reject or degrade model variant.
