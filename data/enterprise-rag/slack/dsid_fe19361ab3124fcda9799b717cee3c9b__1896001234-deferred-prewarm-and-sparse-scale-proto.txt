alex: Quick follow-up on yesterday's allocator chat — thinking about a "deferred prewarm" + "sparse shared warmers" approach to reduce churn and cost for low-throughput tenants. Sketch below, want quick sanity-checks.

maya: quick summary? not sure I caught the whole thread.

alex: TL;DR: instead of prewarming N workers on every tenant quota change, we keep a deterministic min_warm_per_tenant (small, e.g., 1) and a separate shared_sparse pool that can be probabilistically used to serve bursts. If a tenant hits cold, we either route to a shared warmer or kick an async prewarm depending on SLO.

jordan: probabilistic shared pool sounds nice but worried about fairness. tiny tenants could get starved by noisy neighbors.

alex: agreed — hybrid model: deterministic reservation + shared pool. fairness via admission tokens and per-tenant weight. eviction order: tenant-reserved nodes > shared nodes (LRU-ish) > idle.

sam: what are the admission signals? we need to avoid a prewarm thundering herd when multiple requests miss simultaneously.

alex: plan is to gate prewarm with two signals: short-term arrival spike (p95 over 1m) and model hotness (recent kv-cache hits, seq length distribution). Use a cooldown window per-tenant so we don't prewarm repeatedly. Also prefer async background prewarm for non-latency-critical routes.

maya: can you show a minimal config proto?

alex: sure, rough YAML: 
```
prewarm_policy:
  mode: hybrid             # deterministic + shared
  min_warm_per_tenant: 1
  shared_sparse_size: 8   # total shared warm workers for the cluster
  trigger_rate_per_worker: 20 # rps threshold
  cooldown: 30s
  fallback_model: "lite-1.0"
  isolation: partial      # values: full|partial (namespace kv handling)
```

jordan: nice. A couple tradeoffs: shared_sparse_size should be per-region and per-hardware-class. otherwise cross-arch mismatches. Also need graceful fallback when shared pool exhausted (route to smaller model or queue with short timeout).

sam: another ops concern — KV cache pollution if shared workers reuse tenant caches. If we do partial isolation, we need ephemeral KV namespaces and a fast warm-merge strategy for tenants that end up owning a shared worker. That adds complexity.

alex: yes — proposal: shared workers start with ephemeral empty cache; on warm-to-dedicated transition, we do a fast KV prefetch of top-k prefixes from async store. That keeps steady-state cost low.

maya: billing & observability: we need to tag usage as reserved vs shared vs fallback so customers can see effective cost/latency. Also tracing to link request -> warming decision.

alex: agreed — we'll attach tags: warm_type={reserved,shared,fallback}, prewarm_trigger={arrival,kv_hotness,manual}.
