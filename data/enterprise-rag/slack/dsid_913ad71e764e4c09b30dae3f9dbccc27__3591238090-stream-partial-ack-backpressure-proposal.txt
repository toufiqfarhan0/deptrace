Anya: Quick brain-dump — we need a proposal for supporting partial streaming responses with safe retries. Today the gateway either buffers the entire stream for a retry or just fails midstream. Looking for tradeoffs and an actionable plan.

Jonathan: +1. Two axes to consider: memory footprint (how much we buffer) vs client-visible resume/idempotency. Broad options: chunk-level ACKs, resume tokens, or server-side checkpoints. cc @Kevin :thinking:

Kevin: Chunk ACKs reduce server bookkeeping (you only need to track last-acked chunk) but they force protocol changes and more fragile reconnection logic. Resume-token approach pushes complexity to token issuance/validation and either requires state (KV) or a signed stateless token. Tradeoffs: GC, token TTL, and replay protection.

Maria: If we go stateless tokens we could keep them compact (<1kb) and encode model provenance + offset + signature. That avoids needing a KV store but may not represent ephemeral runtime state like KV cache.

Dave: Exactly — stateless tokens don't capture ephemeral KV cache (e.g., attention/kvcache snapshots). Resuming a generation might need that state or force a expensive restart from the beginning which changes output and latency.

Anya: Proposed hybrid: keep a short-lived ring buffer on the edge for recent bytes (N seconds / M KB). Issue resume-tokens that are valid for that window. If the token is used after expiry, fall back to a model restart path (explicitly billed & signaled). This keeps usual paths cheap and handles most transient network issues.

Jonathan: Also we need backpressure signals. If a client is slow we shouldn't buffer unboundedly. Plan: per-connection memory budget + admission control. When budget exceeded, try converting the session to a checkpoint-only mode (persist minimal resume data) and drop live buffer; if that isn't possible, respond with 429 or tear down according to SLO.

Kevin: Prototype header names and example usage:

```

# Server indicates window size
HTTP/1.1 206 Partial Content
X-Stream-Window: 30s
```

Maria: We should also explicitly specify retry semantics: idempotent vs non-idempotent operations. For tool-calls and side-effectful completions, retries must be blocked unless client provides explicit compensation strategy. Add `X-Idempotent: true|false` header; default false for tool-enabled chats.
