alice: Quick question — when a Dedicated tenant runs out of reserved GPUs and we spill to Hosted, do we preserve the tenant's model variant preference (e.g. fp16 vs quant) or can Hosted pick a cheaper variant automatically? This is a mix of legal/isolation + QoE tradeoffs.
ben: Short answer: policy currently _allows_ variant fallback in the runtime, but contract language for some Enterprise tenants forbids substitution. We need an explicit policy that the Console/API surfaces.
carla: If a contract forbids substitution we should reject the request rather than route it to Hosted. Alternatively we can offer an opt-in toggle in the Console: "allow hosted variant fallback" with audit.
dave: From the runtime side: Hosted pools don't necessarily have the exact fp16 builds for every model variant we run in Dedicated. Fallback helps avoid OOMs. Technically we can gate fallback by a compatibility matrix (semantic/eval parity) so only "safe" substitutes are used.
sam_pm: Product preference: conservative default. Reject by default for Dedicated -> Hosted routing unless tenant explicitly opts in via Console. When they opt in, show the expected quality delta and cost delta.
ops_jasmin: Telemetry/SRE ask: every routed request must be tagged with route_origin and variant_chosen so we can trace SLA regressions back to fallback events. Also we need metrics for fallback counts and latencies.
infra-bot: current route header: x-rw-routing: {tier:dedicated|hosted, region, variant_hint}. Proposal: add fields fallback_reason and consent_token.
telemetry-bot: We'll add metrics: routing.fallback.count, routing.fallback.latency.p50/p95 and tags: tenant_id, consent_token, variant_from, variant_to. Also dashboard panels for QoE regressions by tenant.
