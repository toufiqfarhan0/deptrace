maya: FYI onboarding run failed on the HF->Redwood chat_template conversion for a multilingual Jinja template. repro attached in thread.
sam: quick summary?
maya: We have a template with a choice block used to localize system instructions. Example:

```
{% if locale == 'ja' %}
- role: system
  content: "日本語のシステム指示: {{ instruction }}"
{% else %}
- role: system
  content: "English system instruction: {{ instruction }}"
{% endif %}
```

The converter is flattening the blocks but also inserting the sentinel token twice at the boundary: `\u0001<|system|>` gets split across tokens by the model tokenizer (after quantization), causing the runtime to treat it as plain user text and merge the system role into assistant messages.

kai: hmm. Do you have a small reproducer? Which tokenizer/config are we using?
maya: Using the model repo's `tokenizer.json` + config.json. Notably, config.json has `add_bos=true` and a custom `special_tokens_map` that defines `<|system|>` and `<|assistant|>` as single tokens. But after applying our HF->Redwood conversion pipeline + Jieba-like locale preprocessing, the byte sequence gets a ZWJ inserted for Japanese punctuation normalization. That ZWJ changes byte alignment and in int8 quantized runs the tokenizer splits the special token into two tokens.

olivia: So it's a combination of: template whitespace/locale normalization, conversion engine inserting/normalizing whitespace, and quantized tokenizer fragility. Any eval impact measured?
maya: Yes — ran the standard chat-localization eval (chat-multi-locale-eval v2) across 2000 examples. On fp16 baseline the system role preserved and rouge-like score stable. On int8 quantized candidate we saw a ~2.7% drop in instruction-following score and a spike in user-visible role-bleed examples.

sam: Do we know if this is purely tokenizer split or also the converter adding/removing sentinel escapes?
kai: I inspected the converter output. Before tokenization we generate:

```
<|system|> 日本語のシステム指示: ...
```

But after the locale normalizer (we call `render_locale_text`) it returns a string where the first byte of the sentinel becomes a combining char (0xE3 0x80) due to a stray normalization we added for TRIM rules. So tokenizer's byte-level matcher doesn't hit the special token table and falls back to subword pieces.

olivia: Temporary mitigation ideas?
maya: Patch 1: in HF->Redwood conversion, mark special tokens with U+FEFF (zero-width no-break space) wrapper at generation time so they survive normalization: e.g. `\uFEFF<|system|>\uFEFF`. Patch 2: update our quantized tokenizers to include fallback entries for common broken splits (nasty but fast patch). Patch 3: upstream fix — ensure locale normalizer runs after sentinel injection and avoid Unicode normalization forms that change byte sequences.

sam: Which patch did you try first?
maya: Tried Patch 1 on a small subset — it reduces role-bleed from 0.9% -> 0.1% on int8 runs. But it's hacky and may break downstream token counting/cost accounting.
