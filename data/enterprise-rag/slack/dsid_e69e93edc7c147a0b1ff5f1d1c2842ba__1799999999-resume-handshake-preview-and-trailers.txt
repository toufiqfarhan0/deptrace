alicia: quick sync  follow-up to the resumable-streaming doc. want to lock down a couple of small but important handshake decisions before we ship: headers vs trailers for resume metadata, how we expose acceptance to clients, and what errors look like.

ben: headers for the initial resume attempt please. trailers are unreliable across some HTTP transports and make retry logic gnarly. headers make the fast-path checkable by edge filters.

marta: agreed on headers for resume token. separate question: should we include a lightweight resume-proof header (HMAC) or accept token that embeds proof? embedding sounds simpler on the gateway.

sam: token embedding wins for fewer round trips. suggestion: token = base64(payload || '.' || signature). gateway verifies signature and TTL. payload contains tenant, call_id, offset, variant, billing_id.

alicia: good. about advertising resume capability: propose gateway returns Accept-Resume: yes|no in the initial 1xx/2xx response headers so SDKs know if they can rely on server resume. if no, SDKs should buffer locally.

ben: small addition: add Resume-Window: <seconds> to indicate how long the gateway will hold resume state. helps SDK heuristics.

marta: +1. Also we need to define backpressure interaction: if gateway accepts resume but upstream starts dropping chunks, we should expose a `Resume-Throttle` trailer when closing so caller knows why resume failed.

sam: trailers only on close. can't use them for initial accept. but the idea of a Retry-Hint in trailer is useful. e.g., `Retry-Hint: resume_expired` or `retry_with_full` so SDK can act.

alicia: what about error codes? earlier RFC suggested 409 for resume conflict. I'd prefer 422 Unprocessable for semantic mismatch (variant mismatch), and 410 Gone for expired resume. 409 for general conflict seems overloaded. thoughts?

ben: I like distinct codes. 410 for expired makes sense. 422 for incompatible state is ok but less common; clients likely to parse our machine error anyway. include `error_code` in JSON body.

marta: concrete mapping proposal: 410 -> error_code=resume_expired, 422 -> error_code=variant_mismatch, 409 -> error_code=resume_invalid (malformed/signature fail). include `hint` field with Accept-Resume: no if we want quick SDK flow.

sam: good. also attach `Resume-Origin-ID` header on successful resume so billing can attribute to original call. if absent, treat as new billing.

infra-bot: rollout: resume-preview feature flagged to canary; config `resume_preview_enabled=true`.

alicia: resume-preview endpoint idea: POST /v1/resume/preview with token in body returns small `head` snapshot and `ok:true` if resume possible. open question: should preview consume the resume lease? I think no, preview must be read-only and not extend TTL.

ben: preview must be non-consuming. otherwise SDKs will race each other and exhaust TTL. preview should be rate-limited.

marta: ops observability: tag traces `resume.preview=true` and `resume.preview.result=ok|not_found|expired|invalid`. emit metric `resume_preview_calls` and `resume_accept_rate`.

alicia: security checklist: tokens HMAC-signed by control plane, include tenant_id and opaque nonce. proxies must validate tenant match. reject tokens that fail signature with 403.

sam: proto snippet for token payload (minimal):
```
message TokenPayload {
  string tenant_id = 1;
  string origin_call_id = 2;
  uint64 offset = 3;
  uint32 expiry_unix = 4;
  string model_variant = 5;
  optional string billing_record_id = 6;
}
// token = base64(payload_bytes || '.' || HMAC(payload_bytes))
```

marta: operational note: store only pointer+tiny metadata in RAM, snapshot full state to SSD. eviction semantics: LRU with configurable grace window. default resume window = 30s, grace under pressure = 10s. emit `resume_eviction` events.

ben: for multi-hop proxies: resume tokens must be validated at the gateway that minted them or any gateway in the same control-plane cluster with shared signing key. Do NOT allow cross-region resume unless signing keys are synchronized.

alicia: can we add `region` into payload so cross-region mismatch fails fast?

sam: yes add `origin_region` field. if mismatch -> variant_mismatch-like rejection.

marta: final UX suggestion: SDKs should include `Prefer: resumable=true; mode=best-effort|explicit`. `best-effort` auto attaches provisional tokens; `explicit` requires developer to handle resume tokens. Default = explicit.
