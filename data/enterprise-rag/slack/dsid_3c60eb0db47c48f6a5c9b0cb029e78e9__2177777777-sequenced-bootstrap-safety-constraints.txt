anya: Quick follow-up on the packaging RFC — I'm proposing a sequenced bootstrap + operator-controlled activation windows for air-gapped nodes. TL;DR: three-phase activation (seed -> verify -> activate) with deterministic sequence numbers and a small backstop policy. Looking for objections and corner cases we missed.

raj: Sounds reasonable. Main worry: what if several nodes are N+1 behind and miss their window because of bandwidth slowness? Do we block rollout or let them catch up next window? :thinking_face:

sylvie: How does this interact with the verifier agent? Do we require per-component signatures or a single bundle signature? Also need to think about memory limits during verify on small boxes.

anya: Proposed config snippet: ```yaml
activation:
  phases: ["seed","verify","activate"]
  window_seconds: 3600  # operator-configurable
  seq_policy: strict  # require exact seq match to activate
```

david: If a node misses the window, what's the backstop? auto-rollback to previous active or mark as needs-operator? I'd prefer failing-safe (serve previous image) over half-upgraded nodes.

anya: Backstop idea: if missed -> mark node as STALLED, keep old active artifacts mounted, and require operator ACK to attempt reapply. Agents should surface failure reasons in a compact enum for UI.

raj: Edge-case: power loss mid-activate. We probably need an atomic apply pattern + idempotent activation steps instead of a full distributed 2PC. Marker files + atomic rename on move seems pragmatic.

anya: Example atomic step (very small):
```bash

```
