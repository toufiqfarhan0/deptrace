maya: quick q — noticed /v1/generate responses now include `served_model` as an object. will older SDKs/clients that expect a string break? example:
```json
{
  "text": "...",
  "served_model": {"id":"redwood-13b-quant", "region":"us-east-1", "tier":"dedicated"}
}
```
old responses used `"served_model": "redwood-13b-quant"`. is there a compatibility plan? also: how do `routing_hint` params get reflected in the response now? cc @alex

alex: short answer — we intentionally kept compatibility. runtime currently returns both forms for now: the object under `served_model` and a top-level string `served_model_id`. plan is to keep the string for two releases before removing it (announce ahead). SDKs should prefer the object when available.

also, we echo routing decisions in a `routing_info` object when the client sends hints (only in v1 for now). example snippet we return in normal responses (non-debug):
```json
{
  "served_model_id": "redwood-13b-quant",
  "served_model": {"id":"redwood-13b-quant","region":"us-east-1","tier":"dedicated"},
  "routing_info": {"chosen_region":"us-east-1", "chosen_tier":"dedicated"}
}
```

sam: quick follow-up on fallback order. if client requests `routing_hint:{region:"eu-west-1", tier:"dedicated"}` and model isn't in eu dedicated, what's the fallback sequence? current impl behaviour matters for our SLAs.

jin: fallback order implemented today is: 1) same-region other-compatible tier(s) (e.g., eu hosted) 2) other-regions same-tier (prefers nearest region by latency) 3) other-regions other-tiers. if a model-variant is incompatible (quant vs fp) we try nearest compatible variant (kernel/quantization-aware). we also include a `fallback_chain` array in debug responses when `?debug=1` is set to help troubleshoot.
