maria.dev: Quick check — seeing sporadic 429s from hosted API right after token refresh during long-lived gRPC streams. Clients reconnect and re-send from start, causing duplicate side-effects. Any recommended pattern?

alexh: thats rough. For gRPC streams we recommend resume tokens + not re-sending full request on 4xx. Treat 429 specially: honor Retry-After if present, otherwise backoff + full jitter.

samir: +1. For Rust client we added a `resume-token` header and a small ack window. Server dedupes chunks by (stream_id, offset) so retries resume rather than restart.

jen: quick code sketch of client backoff we use (full jitter + respect Retry-After):

```rust
// pseudocode
let mut attempt = 0u32;
loop {
  let resp = send_chunk().await;
  match resp.status() {
    200 => break,
    429 => {
      if let Some(retry_after) = resp.headers().get("retry-after") {
        sleep(Duration::from_secs(retry_after.parse().unwrap_or(1))).await;
      } else {
        // full jitter: random(0..cap) where cap = base * 2^attempt
        let cap = BASE_MS.saturating_mul(1u32 << attempt).min(MAX_MS);
        sleep(Duration::from_millis(rand::thread_rng().gen_range(0..=cap))).await;
        attempt += 1;
      }
    }
    status if status.is_server_error() => { sleep(exp_backoff_with_jitter(attempt)).await; attempt += 1; }
    _ => return Err("non-retryable"),
  }
}
```
