devon: Sounds like accumulation precision. flash_fused uses fp16 accumulation in the reduction path to save regs; fp8 logits + fp16 accum -> overflow easy. nvprof shows big reduction variance and a few infs.
anya: Any perf tradeoffs if we switch accumulation to fp32?
mike: Quick perf numbers on canary (13B, seq 4096, batch 24): flash_fused(fp8,acc=fp16)= 42 tps but NaNs; flash_fused(acc=fp32)= 29 tps and stable; flash_stable(bf16 accum)= 34 tps and stable. So fp32 fixes correctness but 30-35% slower.
devon: Another option: log-sum-exp stable softmax before exp. Add max subtraction: y = exp(x - max(x)). That helps but we still see saturation before reduction because of fp8 dynamic range.
anya: If dtype=fp8, maybe kernel selector should prefer stable kernel when paged-kv is enabled or when max_seq*batch > threshold. Current heuristic picks flash_fused for seq>1024 and batched>16.
mike: Agreed. Also paged KV means keys come from many small appends; distribution has heavy tails causing occasional huge logits from attention bias combos.
devon: Short-term mitigation: clamp logits to [-50,50] before exp. Quick patch reduced NaNs in 99.9% of requests, quality diff small on our eval set (delta bleu ~ -0.2).
