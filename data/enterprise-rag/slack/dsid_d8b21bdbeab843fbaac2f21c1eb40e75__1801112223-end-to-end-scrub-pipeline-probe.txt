ingaest-bot: deploy note: current ingest pipeline supports attribute-filter plugin v0.9 that can drop or hash attrs.
maya: proposal idea: two-stage approach
maya: 1) Ingest: deterministic salt-hash user_id/request_id -> request_bucket (e.g., 1000 buckets) + keep ephemeral truncated request_id only for live debug TTL (30m). Store bucket as request.bucket and drop raw request_id.
maya: 2) Exporter/ingest sampling: keep full prompt hash only for sampled traces (sample rate per route), otherwise store prompt_fingerprint (low-entropy) — i.e. prefix-hash(64) -> fingerprint bucket.
tess: how do we compute prompt hash without keeping raw prompt? we can compute HMAC at the caller side (runtime) and send only the HMAC. that still exposes collisions risk but avoids raw text touching telemetry.
aj: runtime HMAC is good, but key management + rotation needed. we should support deriving per-customer salt from KMS and rotate monthly.
liam: about request buckets: 1000 buckets sounds reasonable for dashboards. For rare debug we can surface a support-only ephemeral mapping to actual request_id when customer consents.
eva: consent flow: support can request mapping for a time-limited token; token is audited. ok.
maya: sample config sketch (pseudo):

```
telemetry.scrub:
  ingest:
    attrs:
      - name: user_id
        action: hash_bucket
        buckets: 1000
        keep_ttl: 0
      - name: request_id
        action: ephemeral_truncate
        keep_ttl: 1800  # seconds
      - name: prompt
        action: keep_hmac
  exporter:
    sample_rules:
      - route: "/generate"
        retain_prompt_hash_for: 0.01  # 1% stored fully for eval
      - route: "/embed"
        retain_prompt_hash_for: 0.001
```
