sophie: Quick question — how should gateway resolve conflicts between host patterns, path prefixes, and x-service overrides? Example attached.

chen: we currently do longest-prefix path first, then host exact, then header overrides. But that causes odd behavior when host wildcard matches broader domain.

ajay: can you paste the config example?

sophie: 
```yaml
- match:
    host: "api.prod.example.com"
    path_prefix: "/v1/"
  route:
    service: payments
- match:
    host: "*.example.com"
    header:
      x-service: "payments"
  route:
    service: payments-fast
- match:
    path_prefix: "/v1/payments/health"
  route:
    service: payments-health
```

sophie: In this, request to api.prod.example.com/v1/payments/health with header x-service=payments hits which route? currently selects first match by host+path then header overrides only after. that makes health not hit payments-health.

chen: hmm. I think header overrides should be higher priority than wildcard host, but lower than exact host+path. so ordering: exact host+path > header match (any host) > wildcard host > path-only? not sure.

maria: Agree header > wildcard host makes sense for customer-driven routing (tool calls). But then what about canary routing via header (x-canary)? we need to allow scoped header rules too.

ajay: Suggest a deterministic precedence table we can document and implement. Proposal:
1) Exact host + exact path (literal)
2) Exact host + longest path prefix
3) Header match with host constraint (header + host)
4) Header match without host constraint
5) Wildcard host + longest path prefix
6) Path-only rules
7) Fallback default

chen: That seems ok but adds complexity to matching engine. Perf impact if we evaluate headers early? But headers are cheap compared to routing lookup.

devex-bot: Note: console UX will need to show explicit priority for rules; otherwise users will be surprised. We can compute a "score" column.

sophie: Also need to define ties: when two rules both are exact host+same path length but different services (A/B). We already have rollout tags; tie-breaker should be rule-created-at or explicit priority field.

maria: explicit integer priority is best for overrides. system computes score when absent.

ajay: Edge case: host wildcard with subdomain capture, e.g., '*.app.example.com' — we should prefer more specific wildcard (a.b.example.com vs *.example.com). So wildcard specificity counts.

chen: agree. Implementation: compute specificity metric = host_specificity_weight*host_score + path_length + header_specificity_bonus + explicit_priority
