maya: Quick follow-up on the RFC — proposing a "carrier-chained" upgrade flow for isolated clusters. Idea: a set of trustworthy carrier nodes shuttle signed artifact chunks between airgapped sites, applying staged roll-forwards with lease-based activation. want feedback on failure modes and operator UX.

sanjay: +1 for the concept. main question: how do we ensure idempotent resumes if a carrier dies mid-transfer?

maya: We attach an activation ledger per cluster: chunk-level checksums + sequence id. Each carrier transfer is a transaction with commit markers. Agents keep a tombstone for applied seqids so retries are safe.

eli: Tombstones ok, but storage on small appliances is tight. Can tombstones be windowed (eg keep last N seqids) and rely on manifest epoch validation?

maya: Yes — windowed tombstones + manifest epoch. If request falls outside window we force a manifest re-fetch and full integrity check. Tradeoff: slower recovery vs space. Thoughts?

ashley: Operator UX: we need a one-command audit to verify if cluster is in-flight, stalled, or failed. Something like `rctl carrier status --cluster X` that surfaces carrier id, seq, pending chunks, last-ack.

kyle: For security: carriers must present an ephemeral carrier-signed receipt and a customer-signed manifest. We should separate artifact signing (customer key) and carrier transit receipts (carrier key) to avoid impersonation.

maya: Exactly. Plan: artifacts are signed by customer/vendor key. Carrier attaches a signed transit receipt with nonce and TTL. On activation, agent verifies chain: artifact sig -> manifest epoch -> receipt sig.

eli: Timeout/backpressure model? If carriers are saturated, we should let cluster agent switch to a degraded mode (serve static cached model) and mark upgrade as pending. Don't block inference.

maya: Agreed — fail open to cached model is important. We'll expose policy: `activation_policy: { mode: cached_fallback | block | canary }`. Default cached_fallback.

sanjay: What about partial apply semantics for large model shards? If shard 2 fails after shard 1 applied, how do we guarantee consistency?

maya: We propose staged activation windows: a staging directory holds incoming shards + a staging manifest. Agent validates all shards locally (checksums + signatures) before flipping the active symlink. Swap must be atomic: either all new shards become active or none.

kyle: Atomic swap via rename on unix/fs works, but what about limited-disk devices where staging duplicates exceed capacity? Need an in-place apply strategy for delta-only updates.

maya: Good catch. For constrained devices we support two modes: full-staging (requires 2x space) and stream-patch mode. Stream-patch applies deltas directly with journaled checkpoints so we can rollback to prior offsets if failure.

ashley: The stream-patch mode needs strong checksums and a final manifest-level validation to avoid silent corruption. Also a rollback fast-path operator command.

eli: Monitoring: emit metrics `carrier.transfer.duration`, `carrier.transfer.failures`, `agent.activation.latency`, `agent.rollback.count`. Also a trace id per transfer to correlate logs end-to-end.

maya: Will add. Also want a small RPC snippet for handshake we're considering:

```
# carrier -> agent
POST /v1/transfer/start
{
  "transfer_id": "uuid",
  "manifest_sig": "base64",
  "epoch": 42,
  "chunks": 128,
  "resume_token": "optional"
}

# agent -> carrier ack
200 OK
{ "accept": true, "lease": { "id": "L-123", "ttl": 300 } }
```

kyle: Lease TTLs should be renew-able by carrier heartbeats. If lease expires, agent should abort transfer and garbage collect partial artifacts after a grace window.

maya: Abort semantics: on lease expiry agent marks transfer aborted, records reason, and exposes `rctl carrier recover --transfer TID` to resume with same or new carrier.

ashley: Rollout policy: we should allow cross-cluster chaining: carrier A brings artifacts to cluster 1, cluster 1 can in turn become carrier for cluster 2 (if operator allows). Need explicit operator opt-in to avoid accidental propagation.

eli: That propagation model could help low-bandwidth sites (mesh style), but also opens attack surface; require admin flag `allow_relay = true` and strict receipt chain depth limit.

maya: Final ask: any concerns with telemetry or PII in receipts? receipts should be minimal (transfer id, checksums, carrier id, timestamp) and avoid site-specific configs.

kyle: Agree — redact anything operator might consider sensitive. receipts = minimal.
