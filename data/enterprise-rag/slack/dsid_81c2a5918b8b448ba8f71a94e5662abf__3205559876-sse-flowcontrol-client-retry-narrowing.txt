alex: repro (simplified):
```js
const es = new EventSource(url);
let buf = '';
es.onmessage = (e) => {
  buf += e.data;
  // naive parse:
  try {
    const obj = JSON.parse(buf);
    handle(obj);
    buf = '';
  } catch (err) {
    // JSON.parse: Unexpected end of JSON input
  }
};
```

priya: Yup. Saw this in the web chat client — heavy small-message traffic + emoji split across utf8 boundaries made JSON.parse blow up. We switched to an incremental parser and a small delimiter on the server (ndjson) as a mitigation. PR: https://git.redwood/pr/streaming-ndjson-sample :thumbsup:

matt: Also check auth rotation. If the client refreshes token mid-stream it can trigger a reconnect that lands mid-object on the consumer. Are you rotating bearer tokens frequently?

olga: Two quick options: server-side emit explicit delimiters (ndjson/newline) so clients can parse per-line, or client-side use a streaming JSON parser that can handle partial tokens. Also consider reducing server batch size or emitting smaller, self-contained events to avoid splits.

priya: We used `clarinet` on node and a tiny stateful parser in the browser. For the browser implementation the trick was to treat `\n` as the object delimiter. Also added a tiny keepalive 1-byte ping at intervals so the connection doesn't idle.

matt: For backpressure we experimented with a simple "window" header where client sends current in-flight allowance and server respects it, throttling batch composition. Cut client stalls during load spikes. Not perfect but helped.
