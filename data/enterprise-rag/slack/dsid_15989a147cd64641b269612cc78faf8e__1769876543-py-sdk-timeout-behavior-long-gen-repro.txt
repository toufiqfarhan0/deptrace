sophie: 0.5.1. Minimal repro:

dev-greg: two things to check quickly: 1) SDK 0.5.x changed how default timeouts are applied (there was a bug where read timeouts were being capped at 60s), 2) underlying HTTP client semantics matter — many libs treat `timeout` as (connect, read) or have separate total/connect/read params. If you don't increase the read timeout, long generations hit ReadTimeout even though the model is still generating.

sophie: I'm not using streaming, just want a blocking call to finish.

dev-greg: ok. Workarounds: set an explicit timeout so the read window is long enough. Examples:
```python
# requests-style tuple (connect, read)
client = InferenceClient(api_key=..., timeout=(5, 300))

# or if you construct your own httpx client
import httpx
timeout = httpx.Timeout(None, read=300.0)
httpx_client = httpx.Client(timeout=timeout)
client = InferenceClient(api_key=..., httpx_client=httpx_client)
```
Also note: enabling retry/backoff means a read timeout can trigger a retry which makes the whole operation take even longer or look flaky. If you rely on long generations, either stream tokens or set a sufficiently large read/total timeout and tune retries.
