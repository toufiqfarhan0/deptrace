Alex: quick q — I'm debugging a customer issue and have a snippet of logs that contains a user email and a partial session_id. Is it OK to paste that into #eng for a quick look?

Maria: pinging @sam_security since this sounds like PII.

sam_security: Hey Alex, please don't paste raw emails or identifiers in public channels. Short rules: redact emails and any direct user IDs before posting. Use [REDACTED_EMAIL] and [REDACTED_ID]. If you absolutely need the original, attach it to a support ticket and request access via the eng-sensitive-access Okta group. :shield:

Alex: thanks — is changing alice@example.com to alice@redacted enough, or do you want the whole email replaced?

sam_security: whole email replaced. Partial redaction (alice@redacted) can still be re-identified. Also avoid posting hashed session IDs unless they're HMAC/sha256 with a salt. Example safe snippet:

```
user_email: [REDACTED_EMAIL]
session_hash: sha256(<session_id> + salt)
```

Oliver: quick note — for Hosted API logs there are extra retention rules. If the logs include model inputs/outputs, check the Console's data classification flags before sharing. We also have a built-in "share snippet" feature that automatically redacts common PII. https://intranet/docs/redaction

Alex: got it. One more: stack traces might include absolute file paths that contain customer usernames/ids. Treat those as PII?

sam_security: yes. Any path components that look like user identifiers should be redacted (e.g., /home/users/12345 -> /home/users/[REDACTED_ID]). If you need to escalate with full context, open a ticket with the "sensitive debug" tag and list who needs access. Approvals go through the security on-call and the data-owner.
