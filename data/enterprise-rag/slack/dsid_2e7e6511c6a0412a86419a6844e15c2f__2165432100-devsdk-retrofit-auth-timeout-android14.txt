tariq: Also Android 14 changed some keepalive behavior in the system TLS stack; idle sockets can be closed earlier which makes okhttp get NO_IDLE sockets and triggers reconnects. Could exacerbate races.

maya: I tried a quick Mutex around refresh (Kotlin coroutines) and it dramatically cut duplicates, but still some calls hang waiting on the refreshed token because the Call was canceled by timeout before the Authenticator completed.

alex: Which timeout specifically? OkHttp call timeout or Retrofit's deadline? If calls cancel we shouldn't trigger more refreshes.

maya: Call timeout = 30s, connect/read intact. Sequence: existing call gets 401, Authenticator runs, token refresh takes ~3s, meanwhile more parallel calls get 401 and queue up. Some callers hit callTimeout and are canceled -> okhttp cancels the connection while the Authenticator is still running, leaving in-flight streams weird.

tariq: Workarounds we've used: 1) move token refresh off the OkHttp Authenticator into an application-managed interceptor with a singleflight/synchronized refresh; 2) bump call timeout or return an immediate 401 fallback earlier; 3) use Dispatcher.setMaxRequestsPerHost to reduce bursty parallelism during refresh.

jen: Sample mutex pattern I used: 
```
private val refreshMutex = Mutex()
private suspend fun refreshTokenBlocking(): String {
  refreshMutex.withLock {
    if (tokenValid()) return currentToken
    // suspend network refresh here
    currentToken = api.refresh().accessToken
    return currentToken
  }
}
```
Then interceptor uses refreshTokenBlocking() when 401 detected and retries once.
