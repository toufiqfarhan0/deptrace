maria: heads-up — discovered a confusing onboarding bug in the Go sample app for generators. If the auth token refresh happens while a generator stream is active, the stream sometimes aborts mid-response with a 401-ish retry path and the sample app spawns a goroutine leak. reproducible with short-lived tokens. logs + minimal repro below.

maria: repro steps: 1) run sampleapp with env TOKEN_TTL=5s and REFRESH_BEFORE=1s 2) start a generator stream that yields a long completion (~10s) 3) wait for the refresh to kick in -> stream closes unexpectedly.

maria: sample auth transport (very minimal):
```
func (p *ShortLivedProvider) RoundTrip(req *http.Request) (*http.Response, error) {
 token := p.currentToken()
 req.Header.Set("Authorization", "Bearer "+token)
 resp, err := p.transport.RoundTrip(req)
 if shouldRefresh(resp) { go p.refresh() } // background refresh can race with active request
 return resp, err
}
```

alex: ugh. thanks for the detailed repro. I can reproduce locally. quick question — does the SDK return an explicit 401 or is it "request canceled" from context()?

maria: it surfaces as request canceled in the generator layer. digging in, seems we call the request with the ctx from the top-level stream; the refresh goroutine fiddles with the token provider which triggers a short lock and sometimes cancels the active http.Request (net/http subtle behaviour).

ken: sounds like two separate UX problems: 1) onboarding sample apps showing an anti-pattern (background refresh mutating transport) and 2) SDK streaming semantics should document/reduce sensitivity to auth provider races. we should make the sample app use a TokenSource abstraction that blocks refresh until safe or prefetches proactively.

ken: proposal for short-term fix: update sample app to use a sync TokenSource that exposes Get(ctx) and Refresh(ctx) and ensure the stream uses Get(ctx) once per request instead of relying on a mutating RoundTripper. Also add a note in onboarding doc about token TTLs and long streaming calls.

tj: for longer-term SDK ergonomics, we should consider adding two primitives:
- TokenProvider interface in go-sdk: Get(ctx) (token, expiry, err) + SubscribeRefresh(chan<- TokenEvent) so streaming layers can avoid races
- Stream option: WithAuthRefreshBehavior(enum{Block, Prefetch, BestEffort}) so apps can opt into blocking refresh vs nonblocking refresh.

maria: I like that. Block would cause the SDK to pause starting new requests until Get(ctx) succeeds; Prefetch would attempt a refresh before expiry; BestEffort preserves current behaviour. Default should be Prefetch to minimize surprises.

alex: API ergonomics idea for generators: make the stream helper accept an auth-aware context wrapper, e.g.
```
streamCtx := client.WithTokenProvider(ctx, tp)
gen := client.Generator(streamCtx, model)
stream, err := gen.Stream(streamCtx)
```
this keeps auth boundaries explicit and more discoverable in examples.
