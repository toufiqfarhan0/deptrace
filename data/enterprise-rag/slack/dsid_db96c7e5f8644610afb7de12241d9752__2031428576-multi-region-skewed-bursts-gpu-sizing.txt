maria: Quick share — I ran a short burst sim for the 30B bring-up (q4f16) comparing H100 vs A100 in us-west1 and eu-west1. Wanted to get sizing thoughts before we update the Dedicated pool plan.
kevin: nice, what metrics did you capture? p50/p95/p99? concurrency assumptions?
maria: captured p50/p95/p99 gen latency for 512-token requests, and sustained tokens/s throughput under synthetic 2x and 5x burst factors. Concurrency measured as live requests per GPU.
ash: fwiw, our current autoscale cooldown is 120s which affects headroom needs for short spikes.
maria: results (high level):
- us-west1 H100: p50 95ms, p95 180ms, p99 260ms; sustained 4800 tokens/s per GPU at 16 concurrent requests.
- us-west1 A100: p50 150ms, p95 320ms, p99 470ms; sustained 2900 tokens/s per GPU at 10 concurrent requests.
- eu-west1 H100: p50 110ms, p95 210ms, p99 330ms; sustained 4200 tokens/s per GPU at 14 concurrency (slightly hotter hosts).
- eu-west1 A100: p50 170ms, p95 360ms, p99 520ms; sustained 2700 tokens/s per GPU.
sasha: big delta on p99 between regions — did you control for kernel choices / cuda & driver versions?
maria: yes — same nightly runtime build + kernels. The region delta looks like hotter tail due to cross-traffic on eu cluster (noisy neighbors on some hosts). We can mitigate by stricter instance packing but that's an ops ask.
kevin: for capacity planning, what concurrency target do you recommend per GPU if we want to hit p95 <= 250ms and p99 <= 400ms under normal traffic?
maria: Recommendation: for H100 size to 12 concurrency/GPU (gives p95 ~200ms, p99 ~350ms) and for A100 size to 6 concurrency/GPU (p95 ~300ms, p99 ~480ms so A100 won't meet p99 target).
ash: so if customer requires strict p99 SLO, A100 pools need bigger headroom or we force H100 routing for that customer/route.
kevin: proposed autoscale headroom math?
maria: baseline formula I used: required_gpus = ceil(peak_tokens_per_sec / tokens_per_gpu_under_target_concurrency * (1 + headroom_fraction)). For short burst protection add an extra 20% to account for autoscaler lag and cold KV cache warmup.
kevin: example numbers?
maria: example: peak burst = 200k tokens/s across pool, tokens_per_gpu (H100 @12c) = 4800 -> 200k/4800 = 41.7 -> 42 GPUs -> add autoscale 20% -> 50 GPUs. For A100 (6c) tokens_per_gpu 2900 -> 200k/2900 = 69 -> add 30% -> 90 GPUs (since A100 p99 worse we use more headroom).
sasha: can we use mixed pools + routing policy to prefer H100 during known peaks? That gets us better economics rather than permanently reserving H100s.
maria: yes — routing policies + predictive warmup could steer flagged traffic to H100 and fallback to A100 when not congested. Need canary rules though.
nash: also remember KV cache warmup: first wave of requests has higher tail. Did your sim include warmed KV?
maria: I ran both cold and warm runs. Cold-run p99s were ~1.5x worse for both GPUs for the first 60s window. That's why we add the short-burst extra headroom.
nash: can we reduce cold penalty via pre-warming on scale events? e.g., pre-populate hot models on a fraction of new nodes before routing traffic.
kevin: agree — implement warmup hooks in autoscaler: launch, attach warmup queue to populate KV, mark ready once warm. Costs some complexity but saves persistent overprovisioning.

sasha: what's the kernel/quant tradeoff? Did you try int8 vs q4f16?
