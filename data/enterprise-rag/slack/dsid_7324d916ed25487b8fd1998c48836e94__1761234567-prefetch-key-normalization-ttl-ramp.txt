suresh: quick thread with the end-to-end on the prompt cache experiments i ran this morning. TL;DR: key-normalization + lightweight prefetch improves hit-rate but increases fragmentation on GPU-side LRU, causing occasional OOMs under spike load.

ashley: can you drop the raw numbers?

suresh: baseline: global hit-rate ~62% (prod tail workload). after key-normalization (strip session ids + whitespace normalize) + prefix-hash bucketing -> hit-rate 78%. adding async prefetch (warmed top-5 prefixes per model shard) -> 82% peak.

mike: nice. whats the memory delta on GPU KV?

suresh: +18% GPU KV memory usage on p50; p95 memory climbed ~32% during warmup bursts. CPU-side cache unchanged.

julia: why the fragmentation? we use slab-ish allocator on the GPU cudamem pool?

suresh: we use variable-length entries for KV (kv_key -> kv_value), and our LRU is single-linked. Normalization caused many previously distinct keys to coalesce into slightly larger value churn windows (more inserts/evicts per shard). allocator doesn't coalesce freed blocks, so we get fragmentation leading to peak allocations failing.

mike: did we change TTL?

suresh: experiment variants: 1) baseline TTL=30m, 2) TTL=adaptive (1m-60m ramp based on recent hit-rate), 3) fixed TTL=5m with aggressive prefetch. adaptive gave best steady-state hit-rate but worst fragmentation. fixed short TTL + prefetch was stable memory-wise but lower overall hit-rate (~75%).

ashley: interesting. so adaptive extends TTL when hit-rate high -> keeps items longer -> more fragmentation.

gary: could we do a two-tier approach? small direct-mapped LRU for short TTL hot prefixes + large slab-alloc pool for long-lived entries? reduces allocator churn.

suresh: prototype idea: keep a hotset (top-n by access freq) in a compact fixed-size bucket (no variable frees), everything else goes to variable LRU with GC/compaction window. Hotset reduces churn. I ran a microbench: hotset size=128 reduced eviction churn by ~45% and removed OOMs in 30-min spike test. hit-rate stayed ~80%.

mike: any perf regressions from kernel selection or batching heuristics when we change cache behavior?

suresh: yes small ones: since prefetch causes larger KV hits, we slightly increased average seq_len in the runtime (more tokens served from cache -> smaller generated token batches but more metadata ops). This pushed select_kernels() to pick "fast_small_attention" path 8% more; we saw a 3-5% increase in CPU time in the kernel selector but GPU time decreased p50 by ~6% for short sequences. net latency improved for 75% of requests, tail got worse during evict storms.
