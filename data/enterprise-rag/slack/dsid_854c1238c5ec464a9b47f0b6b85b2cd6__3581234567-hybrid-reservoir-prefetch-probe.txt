hiro: Quick thread — thinking about a hybrid 'reservoir + greedy' prefetch for weights. Idea: small shards (< X MB) are greedily pulled at load time; large shards enrolled into a reservoir that does prioritized background streaming based on token hotness and recent requests. keeps warmup latency low for common layers but avoids thrashing on huge models.

anna.k: curious — how do you define "hotness"? recent kv-cache hits? request freq?

hiro: yeah, KV reuse + request freq + layer position. heuristic: score = 0.6*kv_reuse + 0.3*req_freq + 0.1*(1 - layer_depth_norm). tuned per-model.

samuel: biggest concern is memory fragmentation and pinning. if we greedily pull a handful of small shards across many concurrent inits we could OOM. fallback?

hiro: reservoir has an aggressive eviction tier — LRU with async writeback for overlays. Also a circuit breaker: if memory pressure > 85% we switch to on-demand streaming for non-hot shards.

priya: what about integrity? if we stream partial slices for a shard, do we validate checksums per-range? I worry about silent corruption when falling back between safetensors vs legacy formats.

matt: we could add per-chunk CRC32 in the shard manifest. cheap to compute and verify on receipt; manifest maps ranges and expected CRCs.

hiro: agreed. manifest change would be additive: optional chunk_checksums: [{offset, len, crc32}]. decoder accepts missing checksums.

samuel: how does this interact with zero-copy mmap paths for on-prem? mmap expects page-aligned, whole-file. streaming/chunked will break that path.

hiro: plan: keep mmap path for local files. streaming only used for remote weight sources. provide a memory-view adapter that exposes same read API; if mmap available, adapter is a thin wrapper. else, underlying buffer is a readahead-backed bytearray.

priya: rollout strategy? we should canary on traffic with smaller models first, then move to LLMs. Also add a perf metric: warmup_latency_95, evictions/sec, checksum_failures.

hiro: yep — canary config snippet:

matt: small_threshold seems small — 16MB might make too many shards greedy for quantized models. maybe 8MB for q4_0 and 32MB for fp16. need per-quantization overrides.

samuel: corner cases: model surgery where layers swap in different shard layouts. we need shard-id stable canonical names + versioned manifests so reservoir entries can be invalidated when manifest version changes.

hiro: will add manifest_version and shard_uuid. eviction invalidates entries where manifest_version != current.
