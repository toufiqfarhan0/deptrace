sana: quick one  saw a replay where a demote was applied, then a completed prefetch writeback rehydrated the prefix and subsequent reads returned stale tokens. gist: writeback didn't validate demote epoch before making visible. anyone seen this exact flow?
maria: yep. i traced a similar case in staging. looks like local writeback path doesn't consult tombstone/epoch.
aj: summary of options: 1) strong CAS on prefix meta during writeback (linearizable) 2) publish a tombstone_epoch on demote and have writeback abort if tombstone_epoch > prefetch_epoch 3) local denylist push on demote so local writes check O(1) before commit.
ken: CAS is clean but pay-for-play: extra rpc/lock on hot path. tombstone is cheap but relies on fast propagation. denylist is fast and local but adds an ephemeral state machine.
clara: nit: denylist TTL choice matters. if too short we might still get stale writeback after denylist expires but before background compaction. if too long we hurt rehydrates. propose default 2s.
pavel: implementation sketch: on demote -> observer increments tombstone_epoch and pushes (prefix, tombstone_epoch) to slab-coordinator.local_denylist with expiry. writeback flow: 1) check local_denylist O(1); 2) if miss, read prefix_meta.tombstone_epoch; 3) if tombstone_epoch > prefetch_epoch abort writeback; else commit.
sana: that hybrid seems to cover the window where propagation is slow. code sketch for 2):
```
// prefetch_writeback
meta = read_meta(prefix)
if meta.tombstone_epoch > prefetch.epoch:
  abort("stale-prefetch")
else:
  commit_local_cache()
```

aj: note race: read_meta and commit are not atomic; tombstone could bump in between. CAS path would be: compare_and_swap(meta.generation == prefetch.generation, meta.generation = new_gen) which is linearizable.
ken: maybe we can expose tenant-level policy: consistency_mode = {strong, eventual}. strong => CAS; eventual => denylist+tombstone hybrid. this keeps tenant choice explicit.
clara: question for ops: how much perf hit for a denylist lookup and extra meta read?
