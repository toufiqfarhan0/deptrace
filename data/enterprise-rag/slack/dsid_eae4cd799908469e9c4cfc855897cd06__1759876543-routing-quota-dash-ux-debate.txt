sarah: quick RFC idea — propose we standardize client-visible errors to always include three fields: category, route_hint, quota_hint. keeps internal codes private but gives apps actionable signals.

michael: +1 on making them actionable. can we keep category small set (e.g., transient, quota, auth, degraded)? apps expect stable enums.

priya: worried about leakiness — route_hint could reveal topology. suggestion: make route_hint opaque (short token) + console mapping that expands to human routes for internal teams.

lee: agree with priya. for rollout UX, clients should only get high-level text + machine-friendly fields. console shows the expanded explanation and suggested retries.

raymond: telemetry question — how do we tag traces so backfills can link client category -> internal cause? need a stable mapping table (category -> internal_signals) and a version field in the error.

sarah: good point. propose adding error_version and an optional telemetry_tags array. error_version lets us evolve the contract without breaking clients.

michael: sample header/body shape I sketched:
```json
{
  "error": {
    "category": "quota",
    "code": "QX_42",
    "route_hint": "r:3f2a",
    "quota_hint": "per_minute:120/600",
    "error_version": "v1"
  }
}
```

priya: +1 to versioning. small nit: prefer quota_hint named pairs so SDKs can parse. maybe: quota_hint: ["limit_per_minute", "used"] or key/value map.

raymond: rollout plan: gate v1 on a small set of tenants, emit both old and new fields during transition. add sampling flag for telemetry to avoid volume surge.

sarah: yes, include retry_hint object: {"retryable":true,"backoff_ms":500} but only for categories we trust. avoid encouraging blind retries for quota errors.
