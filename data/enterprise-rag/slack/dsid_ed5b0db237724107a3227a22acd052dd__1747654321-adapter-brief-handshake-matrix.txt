marta: quick q — i've been sketching a micro contract for the adapter edges between hosted/dedicated/private. want sanity check.

ken: tl;dr?

marta: goal: single *capability matrix* per adapter, small handshake, no heavy runtime deps. keep probe lightweight.

sam: +1 to small. what does handshake carry? auth, capacity hints, supported fallback models?

marta: exactly. minimal fields: `version`, `auth_mode`, `kv_cache_support`, `max_batch_tokens`, `fallbacks` (list ids). sample: ```json
\{"version\":\"1\",\"auth_mode\":\"delegated\",\"kv_cache_support\":true,\"max_batch_tokens\":2048,\"fallbacks\":[\"lite-quant\"]\}
```

ryan: are we baking tenancy semantics into that? e.g., sidecar vs control-plane-managed creds?

marta: not directly. `auth_mode` enum covers: `delegated` (sidecar handles keys), `proxy` (control plane proxies creds), `hsm` (customer-managed). ops decisions still separate.

ken: what about capability discovery over slow links? private deploys in low-bandwidth on prem. handshake should be cachable and TTLed. ops-bot: noted: add `cache_ttl_seconds` suggestion. :memo:

sam: fallback behavior: who decides routing when fallback declared? adapter or control plane?

marta: proposal: adapter exposes `fallbacks` preference order but control plane enforces policy. adapter can nominate but not override routing policies. keeps safety for infra.

ryan: that means we need versioned guarantees: if adapter says `kv_cache_support:true` but later disables it during upgrade, control plane should handle smooth demotion. how signal rolling changes?

marta: signal via ephemeral `status` updates plus a graceful drain flag: `entering_readonly` and `eviction_eta`. e.g., {"status":"entering_readonly","eviction_eta":120}. clients should fall back in 2 minutes.

ken: good. also need auth edgecases: when `auth_mode=delegated` and sidecar fails, do we escalate to proxy or fail closed?

sam: prefer fail-open only if explicit policy allows. default fail-closed. we don't want silent auth bypass.

ryan: latency SLOs: adapter should advertise percentile latency budgets for small and long seqs. otherwise routing decisions are blind. add fields: `latency_p50_small`, `latency_p95_small`, `latency_p50_long` etc.

marta: i worry about over-structuring the handshake. maybe offer an *optional metrics* block adapters can provide, not required for minimal handshake.

ken: agree. required vs optional is key. required minimal: version + auth_mode + capabilities (kv_cache, batch_size). optional: metrics, policy hints.

sam: rollout plan? start with hosted + dedicated adapters, then invite private to opt-in. private often has stricter certs — could be slow.

marta: rollout: feature-flag `adapter_handshake_v1`. staged: 1) adapters emit handshake, 2) control plane reads and logs, 3) routing uses values in canary routes, 4) enforce.
