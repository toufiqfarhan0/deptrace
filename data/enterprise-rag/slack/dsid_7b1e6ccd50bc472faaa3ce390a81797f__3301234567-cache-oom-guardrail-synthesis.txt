Taylor: hmm that gap between pre/post KV usage suggests we're not accounting for peak per-request kv allocs during admission. are we summing worst-case kvcosts into the token budget? we only use average estimate today.

Alex: we currently compute token_budget = floor(node_tokens / running_batches) which ignores per-request KV delta. so a burst of long-kv requests can blow headroom.

Sam: quick idea: maintain a KV_headroom_watermark that is subtracted from node_tokens before budgeting. treat it like reserved memory for ephemeral KV growth during a batch.

Raj: +1. but what value? static watermark will either waste capacity or too small.

Mia: I experimented with a dynamic watermark: watermark = max( min(0.15 * node_mem, 64MB), recent_peak_kv_delta ) where recent_peak_kv_delta is a EWMA of the per-batch observed kv delta. config snippet I used:

```json
{"kv_watermark_pct":0.15, "kv_watermark_floor_mb":64, "kv_peak_alpha":0.2}
```

Mia: results: fewer mid-batch evictions, OOM guard engaged earlier so kernel handoff could do a graceful fallback to lighter quantized kernel. throughput dropped ~3% but p99 OOM errors -> 0.

Taylor: kernel handoff — is that the same warm-switch path that changes to int8 kernels mid-request? we worry about correctness / perf cliff.

Alex: yes it's the graceful fallback: if kv pressure crosses high-water then we try kernel_route("quantized_parallel") for incoming batches and selectively drop KV caching for very long sequences.

Sam: how are you signaling pressure? is it synchronous at admission time or async during scheduling? we need to avoid race between admission and actual allocations.

Mia: admission computes a conservative est_kv_delta for each request (based on model, seq_len, past per-request delta table). then admission checks (node_free_mem - watermark) >= est_kv_delta + batch_sum_est. if not, we either delay or split the request into a smaller sub-batch.

Raj: splitting at admission could increase latency for some requests — but better than OOM. did you try prioritized admission where we let small-kv low-latency reqs through first?

Mia: yes — implemented a triage queue: three lanes (low_kv, normal, high_kv). batcher prefers filling low_kv first, then normal, then high_kv. high_kv only scheduled when enough headroom or after a backoff timer. that reduced tail latency for interactive requests.

Alex: any regressions in kernel selection quality? if we push more to quantized kernels we may see slight drop in quality.

Mia: small QoR delta — human eval on 200 prompts shows 0.8% drop in pass@threshold for a couple models, which we deem acceptable behind a canary flag.

Taylor: can we make the watermark adaptive per-GPU as well? some GPUs have more persistent KV fragmentation.

Mia: implemented per-device EWMA + global fallback. per-device threshold better matches fragmentation noise. also added a "soft-evict" signal the runtime can send to the cache manager to proactively compact before kernel launch.
