maria: quick follow-up on the Bloom-backed shadow slab idea i hacked up today. goal: cheap hotness signal for prefetch/evict without per-page counters. low metadata + stream-friendly updates.

kevin: sketch the core idea? :eyes:

maria: we keep a small per-slab bloom filter that records recently-seen page ids (or kv-cache keys). on allocation/read, we add to the slab bloom. periodic decay is done by rotating buffers (two small bloom bitmaps) every N seconds. membership = likely-hot.

sam: so bloom false positives will mark cold pages as hot, right? what's the impact on eviction?

maria: correct. fp means we might prefetch/avoid evicting some cold pages. tradeoff is tunable via bloom size and rotation interval. empirical goal: keep fp < 5% for resident working sets, so eviction pressure doesn't increase.

prashant: how does this interact with current eviction windup + lease tokens? we already have tenant leases.

maria: plan is to use bloom-hotness only as a soft hint: eviction pipeline still consults lease tokens and resident score. bloom=true increments a soft-hot score by X, but can't override a hard-evict if under memory pressure. think "prefer not to evict" rather than "never evict".

kevin: implementation concerns: concurrent updates and memory for bloom arrays. per-slab means many small arrays; could be fragmented.

maria: agreed. idea: use a shared pool of bloom bitmaps (power-of-two sized, e.g., 512B/1KB/2KB) and slab metadata points to an index. allocation chooses smallest bloom that keeps fp target. this reduces heap churn.

sam: can we get away with a single global bloom per GPU to reduce pointers?

maria: we tried that in the prototype — loses locality. per-tenant/per-slab lets us bias prefetchtargets. global bloom leads to noisy aggregation across workloads. hybrid approach: per-GPU coarse bloom + per-slab fine bloom.

prashant: how do we measure benefit? what's the telemetry plan?

maria: metrics to add: bloom_fp_rate (sampled), prefetch_hit_rate_when_bloom_true, evict_false_positives (pages kept but not used within grace window), change in tokenized cost (GPU token time saved vs extra resident bytes). also add a prometheus gauge for bloom_memory_overhead_by_pool.

kevin: config surface? need to be able to disable per-tenant for Dedicated customers or set strict memory caps.

maria: suggested config snippet:

```yaml
memory_hints:
  bloom_prefetch:
    enabled: true
    pools:
      - size_bytes: 512
        bits: 4096
        rotation_s: 10
      - size_bytes: 2048
        bits: 16384
        rotation_s: 30
    score_increment: 0.6
    max_soft_score: 3.0
```

sam: rotation -> do we zero bits frequently? rotation gives decay without per-bit expensive clears, right?

maria: yes. implement as ring of two bitmaps per pool or small ring of 4; rotate pointer and zero the next on rotate. membership check ORs recent rings to approximate sliding window.

prashant: eviction pipeline needs API: is_hot(slab_id) -> boolean/score. also need a callback when bloom indicates rising hotness to trigger async prefetch.

maria: draft API: `int bloom_hot_score(slab_id)` returns discrete buckets (0..N). `subscribe_hotrise(slab_id, threshold, callback)` for async actions. callbacks rate-limited.

kevin: how about correctness with kv-cache KV eviction semantics? race when a page is prefetched and simultaneously evicted by another thread. we need CAS-style ops or best-effort is fine?

maria: best-effort ok for prefetching; for final eviction we still do a compare-and-evict with residency check. prefetch writes into a staging pool then promotes under lock.
