alex: pitching a 'fastpath reinsertion' (aka mergeflow) idea: tiny low-latency requests go fast past the coalesce window, but we keep a lightweight reinsertion path that can fold them into the next batch to reuse KV warms. main concern: avoid creating head-of-line issues for long-running requests.

mira: agreed. merging mid-flight seems risky. can we restrict reinsertion to happen only at safe batch cut points? otherwise a reinsert could delay an already-waiting long request.

sam: practical approach: per-tenant microqueue that only flushes at batch boundaries and only when admission allows. keeps logic local and simplifies packing. downside: next-batch bloat when many tenants burst.

tj: propose a cheap admission signal: "merge_tokens_available" per tenant. each reinsertion carries merge_cost_est (tokens). accept only if tokens >= cost. tokens accrue at credit_rate (tokens/sec). super cheap check.

chen: also add a dynamic headroom guard: if the current batch's remaining headroom < batch_headroom_ms (config), reject reinserts. prevents tail regressions during peaks.

caroline: think about KV fingerprint tagging. fastpath can emit kv_fingerprint for the warmed prefix. reinsertion should prefer batches with matching fingerprint to avoid polluting other affinity groups.

alex: adding kv_fingerprint to batch key is a surface change. we can make it optional (affinity_enabled) to keep rollouts safe. how heavy is the refactor?

mira: minimal for grouping (model, seqlen, maybe affinity). bigger change for eviction: affinity buckets must not monopolize slots. implement per-affinity caps and aging.

sam: ops/alerting: emit metrics mergeflow_attempts, mergeflow_accept_rate, merge_tokens_used, added_tokens_per_batch, p99_delta.post_merge. add alert: if p99_delta > 5% for 5m -> rollback.
