morgan-arch: Quick follow-up to the canary thread 11 proposing a 'micro-cohort rolling' pattern. Instead of big percent slices, we roll very small tenant sets (0.25%-0.75%) but allow probabilistic overlap for faster warmup. Intent: reduce noisy aggregates and make signal attribution per-tenant clearer.

sasha-sre: Sounds promising. How does probabilistic overlap work? Won't overlap increase blast radius?

morgan-arch: Overlap is bounded. Strategy: pick cohort A deterministically, then cohort B contains 10% of A plus new tenants. That overlap accelerates cache warming for subsequent cohorts while keeping isolation.

tomi-platform: Concern: shared infra tenants (reporting, batch jobs) could skew metrics. We should maintain an exclusion list and a "weight" attribute for tenants so heavy ones are scheduled less frequently.

ev an-ml: (typo) evan-ml: Also want a staged model-compatibility check. If the new variant changes tokenizer or detokenization behaviour, overlapping sessions might surface subtle regressions. We should run lightweight diff-evals per cohort pre-commit.

morgan-arch: Agreed. Proposed pre-advance gates: 1) min_requests >= 500 for cohort window 2) perf p50/p95 within thresholds 3) delta-quality below threshold on per-tenant micro-eval.

sasha-sre: Auto-rollback semantics? Immediate rollback vs. staged revert? My vote: immediate drop back to baseline for new requests, but allow in-flight requests to finish with a short quiesce (15s). Also emit an incident event.

morgan-arch: Yup. Implementation: route-map change is atomic for new requests. We flip selector for affected tenant ids back to baseline. Add a soft quiesce for existing sessions and populate a telemetry tag that marks which requests were served during rollback.

```
  p50_ms: 250
  p95_delta_ms: 120

```
