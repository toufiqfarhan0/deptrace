arya: quick question — i'm prototyping a thin 'pin handshake' field for rollout metadata. idea: add `pin.scope` + `pin.handshake` where client can request a tenant-scoped soft pin and get back a short lease token. thinking this helps private deployments avoid global pins. thoughts? :thinking:

mike: i like the direction. two quick tradeoffs: soft vs hard semantics (soft = best-effort affinity, hard = guarantee eviction blockers) and who enforces expiry. if control plane issues lease tokens we need revocation + observability.

sasha: +1 to lease token. also we should be explicit about fallback ordering in the metadata. if tenant-scoped pin not available, do we fall back to region-scoped, model-variant, or return 409? need a client contract.

oliver: ops note — we need cheap probes to avoid pin storms. clients should include `probe=true` flag that doesn't consume slot but validates routing. otherwise a mass-retry could pin everything.

mike: for enforcement, propose AH: control-plane issues `lease_id` and `expires_at`. runtime accepts lease_id for affinity and logs `lease_source`. Revoke flows: mark lease as revoked -> runtime drops affinity on next reclaim window.

arya: rough schema sketch: ```json
{"pin": {"scope": "tenant|region|global", "type": "soft|hard", "handshake": {"lease_id": "uuid", "issued_by": "control-plane", "expires_at": "iso8601"}, "client_probe": true}}
```

sasha: bikeshed: name `handshake` feels vague. maybe `lease` or `affinity_lease`. also add `grace_window_ms` so clients know eviction timing.

oliver: +1 `grace_window_ms`. for hard pins we must surface quota accounting (reserved GPU slots). we can't allow unlimited hard pins. metadata should require `commit_level` for hard pins: `reserved|best-effort`.

mike: compatibility note: older clients will ignore unknown fields. but older runtimes may not honor `lease_id`. we need a migration path: 1) emit telemetry when handshake fields are unused 2) run a canary that returns `lease_supported:true` header so clients can opt-in.

arya: good call. propose control-plane adds `rollout.metadata.capabilities` per tenant: `supports_lease=true|false`. clients can call `/resolve` and check header.

sasha: also think about compact encoding for pins in the routing index. we can't store full JSON per-tenant per-model. suggest a small bitmask + lease pointer id. i.e., index entry: `pin_mask` + optional `lease_ptr` -> resolves to a secondary table.

oliver: operationally, eviction and stale-lease cleanup needs a GC. GC should be async and idempotent: `lease_state: active|revoked|expired|orphaned`. runtime periodically reconciles with control-plane. small windows OK but must be observable.

mike: can we define semantics for `client_probe`? proposal: `client_probe=true` means do not create a lease, just return candidate routing + `probe_ttl_ms`. Also respond with `probe_confidence` if runtime used cached KV vs fresh.

arya: example client flow i imagine: 1) client requests resolve with `pin.scope=tenant&client_probe=true` 2) if runtime reports `lease_supported` and `probe_confidence>0.8`, client then issues full request with `pin.handshake.request_lease=true` 3) control-plane issues lease -> runtime uses affinity.

sasha: we should codify failure modes: if lease issuance fails, client should retry with exponential backoff and degrade to `scope=region` or `global` depending on request SLO. document fallback priority in metadata.

oliver: question on auditing — every lease assignment needs an audit id. include `audit_ref` in handshake so customers can map affinity assignments to billing/ops events.

mike: right. add `audit_ref` and `origin` (api|console|migration-tool). Also TTL enforcement: runtime should cap max lease to prevent runaway reservations. config knob per-tenant `max_lease_ms`.
