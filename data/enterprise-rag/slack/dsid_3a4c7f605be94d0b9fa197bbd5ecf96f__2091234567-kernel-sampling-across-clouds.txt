devon: sure — short summary first: same model (7B int8), same TensorRT-quantized build, different driver/CUDA stacks show consistent throughput but p95 diverges. sara: big p95 gap on GCP. Any kernel differences (cublas vs cutlass) or thermal throttling?

devon: checked kernel selection — TRT chose different GEMM kernels on GCP (fallback to cuBLAS algo 7) under certain sequence lengths. Also saw more memcpy spikes in dmesg (PCIe retrains rare but present).

infra-bot: infra note — GCP host images assigned nvidia-driver-525 by default; some zones on GCP auto-upgrade GPU firmware asynchronously.

mike: did you try forcing the same driver/CUDA on GCP to prove it's the driver stack?

devon: quick follow-up run with 535+CUDA12.1 on a GCP test node — p95 dropped to ~82ms, throughput up to 268 tok/s. So driver/CUDA combo explains most of the p95 delta.

sara: nice. Any quantization sensitivity differences? int8 perf looks similar, but do you see quality regressions with runtime changes?

devon: we ran a small eval set (100 prompts) — logits/likelihood diffs negligible (avg KL ~0.0009). A couple of edge prompts changed top-1 for the 525 stack, but not systematic. Likely kernel ordering + micro-batching timing leads to different RNG ordering for some ops.
