Maria Gonzalez: quick heads-up — I ran a narrow perf sweep on the rolling batcher after the kernel selector changes and hit a surprising kv OOM pattern. TL;DR: some kernels that we route to (fp16 fused-attn) spike transient KV occupancy and cause the batch-acceptor to reject more batches under steady load.

AJ Chen: could you paste the numbers?

Maria Gonzalez: paste from profiler:
```
scenario: steady 100QPS, median seq=512
baseline kernel (quantized-attn): avg batch size=6, accept rate=98%, kv_live=~1.9GB
new fp16-fused kernel: avg batch size=4, accept rate=83%, kv_live=~2.15GB (+13%)
OOMs observed: 6 over 30m, all when queue had 2 long prefixed requests
```

Samir Patel: interesting — so the kernel itself doesn't leak, but its execution path increases per-request temporary KV/aux memory?

Maria Gonzalez: yep. Looks like a combination of a different KV layout + extra temp allocs for fused ops. The runtime's admission currently estimates budget using a per-request token estimate that ignores per-kernel temp overhead.

AJ Chen: that would explain the lower accept rate. Any perf regressions on latency when we fell back?

Maria Gonzalez: when accept drops we see more small batches -> p95 token latency +18ms and CPU jitter up. Also the kernel switch adds a tiny 3-5ms tail when route changes.

Samir Patel: proposal: add a "kv occupancy multiplier" into the admission heuristic, per-kernel. When computing if a request fits in a batch, do:
```
estimated_kv_for_request = base_kv_per_token * tokens + kernel_temp_overhead[kernel_id]
batch_kv = sum(requests.estimated_kv_for_request)
allow if batch_kv + reserved_safety <= kv_capacity
```
That lets us keep current token-budget targets but account for kernel-specific overhead.

Maria Gonzalez: +1. I prototyped a cheap estimator: kernel_temp_overhead derived from median allocator high-water observed in perf runs. We should clamp it (min 0, max 30% of base per-request kv) to avoid being too conservative.

AJ Chen: two additional knobs we should discuss: 1) a soft-skip kernel routing policy — if routing to kernel X would cause >25% drop in batch accept over a short window, temporarily prefer an alternative kernel even if it costs a few ms; 2) a small per-batch spare-slot reserve (like reserve 1 token slot worth of kv) to handle transient spikes.

Samir Patel: Agree on (1). We already have metrics to detect accept-rate regressions; we can hook an experiment: on detection, set kernel_preference_score[kernel] -= 0.2 for 30s. For (2) I'd rather make it dynamic: spare_slots = ceil(0.05 * batch_size) but min 1. That scales with load.

Maria Gonzalez: note: need to avoid oscillation — if many requests are long-prefix (large KV), switching kernels might move pressure elsewhere. I added a dampening window: only apply kernel preference changes if the accept-rate delta persists > 60s and kv-occupancy > 8% above baseline.
