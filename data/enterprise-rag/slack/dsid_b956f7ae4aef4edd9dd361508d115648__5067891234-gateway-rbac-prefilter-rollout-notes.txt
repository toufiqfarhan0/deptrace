maria: Quick thread to capture the gateway RBAC prefilter idea and a safer rollout path. posting rough sketch here so we don't lose it.

ashok: high level: move ultra-cheap auth checks into gateway to avoid expensive fanout. what qualifies as "ultra-cheap"?

maria: token->tenant, token scope allowlists, tenant rate buckets, and static deny rules. no attribute or resource OR enrichment-based checks.

samir: important to call out: prefilter must be conservative on ambiguity. we should default to DENY if cache is stale.

maria: agreed. plan: monotonic rule versions + last-applied timestamp. gateway rejects if version < controlplane_min_version_for_tenant or rule missing. permissive flag only for explicit canaries.

jen: how do we deliver rules? polling or push? both have tradeoffs.

maria: push over a small pubsub (we'll use an internal lightweight channel, protobuf deltas). gateway will also fall back to periodic reconcile (30s).

lee: sync lag detection is key. we should emit metrics: rbac_sync_lag_seconds, rbac_version_gap, prefilter_denies_by_reason.

maria: noted. also add a health indicator: if sync_lag > threshold, mark prefilter in degraded mode (auto-switch to pass-through or conservative deny depending on flag).

ops-bot: deploy note: gateway build 5067891000 passed staging tests. feature flag gate=rbac_prefilter created.

ashok: runtime complexity: gateway now holds per-tenant rule sets; memory impact? do we shard the cache?

maria: cache per-process but with LRU evictions + per-tenant size cap. rough numbers: 10k tenants * avg 2KB rules ~ 20MB, safe. we'll cap at 200MB process mem for rules and advertise eviction metrics.

ricardo: be careful with batching semantics. If we batch requests across tenants we mustn't leak a tenant's allowlist into another tenant's evaluation. batching should be intra-tenant or tag-aware.

maria: good catch. default: batch_window_ms applies only inside same-tenant buckets. optional cross-tenant multiplexing behind explicit opt-in for low-risk tenants.

samir: testing: we need a perf harness that simulates 80/20 read-heavy dashboards, with ~15% of requests denied early. capture p50/p95 end-to-end and backend CPU.

maria: I'll add a scenario in perf-lab named `console_prefilter_fanout_reject`. tie into our existing k6 scripts.

jen: rollout steps?

maria: propose: 1) implement feature-gated prefilter, default off; 2) unit/integration tests + perf harness; 3) canary: enable for internal tenants and 5 pilot customers in permissive-mode (log-only) for 24h; 4) enable conservative deny for those tenants for 24h; 5) expand % rollout by monitoring prefilter_denies, backend_tail_latency, and error rates; 6) global rollout with kill-switch.

lee: add an escape hatch: gateway admin API to invalidate a tenant's rule set and force immediate reconcile. ops needs RBAC to call that API.

maria: will add `POST /admin/tenants/:id/invalidate-rules` guarded by operator certs.

ashok: instrumentation: sampling traces where prefilter rejects + full trace on any unexpected backend call where prefilter would have denied. helps find mismatches.

maria: yes. also store a tiny audit event for all denials for 7d. not full payloads, just rule_id, tenant_id, timestamp, request_hash.

ricardo: config example? paste please.

maria: config snippet:

```
console.gateway:

```
