maya: quick sync — i'm proposing we add a `criticality` enum to runtime flags (low/medium/high) so console shows which config changes need stricter rollout windows and approvals

alex: sounds reasonable. what's the behavioral difference between medium and high?

maya: high = require 2 approvers + canary <= 1% by default + audit entry + rollback playbook linked in UI. medium = 1 approver + canary 5% + telemetry gating required. low = no approver, just normal rollout.

sam: how do we enforce approver counts? existing console only has single-approval flow.

nidhi: we can reuse the approval webhook + add `required_approvals` field in API. console can grey-out the activate button until approvals met.

paul: need to be careful about automation. some infra flags get toggled by scripts — will this break them?

maya: good point. we should support `service_account_bypass` with an audit exception. bypass must be scoped to a principal and recorded in audit log with reason.

alex: telemetry gating — what's the contract? is it blocking activation until X metrics are observed?

maya: not blocking exactly. activation goes to canary cohort but the rollout won't expand beyond canary if error_rate increase > threshold for N minutes. We need a `telemetry_policy` object: metrics, windows, thresholds.

sam: can we reuse the existing evals infra? we already have per-route latency and error dashboards.

nidhi: yes; runtime will emit rollout events to `rollout.ingest` with `config_id`, `cohort_pct`, `metric_snapshot`. console will evaluate policy and show stop/start suggestions.

paul: API semantics question: how do we compute "effective config" when there are per-route overrides, env overrides, and a global flag criticality?

maya: proposal: precedence order -> route override > environment > global default. `effective_config` in API returns resolved object + provenance array of strings (e.g., "route:cart:override", "env:prod", "global").

alex: provenance as array is fine, but provenance must be small (strings) not nested objects per decision.

sam: need to ensure telemetry tagging includes the provenance so we can slice regressions to overrides vs global.

nidhi: runtime metric tags will include `config_source` and `config_id`. that should be enough to filter.

paul: deprecation windows — we should prevent deleting a config that has active route overrides.

maya: yes: delete API either 1) rejects with list of active usages, or 2) marks `deleting` and auto-notify owners with 7d window. default -> reject.
